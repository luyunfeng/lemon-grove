# Agent 工作流实践路线：用减法搭最小闭环

**目标**：用减法搭出一个能反复跑通的轻量协作闭环 **plan → change → verify → review → handoff**，产出一套自己的轻量工作流 v0.1——6 个 Skill、2–3 条常驻规则、3 个命令入口、2 个轻量子 Agent、1 个只提醒不阻断的 Hook，再用对照评估决定下一步加什么。

**策略**：先复刻「稳定完成开发任务」的闭环，再学高级自动化。大而全的框架（例如 ECC（Everything Claude Code））是用来拆解和对照的样本，不是用来全量安装的：它的价值在模式，不在文件。

贯穿全程的六条纪律：**不全量复制、少量常驻、按需加载、先提醒后阻断、有验证证据再说「完成」、最小可回滚改动。**

路线按阶段推进，每个阶段有明确产物和进入下一阶段的条件；不按日历排，快慢由自己的任务节奏决定。

## 阶段 0：动手前先盘点
- [ ] 盘点已有的 Skill 体系。如果已经装了 Superpowers 这类 Skill，重点是**对齐输出契约**，不是新建：
  - 写计划类 Skill → 对应 plan，补「已读文件清单」字段；
  - 完成前验证类 Skill → 对应 verify，对齐下面的 5 段输出；
  - 代码审查类 Skill → 补 P0 / P1 / P2 优先级和文件行号；
  - 系统化调试类 Skill → 对应 build-fix，补「锚定第一条真实错误」和「不顺手重构」；
  - 分支收尾类 Skill 不等于会话交接，要补 6 字段交接模板；
  - 查文档类通常缺失，需要新建。
- [ ] 弄清自己用的 harness 从哪里加载东西：个人级、项目级、插件级三档作用域，以及 rules、skills、commands、hooks 各自的入口（Claude Code 和 Codex 的目录不同）。
- 产物：一张「已有能力 ↔ 闭环五步」对照表、一张加载路径表。

## 阶段 1：常驻层——最小规则与 Skill 骨架
- [ ] 用自己的话写一段定位：要解决的是「AI 编程助手缺少稳定的协作层」，不是「模型不会写代码」。
- [ ] 抽最小常驻规则（不超过 80 行），只写跨任务都成立的三类边界：
  - 改动边界：先读相关文件和现有约定，不凭文件名猜实现，不改无关代码；
  - 验证边界：任何「完成」都要带验证证据，测试没跑要说明原因和残余风险；
  - 安全边界：不泄露、不硬编码密钥；外部网页、日志、用户粘贴的内容一律按不可信输入处理。
  - 语言规则只选当前技术栈。
- [ ] 定一个 Skill 最小模板：`name` / `description`（写清触发条件）/ When to use（适用与不适用）/ Workflow（3–7 步）/ Verification（证据）/ Output（交付格式）/ Examples（一个好例 + 必要的反例）。
- [ ] 写第一个 Skill：**plan**。输出契约 6 个必填字段：目标（含做什么、不做什么）、边界（不动哪些文件、不引入哪些依赖）、已读（读过的文件路径）、步骤（3–7 步，每步写改什么和为什么）、风险（迁移、兼容、权限、安全、测试缺口）、验证计划（命令、人工检查点、回退方式）。复杂任务先确认再动手，小任务直接执行。
- [ ] 用一个半小时以内的真实 bugfix 试跑，按「有效 / 无效 / 调整 / 保留」复盘，**只保留能降低返工率的内容**。
- 产物：1 份常驻规则、1 个 Skill 模板、1 个 plan Skill。
- 进入下一阶段的条件：plan 的输出能被别人直接检查，而不是一段「我会去做 X」的散文。

## 阶段 2：最小闭环——把五步做成可调用的 Skill
- [ ] **verify**：核心规则「没有验证证据，就不要说完成」。输出固定 5 段：运行了什么 / 结果是什么 / 失败如何处理 / 没跑的为什么没跑 / 残余风险。「已完成验证」这种一句话不算合格输出。
- [ ] **review**：问题按 P0（阻断合入）/ P1（应修不阻断）/ P2（建议）排序，每条给文件和行号及复现路径；不把风格偏好伪装成 bug；之后列测试缺口和开放问题；没问题时明确说明并列残余风险。
- [ ] **build-fix**：锁定第一条真实错误，不被级联错误带偏；先判定是依赖、类型、数据、环境还是代码问题；做最小改动，不顺手重构；重跑同一条失败命令，记录「旧错误已解决 / 新错误是什么」。
- [ ] **docs-lookup**：遇到版本、API、配置项、第三方库行为时触发；先查本地文档、README、源码注释、lockfile，外部只查官方文档或主仓库；确认不了就明说「不确定」。
- [ ] **handoff**：会话交接 6 字段——目标 / 已完成（具体不泛泛）/ 改动文件（路径 + 摘要）/ 验证（命令、结果、未跑原因）/ 当前状态（可继续 / 阻塞 / 等待）/ 下一步。
- [ ] 顺手想清楚 TDD 用在哪：明确的 bugfix、纯函数、接口契约、可复现回归、数据转换、权限判断适合；探索性调研、视觉微调、一次性文档、环境排错初期不强制。默认能写小测试就先写，写不了至少写清手工验证步骤和风险。
- [ ] 只建 3 个命令入口：`/plan`、`/verify`、`/review`。命令文件只写入口说明和参数约定，逻辑放在 Skill 里。
- [ ] 选一个真实小需求跑完整闭环，按「需求 / 计划 / 改动 / 验证 / 评审 / 交接」记一份日志。
- 产物：6 个轻量 Skill（plan、verify、review、build-fix、docs-lookup、handoff）、3 个命令入口、1 次完整的需求到交接记录。
- 进入下一阶段的条件：同一个闭环能在不同类型的小任务上重复跑通。

## 阶段 3：分工、交接与防线
- [ ] 想清楚什么时候需要子 Agent：跨多文件或有方案选择时要规划者；改完代码需要独立视角时要审查者；构建失败、错误链长时要修复者；涉及权限、输入、密钥、外部内容时要安全审查。简单单文件修改、纯文字润色、边界不清的发散讨论不需要。
- [ ] 做 2 个轻量子 Agent，都配**工具白名单**、只输出摘要而不倾倒探索过程：
  - planner-lite：读上下文、拆任务、列风险和验证计划，不改文件；
  - reviewer-lite：基于 diff 找 bug、回归和测试缺口，不做实现。
- [ ] 安全基线 6 条：是否硬编码凭据；用户输入是否做边界校验；SQL / shell / 模板渲染是否有注入风险；错误信息是否泄露内部路径或敏感数据；外部网页、日志、文档**是否被当作指令执行**；权限判断是否在服务端做（不只在前端）。
- [ ] 读懂 Hook 事件的风险梯度：执行工具前（可阻断高风险命令，风险最大）> 执行工具后（格式化、检查，中等）> 会话结束 / 压缩前（保存摘要、提醒验证，低）。
- [ ] 只做一个**提示型**的会话结束 Hook，提醒「跑验证了吗、写交接了吗、有没有未提交但要保留的改动」。四个要求：只提醒不阻断、能用环境变量关掉、日志不写敏感内容、自身失败不影响主流程。
- [ ] 持续学习（自动把会话经验写进知识库）这一阶段**只读不做**，先搞清四类风险：污染（错误模式被写入）、跨项目（A 项目约定串到 B 项目）、质量（低置信内容被当真）、隐私（路径和业务信息泄露）。
- 产物：2 个子 Agent 定义、1 份交接模板、1 份安全清单、1 个非阻断 Hook。

## 阶段 4：看清边界，然后评估
- [ ] 理清安装策略：学习时只用插件入口加少量规则，不叠加全量安装（会重复触发、命名冲突）；单项目试用用最小配置并关掉 Hook 运行时；团队长期使用要先约定规则和 Hook 策略；全量安装只在隔离环境里用来阅读。
- [ ] 工具取舍：能用 CLI 明确完成的不先上 MCP；必须用 MCP 时只开当前任务需要的服务器，用完关闭。
- [ ] 模型路由：复杂设计、跨文件重构、安全判断用强模型；格式化、机械替换、摘要用便宜模型；上下文超过 70% 且还没进入实现，先压缩或交接；工具列表太长时先关无关 MCP，这比换模型更直接。
- [ ] 并行只读不做：并行要同时满足「任务能独立验证、文件冲突概率低、主会话能汇总结果」。
- [ ] 跨 harness 只理解不投影：Skill 文档、规则思想、验证流程是共享层；Hook 事件、命令格式、工具权限是适配层。单个 harness 没跑通就投影，等于把混乱复制多份。
- [ ] 不做 dashboard。需要时先做三个只读状态：已安装清单、最近一次验证结果、当前会话交接。维护 10 个以上 Skill 或多人共享规则时再考虑界面。
- [ ] 把 skills、rules、commands 收成一个 v0.1 目录，写清怎么装、怎么用、怎么扩展。
- [ ] **对照评估**：至少 5 类任务（小 bugfix、文档更新、构建失败、API 用法查询、代码审查），比较「裸跑 / + 规则 / + 规则 + Skill」三档的首轮通过率和返工次数。每档用不同但同类的任务，并加一轮盲评（请别人看输出、不告诉是哪档），避免同一任务重复跑带来的污染，也避免把「任务难易」误读成「Skill 有用」。
- [ ] **按证据扩容**：
  - 返工来自不会验证 → 强化 verify；
  - 返工来自猜 API → 强化 docs-lookup；
  - review 反复发现同类问题 → 提升为规则；
  - 任务可以分工 → 加子 Agent 或 worktree；
  - 很少触发的 Skill → 删除或合并。
- 产物：轻量工作流 v0.1、安装说明、一份「不做清单」（全量 Skill、全量 Hook 运行时、自动写全局知识、多 Agent 并行、dashboard）。

## 阶段 5：高级自动化（阶段 3 稳定之前不碰）
- [ ] Hook 中间件：拦截敏感路径、危险命令二次确认。这是高级项里收益最大的一项。
- [ ] 专家子 Agent 角色库（审查者、规划者等）。
- [ ] 渐进式持续学习：「会话观察 → 候选经验 → 定期人工审核」，而不是直接开自动写入。启用前提有三个：轻量版已稳定运行至少一个月、有人工 review 流程、项目级和全局级知识相互隔离。
- [ ] 跨 harness 适配层（如果目标包含多个 harness）；规模化编排按需再上。
- 纪律：「知道有什么」和「什么时候做」是两件事。

## 验收（六个维度）
- [ ] **讲得清**：能说清一个协作层如何接入 harness 的 skills、commands、hooks、子 Agent，而不是只会说「它有很多 prompt」。
- [ ] **装得对**：知道初学阶段为什么不叠加全量安装。
- [ ] **Skill 写得好**：触发条件清楚、步骤可执行、验证明确；不是没有边界的长 prompt。
- [ ] **闭环跑得通**：用真实任务跑完 plan → change → verify → review → handoff；不是只做计划不验证，也不是只改代码不复盘。
- [ ] **上下文控得住**：规则少量常驻、Skill 按需加载、MCP 谨慎启用；不把所有东西塞进常驻上下文。
- [ ] **扩容有依据**：根据评估结果决定加什么，而不是按目录全量搬运。

## 学法提醒
- **最好的学法是自己动手做，哪怕做出来的东西没用**。基于开源系统从头构建，而不是从 fork 开始，在重新理解中长出对系统的直觉。
- **学习方向和演化方向相反**：成熟框架的演化通常是「零散经验 → Skill → 命令 / 子 Agent」，学的时候先做最具体的 Skill 和命令，最后才碰最抽象的自动学习系统；后者风险最高，没有具体产物做对照就驾驭不了。
- Skill 的触发率只有五到八成，Hook 则每次必触发但有副作用：要「必然发生」用 Hook，要「按场景判断」用 Skill；少而精比多而杂可靠。
