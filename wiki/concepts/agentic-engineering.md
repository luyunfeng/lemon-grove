# Agentic Engineering（智能体工程）

> 当 Agent 成为代码的主要执行者，工程的重心从「写代码」转向定义意图与约束、设计验证与治理、承担判断。它要解决的问题是：代码产出不再稀缺之后，怎样让这些产出可靠、可控、可复利。

## 要点
- **稀缺的东西变了**。生成代码变得便宜，稀缺的是：说清楚要什么、证明它做对了、决定该不该上线。人的角色从亲手写代码的人变成意图架构师、协调者和审计者。
- **人从 in the loop 走向 on the loop**。in the loop 是困在回路里逐个补洞；on the loop 是站在回路之上，设计约束、反馈信号、自动修正规则和介入节点。人不是从系统里消失，而是上移到更合适的抽象层。
- **四种新的核心能力**：意图表达（以足够的清晰度和约束定义目标）、架构监督（多个 Agent 如何协调）、质量校准（定义什么叫「好」）、伦理治理（Agent 行为与组织价值一致）。
- **价值落在判断力上**，分三层：Build the Right Thing（做对的事）、Build the Thing Right（选对技术路线、source of truth 和验证边界）、Run It Right（上线后能观测、能衡量效果）。
- **按模型能力设计系统，而不是追名词**。评估一个方案时先问：如果模型能力提升 10 倍，这个方案的效果能否同步放大 10 倍？能随模型变强而放大的投入（Prompt 质量、上下文管理、工具能力设计）才是高杠杆；为补偿当前模型短板而堆的复杂结构，会随模型进步变成负担。

## 怎么做
Agentic Engineering 是一个根概念，具体落到几件事上：

1. **管住输入**：模型每一步能看到什么、看不到什么，见 Context Engineering（上下文工程）。
2. **包一层控制系统**：用反馈闭环约束会漂移的概率模型，见 Harness Engineering（驾驭工程），以及它的外层延伸 Loop Engineering（循环工程）。
3. **定义「对」**：事前把意图写成规格，见 Spec 驱动开发与执行前校准（Vibe / Plan / Spec）；事后用证据确认，见 Verification（验证）。
4. **让经验复利**：每次工作都沉淀成规则、Skill、文档，让下一次更容易，见 Compound Engineering（复利工程）。

**组织层面**：单个工程师的效率已经明显提升，大型组织的问题变成「有没有能力治理这些代码」——边界、可评审的产出、安全回执、成本预算。采用路径可以分四阶段：

| 阶段 | Agent 能做什么 | 前提 |
|---|---|---|
| 1. 咨询与只读 | 检查代码库、总结事件 | 无写权限 |
| 2. 有界写入 | 可以开 PR | PR 必须附带测试和证据 |
| 3. 专用工作流 | 依赖升级、测试改进、安全审查等固定场景 | 场景边界清楚 |
| 4. Agent 团队 | Planner、Builder、Reviewer、Security、Release 分工协作 | 治理、证据、预算齐备 |

两类失败要同时避免：**欠采纳**（只把 AI 当本地聊天助手）和**过度自治**（组织还没准备好就给 Agent 大范围权限）。规模化部署还需要明确的负责人：最小可行的做法是指定一个 DRI，拥有配置、权限策略、插件市场和入口文件规范的决策权。

**人审什么**：Agent 产出太多时，人工审阅从「逐个写和看补丁」转为「接受证据」：设定自动接受标准，只有关键区域才提交人工。

## 为什么
- 生成与验证的成本不对称：生成越来越便宜，验证仍然贵，所以工程投入要向验证、约束和反馈倾斜。
- 能力的天花板仍然明显：Agent 在孤立任务上成功率可以超过 80%，在连续演进的真实场景里会跌到 38% 以下；验证保真度不足（通过了测试却引入细微的语义错误）是主要障碍之一。完全自主开发仍是长期挑战，人的判断不能缺位。

## 边界与误区
- **误区：会写 Prompt 就是 Agentic Engineering**。Prompt 只是最内层；真正的工作量在上下文、验证、约束和治理。
- **误区：人可以退出**。验证「完成」仍要有人负责。循环产出越快，人对系统的理解差距（理解债务）越大；不加判断地接受 Agent 返回的一切，是「认知投降」。
- **缄默知识写不完**。历史背景、低频风险、人际信息很难被完整、无损地写成规则。学徒制和现场经验（code review、线上排障、发布回滚）仍然是判断力的来路，不能指望全靠文档和 AI 替代。
- **追名词的陷阱**。新名词层出不穷，但只有随模型能力放大的投入才值得做；否则等模型升级，搭的结构就要拆掉。
