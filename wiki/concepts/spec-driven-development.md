# Spec 驱动开发与执行前校准（Vibe / Plan / Spec）

**一句话**：Vibe Coding、Plan、Spec 的区别不在「谁更高级」，而在**把多少校准机会前置到执行之前**。Spec 驱动开发是这条光谱最重的一端：写代码前，人和 Agent 先就「为什么做、改什么、怎么做、怎么验收」达成一致，并把共识写成可审查、能进仓库的产物，解决「需求只活在聊天里，Agent 只能靠猜」的问题。

## 要点
- **一条校准光谱**：
  - Vibe Coding：只说目标，Agent 自己定方案、拆任务、写代码；
  - Plan：执行前加一次方向校准，先对齐需求和方案再动手；
  - Spec：把需求、设计、任务拆解都纳入「用户输入 + Agent 执行 + 用户审查」的循环。
- **按任务选仪式**：任务越复杂、越长期，越值得为额外校准付流程成本；小需求走完整 Spec 仪式不划算；需求边界还在收敛、实现成本又不低的任务，Plan 往往投入产出比最高。
- **Plan 的价值在校准，不在文档**：真正起作用的是执行前那次方向对齐，文档只是副产品。
- **Spec 定义的是「正确」本身**：用控制论的话说，先有目标值，系统才能测量偏差。Spec 给出目标值，Verification（验证）负责测量。
- **约束比代码值钱**：Agent 能生成任意代码时，稀缺的是约束——什么不能做、什么必须做、什么优先级更高。「以足够的清晰度和约束条件定义目标」本身成了工程师的核心能力。
- **Scope 比实现重要**：「做不做」比「怎么做」重要得多；业务级代码评审也必须以 Spec 为依据。

## 怎么做

### 一条完整的执行前流水线
| 阶段 | 解决什么 | 典型做法 |
|---|---|---|
| 探索路线 | 目标明确、路径模糊，连该问什么都不清楚 | 先写一句 Destination（这轮结束要拿到什么）；建一个共享「地图」主 Issue；把未定的部分拆成 grilling（需要用户回答）/ prototype / research / task 四类子问题；每次只推进一个 Frontier 问题并回写地图 |
| 澄清需求 | 用户脑子里的隐性需求、术语与冲突 | 拷问式多轮对话：一次只问一个问题并附推荐答案，主动指出冲突（例如「零后端」和「AI 生成主视觉需要调外部图像 API」互相矛盾），把术语和架构决策沉淀成 `CONTEXT.md` 与 ADR；或者给出 2–3 种方案，以 200–300 字一段分段确认设计 |
| 形成规格 | 对话不可执行 | 写成规格文档：Problem Statement、Solution、User Stories、Implementation Decisions、Testing Decisions、**Out of Scope** |
| 拆任务 | 大任务不可控 | 拆成带依赖、标出可并行项的 ticket；或拆成 2–5 分钟一步的计划，写明精确文件路径、测试代码、命令和预期输出 |
| 实现与审查 | 实现过程需要纪律 | TDD + 代码审查；两阶段审查：先查是否符合规格，再查代码质量 |

两个细节值得单独记：
- **Out of Scope 是给 Agent 的护栏**：写明这一版不做什么，防止 Agent 自行扩展需求。
- **把执行者当成「热情但品味差、判断力差、没有项目上下文、讨厌写测试的初级工程师」来写计划**：这解释了为什么计划要细到文件和命令。

### OpenSpec：把 Spec 工具化的一种方法
OpenSpec 是一个面向 AI 编码助手的 Spec 驱动开发工具，理念是「流动而非僵硬、迭代而非瀑布、面向存量项目而不只是新项目」。它在写代码前加一层轻量规格，先对齐要做什么。
- **目录即方法**：`openspec/specs/` 放系统当前已生效的规格（当前事实）；`openspec/changes/<change>/` 放每个变更各自的 `proposal.md`（为什么做、改什么）、`specs/`（需求与场景）、`design.md`（技术方案）、`tasks.md`（实现清单）。核心思想是**把「当前事实」和「拟议变更」分开**。
- **规格写法**：普通 Markdown，按 Requirement + Scenario 组织，场景用 WHEN / THEN 描述；变更里的规格用增量形式（如 `ADDED Requirements`）表达，归档时并回主规格。
- **工作流**：默认路径是 `/opsx:explore`（不落变更，先讨论）→ `/opsx:propose`（生成变更包）→ `/opsx:apply`（按 tasks 实现）→ `/opsx:archive`（归档并更新主规格）；扩展流程还有 `/opsx:new`、`/opsx:continue`、`/opsx:ff`、`/opsx:verify` 等，通过 `openspec config profile` 启用。

两种规格形态的取舍：
- **持续演进的主规格库**（OpenSpec 式）：每次变更归档后并回主规格，规格库始终描述系统现状，适合长期维护的存量项目；
- **单次需求的规格文档**（to-spec 式）：一次需求一份规格，轻、快，适合一次性功能或小团队。

两者的共同点是规格都**进入仓库**而不是留在聊天记录里，所以天然和 Compound Engineering（复利工程）接上：归档的规格就是下一次变更的上下文。

### 实践要点
1. **先判断路线清不清楚**：路线不清先探索；已有想法先拷问式澄清；需求稳定再写 Spec、拆任务。
2. **一次只问一个问题，并附推荐答案**，降低用户的决策成本。
3. **每份 Spec 都写 Out of Scope 和 Testing Decisions**：前者防需求蔓延，后者给验证回路提供锚点。
4. **进入编码前清空上下文**：规格落盘后清掉澄清阶段的对话，把窗口留给实现。
5. **变更回到澄清**：新需求不要直接补代码，重新走一遍澄清，把新决策沉淀进项目知识。
6. **按复杂度选重量**：小改动 Vibe 即可，中等不确定性用 Plan，长期复杂变更上完整 Spec。

最轻的一端，可以把同样的精神压缩成两条执行习惯：**Think Before Coding**（不替用户补假设，有歧义就问，有取舍就讲）和 **Goal-Driven Execution**（把命令式任务改写成可验证的成功标准，先定验证方式再改，多步任务先列短计划和验收点）。

## 边界与误区
- **Spec 越重越好？不是**。完整 Spec 对小需求是负担；需要时应能回退，灵活性优先于刚性推进。
- **有了 Spec 就不用验证？不是**。Spec 解决的是「做什么、怎么做」的对齐，回答不了「写完怎么确认写对了」。只强调流程、不建反馈闭环，Agent 可能只是「按流程稳定地产出错误」。
- **Spec 不是 plan 的同义词**：plan 定步骤，Spec 定目标、边界和验收标准。Spec 可以交给按步骤执行的 plan，也可以交给只看结果的 goal / 循环（见目标驱动与计划驱动（Goal vs Plan））。
- **开放问题**：如果工程师的主要工作变成设计约束边界，描述边界的「语言」会是形式化规范、自然语言，还是新的 DSL？
