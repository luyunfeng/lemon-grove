# Agent Skill

> Agent Skill 是一个按需加载的**专家能力包**：一份 `SKILL.md` 写清什么时候用、怎么判断、按什么流程做，旁边可以附带细则、模板和脚本。它解决的问题是：把反复出现、需要专家判断的工作方法沉淀下来，让 Agent 在需要时才把它装进上下文，而不是每次靠临场发挥或一段越写越长的提示词。

## 要点
- **Skill 不是更长的 Prompt**。一个合格的 Skill 至少包含：触发边界（何时用、何时不用）、决策逻辑、反模式、输出模板，能脚本化的检查交给脚本。缺了这些，它只是换了个位置存放的提示词。
- **不是所有任务都值得做成 Skill**。判断标准可以记成一个式子：反复出现 + 足够复杂 + 需要专家判断 + 对输出质量有要求。简单、低频、一次性的任务，直接说一句话更省事。
- **按需加载是它的核心机制**。启动时只加载每个 Skill 的名称和描述；任务匹配上以后才加载 `SKILL.md` 正文；真正用到时再读取脚本和附带文件。这让一个 Agent 可以挂很多 Skill，而常驻上下文的成本只有几行描述。
- **Skill 属于「流程」这一层约束**。它比入口文件（CLAUDE.md / AGENTS.md）里的建议更结构化，但仍然依赖模型选择触发，做不到每次必然执行；必须每次发生的事要交给 Hook 这类确定性机制。
- **安装位置本身是接口**。Skill 要装在工具官方承诺会扫描的目录里，不能依赖当前环境碰巧能用的路径。

## 怎么做 / 为什么

### 一个 Skill 由什么组成
| 部分 | 放什么 | 作用 |
|---|---|---|
| frontmatter | `name`、`description`（有的工具还支持 `when_to_use`） | 常驻上下文，决定能不能被找到、会不会被触发 |
| `SKILL.md` 正文 | 核心流程、判断分支、资源导航 | 匹配后加载，是 Skill 的主体 |
| `references/` | 细则、检查清单、反模式、案例 | 需要时再读，避免正文膨胀 |
| `templates/` | 输出模板 | 让产物结构稳定 |
| `scripts/` | 格式检查、字段校验等确定性动作 | 把能机器判断的部分从模型手里拿走 |

### 为什么要按需加载
上下文是稀缺资源，塞进去的每一段都在和当前任务争注意力。Skill 的三级加载（元数据 → 指令 → 资源和代码）是渐进式披露最典型的落地：模型先知道「有这么个能力」，需要时才看到细节。同一个思路也用在 CLI 设计上：顶层一句话说明，按需 `--help`，执行时才给完整参数。部分工具还支持把 Skill 绑定到特定路径，只在相关代码区域自动加载。

### Skill 和其他载体怎么分工
- **入口文件（CLAUDE.md / AGENTS.md / Rules）**：放项目特定约定和始终适用的规则，常驻加载。可复用的方法论不该塞进这里。
- **Skill**：放可复用、按需触发的工作方法。
- **Hook**：放必须每次执行的检查和拦截。
- **Plugin**：把 Skill、Hook、MCP 配置打包，在团队或组织内分发，避免好的配置只停留在少数人的「部落知识」里。
- 一条健康的演化路径：一段内容先以 Skill 形式存在，发现被多个 Skill 共用、而且几乎每次都需要时，再提升为常驻规则。

### 装在哪里
以 Codex 为例，官方会扫描的位置是：仓库级 `.agents/skills`、用户级 `$HOME/.agents/skills`、管理员级 `/etc/codex/skills`，以及随工具打包的系统 Skill，支持符号链接。`~/.codex/skills` 不在官方列表里，即使某些环境能用，也应视为实现细节。团队共享时统一用 `$HOME/.agents/skills`，并在安装说明里区分「官方承诺目录」和「当前环境可用路径」。

### 常见形态
- **纪律型**：强制一套工作纪律，例如先写失败测试再实现。
- **方法型**：有明确步骤的做法，例如从需求澄清到规格、到任务拆分。
- **行为准则型**：不教模型「怎么写得更好」，而是让它少犯工程性错误，例如先想清楚再动手、只做必要改动。
- **领域产出型**：生成技术图、可编辑 PPT 这类具体产物。
- **知识型**：给 Agent 提供代码推不出来的领域知识。

## 边界与误区
- **误区：Skill 越多越好。** 每个 Skill 的描述都常驻上下文，数量膨胀会稀释触发准确率，还会出现内容重叠。挑着装、定期清理比堆数量更有效。
- **误区：写了 Skill 就一定会被执行。** Skill 靠模型判断是否触发，存在「该触发没触发」和「不该触发乱触发」两种失败。关键约束不能只写在 Skill 里。
- **误区：把可复用知识全塞进入口文件。** 入口文件常驻加载，越长越稀释；按需的方法应该拆成 Skill。
- **Skill 会过时。** 为弥补旧模型短板写的 Skill，在模型进步后可能变成负担，需要定期审查和删减。
- **边界**：Skill 解决的是「怎么做」的沉淀，不替代工具本身；需要调用外部系统时，Skill 背后通常还是一个设计良好的 CLI 或 MCP 工具。
