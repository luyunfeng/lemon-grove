# 模型评测

> 模型评测回答「这个模型在我关心的事情上到底好不好」。它大致分三层：**Arena**（匿名盲测 + 人类投票 + Elo 积分）衡量真实使用体感；**传统基准**（MMLU、SWE-bench 等）衡量可复现的能力切片；**自有评测**衡量模型在你的任务里是否真的减少返工。三层各有盲区，读一次模型发布或做一次选型，都要三层一起看，任何单个数字都不宜单独当结论。

## 要点
- **Arena 测的是「体感」**：用户现场出题，两个匿名模型同时作答，投票后才揭晓身份，按 Elo 积分排名（赢了加分、输了扣分，和棋类排位一样）。题目是实时出的，模型没法背题，所以最难作弊。代价是主观性强，对推理慢的模型不友好。
- **传统基准的问题是饱和与刷题**：固定题库客观、可复现，但容易被针对性优化，「高分不等于好用」；头部模型在主流基准上挤在高位，一两个百分点的差距更像噪声。
- **分数只有在同口径下才可比**：同一个基准，用不同的 Agent 框架（harness）跑出来的分数不能直接横比；基准本身的评测方法更新后，旧分数也会被重算。
- **基准之外的行为变化往往更重要**：是否愿意标注不确定性、工具调用和编排能力、推理强度可调档位、价格，这些常常比榜单名次更影响实际体验。
- **最终要落到自己的任务上**：公开榜单用来缩小候选范围，再用自己的任务集做带盲评的对照。

## 怎么做 / 为什么

### 1. Arena
- **为什么流行**：公信力强（匿名盲测 + 大规模投票，最难作弊）；行业共识（厂商发布新模型常引用 Arena 排名）；用户导向（排名高意味着用户觉得好用）；动态竞争（排名实时变化）。
- **主要平台**：LMSYS Chatbot Arena（全球影响力最大，英语为主）；SuperCLUE 琅琊榜（中文语境，有性价比四象限图）；OpenCompass CompassArena（联网与非联网分开排名）。
- **盲区**：模型要主动提交 API 才会被收录；投票用户以海外英语用户为主，中文场景样本偏少。所以一个模型「榜上没有」往往是选择不上（更看重业务指标、面向的市场不同），不等于能力弱。

### 2. 传统基准速查
| 基准 | 侧重 | 局限 |
|---|---|---|
| Chatbot Arena | 真实好用程度（盲测 + Elo） | 主观性较强 |
| SWE-bench | 软件工程实战，解决真实 GitHub Issue | 难度大、运行成本高 |
| MMLU | 57 个学科的通识选择题 | 容易被刷题，高分不等于好用 |
| MATH / GSM8K | 数学与逻辑推理 | 强逻辑不等于强应用 |
| HF Open LLM Leaderboard | 开源模型生态 | 不收录闭源模型 |
| OpenCompass | 几十个数据集的综合评测 | 维度庞大，要注意权重 |

### 3. 怎么读懂一次模型发布
1. **先看口径**：每个分数用的是什么 harness、什么版本的基准、和谁在什么条件下对比。跨框架、跨评测版本的分数不能横比。
2. **看基准之外的行为变化**：诚实性（是否主动暴露不确定、是否减少无根据的断言）、推理强度档位、长任务编排、API 能力、价格与速度档位。
3. **看它押注哪条能力线**：工具使用与 Coding、纯推理、多模态……同一代模型的差异更多来自优化方向，而不是谁高一两分。
4. **分清发布版与内部最强版**：经过安全对齐和能力裁剪后公开的版本，能力不等于实验室内部最强模型；评测对象要写清楚具体版本。
5. **只有发布信息、没有基准数据的消息**，只能当作定位线索，要靠自己的评测验证。

### 4. 自有评测
- **对照设计**：至少五个不同类型的任务（小 bugfix、文档更新、构建失败、API 用法查询、代码审查），对比「裸跑 / 加规则 / 加规则和 Skill」三档，看首轮通过率和返工次数。目标是判断配置是否真的减少返工，而不是看配置了多少东西。
- **方法论的坑**：同一个任务连跑三遍，模型已经受缓存和上下文偏差影响，结果可能只反映任务难度。更稳的做法是每档用不同任务、引入不告知档位的盲评，主观体感只作辅助信号。盲评就是把 Arena 的思路搬到个人评测上。
- **三类评分器**：代码评分器快、便宜、客观，但脆弱；模型评分器灵活，但不确定且贵；人工评分器最可靠，但慢且贵。能用代码判的先用代码判。
- **消融比堆上下文更能说明问题**：在一个数据分析 Agent 上，没有 Skill 时准确率不超过 21%，加上 Skill 后持续高于 95%；而给 Agent 检索数千个历史文件，准确率提升不到 1 个百分点。瓶颈在结构，不在上下文数量。

### 5. 上线后的评测
- 离线评估应接近 100%，上线后通常会降到约 95%；数据陈旧会让准确率在一个月内从约 95% 漂移到约 65%。
- 按领域设发布门槛（约 90%），评测结果像遥测数据一样持续存储和监控。
- 对抗性审查能让准确率再提升约 6%，代价是 token 增加约 32%、延迟增加约 72%，要按场景权衡。
- 最难的是「静默失败」：答案错了，但看起来很合理。

## 边界与误区
- **误区：Arena 第一就最适合我。** Arena 偏向英语通用对话；Coding Agent 场景要结合 SWE-bench 类基准和自己的任务测。
- **误区：基准高一两分就是更强。** 头部之间的这种差距更像噪声，跨 harness 的分数更是不可比。
- **误区：离线评测过了就行。** 线上会衰减，还有静默失败，需要持续监控。
- **误区：热度等于质量。** 项目的 Star 数不等于实际使用量，更不等于在你的任务上有效。
- **误区：模型自报的置信度可以跨模型比较。** 不同模型的置信度尺度不可直接比较，只能在同一模型内部做相对比较。
- **边界**：评测本身也是一个验证问题。Arena 用大规模人类偏好换「难以作弊」，基准用固定答案换「可复现」，自有评测用业务真值换「与场景相关」，三者互补而不能互相替代。
