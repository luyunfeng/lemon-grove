# Loop Engineering（循环工程）

> 不再亲手一轮轮地提示编码 Agent，而是设计一个能自动**触发 → 生成提示 → 运行 Agent → 验证结果 → 记录状态**的外层循环，让系统替你持续驱动 Agent。它解决的是人成为吞吐瓶颈的问题：人不再盯着每一轮对话，而是设计循环本身。

## 要点
- **两层循环**：内层是所有 Agent 都有的 Agent Loop（感知 → 推理 → 行动 → 观察，即 ReAct 模式）；外层才是循环工程：触发条件（定时 / 事件）→ 提示生成 → 内层 Agent Loop → 评估器 → 记忆。
- **核心转变**：从「写一个好提示」变成「设计一个能持续生成好提示的系统」。
- **本质是把反馈回路产品化**：它是 Harness Engineering（驾驭工程）里「执行器 + 反馈回路」落到日常工具上的形态。循环的上限，由「完成」的定义和验证质量决定。
- **风险与收益同速放大**：无人值守的循环，也在无人值守地犯错，必须配硬护栏。

## 六个要素
| 要素 | 作用 |
|---|---|
| 自动触发（Automations） | 定时或事件触发，自动发现和分类任务，例如 cron |
| 工作树隔离（Worktrees） | 每个并行 Agent 一个独立工作目录，避免文件冲突 |
| Skills | 把项目知识固化成跨会话可复用的指令 |
| 插件（Plugins） | 通过 MCP 连接工单、数据库、错误监控等外部系统 |
| 子 Agent | 分离实现者（maker）与检查者（checker） |
| 记忆（Memory） | 对话记录之外的持久状态 |

这六个要素可以归成三类基础模式：**工作流自动化**（计划 → 执行 → 测试 → 改进，直到目标完成）、**文件系统即记忆**、**子 Agent 与后台任务**。

## 三种驱动方式
| 驱动方式 | 怎么停 | 适合 | 典型限制 |
|---|---|---|---|
| 目标驱动 | 每轮结束后由评估器判断完成条件是否满足 | 有明确终态的任务：修 bug 到测试全过、覆盖率达标 | 条件必须可验证；评估器看不到的东西不能当条件 |
| 时间驱动 | 按间隔反复触发，手动停止或判断工作完成 | 反复执行的任务：轮询 CI、检查 PR 新评论 | 会话级调度通常只在会话运行且空闲时触发，错过不补，任务有过期时间和数量上限 |
| 脚本驱动 | 编排脚本跑完所有子任务 | 能拆成大量独立子任务的工作 | 并发数和总数有上限；运行中一般不接受用户输入 |

常见的组合是「目标定义完成标准 + 定时循环持续推进，直到达标」。脚本驱动的好处是把编排逻辑代码化：中间结果留在脚本变量里，不占主上下文，还能保存成可复用的命令。目标驱动和计划驱动的取舍，见目标驱动与计划驱动（Goal vs Plan）。

## 谁来判定「完成」
| 做法 | 机制 | 适用 |
|---|---|---|
| 独立评估器 | 另一个（通常更轻量的）模型只看完成条件和对话记录，返回是 / 否和理由；否则把理由带进下一轮 | 需要语义判断时更可靠，也更可控 |
| 模型自判 | 执行模型自己决定何时完成，循环本身保持无状态、自动压缩上下文 | 完成条件能被测试、lint 等确定性信号覆盖时，问题不大 |

这是驾驭工程两条路线（确定性约束 vs 生成与评估分离）在循环层的延续。默认用独立评估器更稳妥；如果完成条件本身就是「某条命令输出 0 个失败」，确定性信号已经足够。

## 怎么做
1. **先写完成条件，再开循环**：条件要可验证、对评估者可见，例如「运行 `npm test -- --coverage`，输出的覆盖率一行显示 ≥ 80%」。条件怎么写，见 Verification（验证）。
2. **maker 与 checker 分离**：实现和检查交给不同的子 Agent 或独立评估器。
3. **状态落盘**：「记录状态」是外层循环的固定一步；子 Agent 和后台任务的输出要写进文件和日志，才可检查，中断后也可恢复。
4. **配硬护栏**：
   - 迭代上限（最多 N 轮）；
   - token 或金额预算；
   - 无进展检测（连续 N 轮无变化就停）；
   - 熔断（错误率超过阈值就停）。
5. **权限自动分级**：用分类器对每个工具调用做风险评估，安全操作自动放行，风险操作被拦截——这是让循环能无人值守的前提。
6. **人审证据，不审补丁**：设自动接受标准，只有关键区域提交人工。
7. **给低置信留出口**：让循环在不确定时停下来求助，而不是继续跑，见提示词中的置信度。

## 边界与误区
- **误区：循环能替代验收**。循环跑得越快，模糊的完成条件只会让它越快收敛到错误答案。「完成」的验证最终仍需要人负责。
- **理解债务**：循环产出你没有亲手写的代码越快，你对系统的理解差距就越大。
- **认知投降**：不加判断地接受循环返回的一切。
- **并行 ≠ 有效**：大规模并行的子 Agent 之间的冲突、错误恢复和成本仍然难以预估。
- **没有护栏的自主循环**：无约束的自主 Agent 容易陷入无限循环、烧掉大量 API 费用，这正是迭代上限和预算护栏存在的理由。
- **目标模式里的「循环」不等于定时循环命令**：前者是内置的「做 → 验 → 修 → 验」自验证机制，后者是按时间触发的调度器，两者可以组合但不是一回事。
