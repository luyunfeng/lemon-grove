# Harness Engineering（驾驭工程）

> 把大模型当成一个会漂移、会犯错、会高估自己的概率系统，不指望它一次答对，而是用上下文供给、规则约束、工具执行、状态管理和反馈回路组成外部控制系统，让整套系统在长时间运行中持续逼近正确结果。常见的写法是 `Agent = Model + Harness`。

## 要点
- **换一个问法**：AI 写代码可不可靠，关键不只在模型，而在有没有足够强的「验证 → 反馈 → 修复」闭环。注意力从「怎么驱动模型」转向「怎么设计模型工作的环境」。
- **三层逐层外扩，不是替代**：提示词工程管「该怎么问」，Context Engineering（上下文工程）管「模型该知道什么」，驾驭工程管「模型做偏之后，系统怎样把它拉回来」。
- **本质是把开环改成闭环**：稳定性来自反馈，而不是前馈。
- **杠杆在模型外面**：提升 LLM 系统稳定性和可靠性，真正的杠杆不只在模型本身，而在包裹模型的控制架构。harness 往往比换模型更能决定表现。
- **harness 是临时的**：它的每一个组件，都编码了一个关于「模型当前局限」的假设。模型进步后，要回头删减。

## 为什么：概率系统需要闭环
传统软件默认输入到输出是确定映射；LLM 是在概率分布上采样。放任它运行，就像在语义空间里做有偏的随机漫步：每一步都「差不多合理」，但小偏差会成为下一步的上下文，在多步链条里逐渐放大。编码 Agent 里尤其明显——模型会复制仓库里已有的次优模式，长期看等于吸收并强化已有缺陷。

输入端优化（改提示词、改检索）只能提升单步质量，挡不住长期运行中的漂移和误差累积；靠人兜底也扩展不了——人力不是一个适合 7×24 小时持续吸收系统熵增的控制部件。结论是：被控对象本身不可信，稳定性必须主要来自外部闭环。

## 五个部件
| 部件 | 在 Agent 系统里对应什么 | 要点 |
|---|---|---|
| 被控对象 | LLM 驱动的执行过程 | 会漂移，还会自我欺骗：对平庸产出也打高分 |
| 传感器 | 测试结果、运行日志、工具返回值、监控指标、UI 截图 / DOM | 传感器的精度决定控制的精度 |
| 控制器 | 仓库里的规则、linter、架构约束，或独立的评估 Agent | 好的 linter 报错同时给出「哪里错 + 怎么改」，而且是确定性的 |
| 执行器 | 改代码、跑命令、提交 PR、回应 review、修 CI | 价值在于持续尝试直到满足约束 |
| 反馈回路 | 输出再回到传感器，被观测、比较、修正 | 让系统越跑越稳的核心 |

落地顺序可以用误差式 `e = r(t) - y(t)` 概括：先定义「什么叫正确」（目标值 r），再持续观测「现在离正确还有多远」（实际值 y），然后用工具、验证、回退、修复把偏差压回去。

**传感器是最容易被低估的部分**。例如给每个独立工作区配临时的日志、指标、trace，让「服务 800ms 内启动完成」「关键链路没有超过 2 秒的 span」这类要求变成 Agent 能直接读取的测量信号；接入浏览器让 UI 变得可观测；跟踪质量趋势而不只看单次成败。这也解释了为什么 Agent 在代码领域表现最强：代码可运行、结果可观测、观测能快速回流，天然适合闭环。

## 两种控制路线
| 维度 | 多层级联 | 生成与评估对抗分离 |
|---|---|---|
| 对被控对象的假设 | 会漂移，但能用确定性约束拉回 | 会漂移，而且会掩盖偏差，必须外部独立评估 |
| 架构 | 多层嵌套的反馈回路 | Planner – Generator – Evaluator 三方分离 |
| 反馈信号 | 测试、linter、运行态信号，外加修正建议 | 独立 Agent 给出的语义级差距描述 |
| 擅长 | 能形式化测量的偏差：测试、架构规则、性能 | 难以用单一指标定义的质量：设计感、交互顺手度 |

对抗分离的关键是把传感器从被控对象里解耦。生成者和评估者如果是同一个推理过程，评估者就是在生成者留下的语境里思考，天然倾向于高估质量；独立评估者不看生成过程，只看产出和预先定义的验收标准，循环一直运行到所有子任务通过评估，或达到最大迭代次数。

两条路线不冲突：成熟系统可以同时用两类控制器——能形式化的约束交给确定性工具，需要语义判断的质量问题再花一个独立评估者。这个「生成与评估分离」的思想反复出现在各种产品里，比如目标驱动循环的独立评估器、「先查规格合规、再查代码质量」的两阶段审查。

## 怎么做
1. **先建传感器，再谈自治**：最值得先建设的是验收标准、自动化测试和可观测性。没有传感器的控制器是盲的。
2. **把资深工程师的判断写进仓库**：带修复建议的 linter、架构依赖方向规则（如 `Types -> Config -> Repo -> Service -> Runtime/UI`）是确定性控制器，同样的违规永远触发同样的修正。约束怎么按强制力度分层，见约束的强制分层（Rule Enforcement Layers）。
3. **生成与评估分离**：需要语义判断的质量问题，用有独立上下文、独立验收锚点的评估者，而不是让模型自评，见 Verification（验证）。
4. **状态外部化**：跨会话工作时，控制系统的状态必须外部化、持久化、增量化；子 Agent 的输出要落到文件和日志里才可检查。
5. **随模型进步做减法**：找到最简的方案，只在需要时增加复杂度。给每个组件标注它在补偿哪条模型局限，定期（例如每 3–6 个月）审查一次：「每次重构只改一个文件」这类规则会限制新模型；为强制某个版本控制操作而写的拦截钩子，在工具原生支持后就成了冗余。
6. **判断成熟度的三个问题**：是否把失败变成可检索的证据；是否把每次改动变成可证伪的假设；是否把验证器、权限和人工审查放在自我演化循环之外。缺任何一个，系统都容易从自我改进滑向自我确认。

**规模的层次**：一个 harness 驱动一个 Agent 循环；当团队同时使用多种编码工具时，还需要一层「元 harness」治理多个 harness——运行时层不断变化，持久的价值在行为层（规则、Skill、记忆、评测、证据链）。编码 Agent 的 harness 形态已经趋于稳定：文件系统、Shell、git / LSP、MCP / Skill、后台任务、子 Agent 委派，外加循环、评测、权限控制和持久状态，整体更像一个操作系统而不是一段提示词。

## 边界与误区
- **误区：harness 就是更长的 system prompt**。它包括循环、评测、权限、记忆、子 Agent 管理和人工接管策略。
- **误区：有了 harness，上下文工程就过时了**。驾驭工程是上下文工程的上位框架，不是替代品。
- **误区：只要有流程就可靠**。只强调流程约束、不解决反馈闭环，AI 可能只是「按流程稳定地产出错误」；只强调执行自治、不提供可验证的环境，效率再高也转化不成可靠交付。约束、自治、验证三者缺一不可。
- **误区：人从循环里消失**。人的位置是上移：从 in the loop 到 on the loop，负责设计约束、信号、自动修正规则和介入节点。
- **harness 会变，但不会消失**。模型变强后，整体层次会变少，但单层的工作更复杂：重心转向权限与策略的精细管理，可观测性更加核心。harness 本身也在变成优化对象：优化目标从提示词、结构化上下文、工作流，逐级上移到 harness 代码乃至优化器代码。
