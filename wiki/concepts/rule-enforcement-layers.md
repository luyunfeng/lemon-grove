# 约束的强制分层（Rule Enforcement Layers）

> 给 Agent 的约束按强制力度分三层：**建议**（入口文件、Rules）、**流程**（Skill）、**硬拦截**（Hook）。它解决的问题是：该写在哪一层。原则是能交给确定性检查的，就不要指望模型「记住」。

## 要点
- **三层强制力度不同**：

| 层 | 载体 | 怎么生效 | 可靠性 | 适合 |
|---|---|---|---|---|
| 1. 建议 | CLAUDE.md / AGENTS.md、Rules | 每次会话自动加载进上下文，靠模型遵循 | 取决于写得好不好，模型可能忽略 | 编码风格、项目约定、始终适用的行为准则 |
| 2. 流程 | Skill | 相关任务时按需加载，用步骤、检查清单、反驳表引导 | 靠模型自己挑选触发，触发率大约 50%–80% | TDD、调试流程、代码审查这类「按场景判断」的流程 |
| 3. 硬拦截 | Hook | 在生命周期事件上运行脚本，可以放行、拒绝或修改操作 | 100% 触发，不依赖模型听不听话 | 安全策略、必须运行的检查、格式化 |

- **入口文件是建议，不是配置**。写进 CLAUDE.md 的内容是建议性上下文，模型会遵循多少取决于写法和上下文压力。
- **「必然发生」用 Hook，「按场景判断」用 Skill**。需要每次都发生的事（密钥检测、格式化、危险命令拦截），交给 Hook；需要模型结合情境决定怎么做的，写成 Skill。
- **确定性规则比记忆可靠**：lint、format 这类规则交给 Hook 自动执行，比在提示里要求模型「记得格式化」可靠得多。
- **把准入门槛焊在工具调用上**：能用 Hook 拦的，就别靠模型自觉。Agent 定义里的工具白名单（例如规划角色只有读、搜索类工具）也是同一类物理护栏，能防提示注入。

## 怎么做
**1. 按问题选层**

| 你要的效果 | 放在哪一层 |
|---|---|
| 让模型知道项目约定、关键陷阱、目录指针 | 入口文件（根目录只放全局，子目录放本地约定） |
| 跨任务、跨场景始终适用的硬规则（如不打印密钥、默认用中文回复） | Rules，始终加载 |
| 某类任务的专业流程和判断 | Skill，按需加载 |
| 绝不能跳过的检查、绝不能执行的操作 | Hook，阻断式 |

**2. 让流程层更「硬」一点**
Skill 的弱点是模型会「合理化」绕过：它不是不知道规则，而是会找理由说服自己这次可以例外。补法是：
- **合理化反驳表**：预先列出可能的借口和对应的反驳；
- **红旗列表**：让 Agent 自检「我是不是在找理由」；
- **基础原则声明**：「违反字面就是违反精神」，一句话切断一整类论证。
写法细节见 Agent Skill 设计。

**3. Hook 从轻到重地加**
Hook 有副作用，还能阻断操作，引入顺序宜由轻到重：
1. 提示型：会话结束、上下文压缩前提醒或保存状态；
2. 检查型：工具调用后自动格式化、跑检查、提示下一步；
3. 阻断型：工具调用前拦截高风险命令。

Hook 不只用来拦错事。会话结束时的 Hook 可以趁上下文还新鲜，反思这次会话并提出入口文件的更新建议；会话开始时的 Hook 可以按团队或模块动态加载上下文。

**4. 让内容在层之间迁移**
同一份内容可以在不同层之间升降：
- 一套编码行为准则（先想后写、不擅自补假设；简单优先；只改被要求的部分；先定义验证方式再动手）可以同时做成入口文件条目、编辑器规则和 Skill：常驻就是 Rule，按需就是 Skill。
- 健康的演化路径是「先以 Skill 形式进库，被多个 Skill 共用后再蒸馏成 Rule」；反复出现、必须百分之百执行的，再升级成 Hook。
- 反过来，项目特定的约定放入口文件，不要做成 Skill；跨项目可复用的专业知识做成 Skill，不要全塞进入口文件。

## 为什么
- 模型的遵循是概率性的，越往后的上下文、越复杂的任务，建议类约束越容易被忽略；强制力度应该和违规代价匹配。
- 三层的上下文成本也不同：入口文件每次都占上下文，Skill 用到才加载，Hook 在模型之外运行、几乎不占上下文。把规则放对层，同时也是在做 Context Engineering（上下文工程）。

## 边界与误区
- **误区：Hook 万能**。Hook 只能拦截它能看到的事件和能写成规则的条件；Hook 之外的行为仍然靠模型自觉。安全声明再强，也要清楚它止步于哪里。
- **误区：所有规则都塞进入口文件**。入口文件越长，关键规则越容易被淹没，也越占上下文。入口文件要小，只放指针和陷阱。
- **误区：只写规则就够了**。流程层真正起作用的是堵住合理化路径，而不是写更多规则；而且反驳表依赖对 Agent 行为的准确预测，遇到新借口就要继续补，需要持续迭代。
- **约束会过时**：为补偿旧模型局限写的规则和 Hook，在局限消除后会变成负担，甚至限制新模型的能力。定期审查，删掉不再承重的约束。
- **不同工具的 Hook 能力不同**：有的工具用退出码表示阻断（例如退出码 2 阻止操作），有的用结构化的请求 → 结果模式；事件种类和数量也不一样。规则思想可以跨工具共享，Hook 实现属于适配层。
