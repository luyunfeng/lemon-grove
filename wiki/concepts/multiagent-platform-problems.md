# 多 Agent 规模化的平台工程问题

**一句话**：把多 Agent 系统从演示推向规模化，靠的不是更强的模型，而是四类平台级工程——基础设施、身份与授权、安全与隔离、监控与熔断。这些是子 Agent 编排层之下的另一层问题，也是模型能力兑现的前提。

## 要点

### 基础设施要为 Agent 负载重造
- 现有云基础设施为无状态、可复制或固定副本集的应用设计，Kubernetes 是典型；Agent 是隔离的、有状态的、单实例工作负载，大量时间花在等待工具、推理、其他 Agent 或人的输入上，可以任意时长 idle。
- 不同负载的诉求互相冲突：有的要快启动，有的要省算力，有的要极端规模。新的文件系统、沙箱产品和专用运行时（如 Google 在建的 Agent Substrate）都是对这个空白的回应，离收敛还很远。

### 身份与授权
- 认证相对成熟：识别「哪个 Agent 干了这件事」可以复用微服务时代的资产——用短期证书的工作负载身份替代静态密钥。
- 授权远未解决。多数 Agent 以人的身份和凭据代行（OBO，on-behalf-of）：首先要能区分动作是 Agent 还是本人做的；更深的难题是同意——系统连续运行数周时，人怎么有效审批 Agent 的行为。自动批准工具调用只是浅层，高规模需要更细的权限模型。
- Agent 用自有身份行动、以及 Agent 之间怎么互信（凭什么信任另一个 Agent 发来的请求），比 OBO 更不成熟。

### 安全与隔离
- 不可信组合被放大：核心软件漏洞的暴露速度快于修补速度，而规模化多 Agent 系统让成千上万个 Agent 在这些组件上写不可信代码、读不可信内容。加固内核、浏览器、运行时和通用库是这个领域最值得投入的工程。
- 多 Agent 引入新攻击面：一个被攻破的 Agent 可以向协作者注入指令，指令还可能写进记忆被后续 Agent 误信。爆炸半径成为实际问题：第一个 Agent 失陷时，整个系统有多大范围暴露？
- 对策是强隔离：Agent 的动作放进强隔离的沙箱执行环境。

### 监控与熔断
- 需要跨 Agent 的分布式追踪（如 OTel），且保证 Agent 不能修改自己或其他 Agent 的 trace。
- 监控要能触发真正的熔断：一键停掉整个系统并吊销其全部凭据。
- 最难的判断是「跑偏」：善意的坚持和恶意行为看起来很像——反复尝试访问不在白名单内的域名，可能是不死心的重试，也可能是攻击。

## 为什么
模型会持续变强，但这些平台问题不解决，多 Agent 系统的威力就解锁不了，世界也不敢把它交给关键事务。问题空间大多空白，是工程师角色上移后的新主场：从写代码转向建环境、立规矩。

## 边界与误区
- 编排层的问题（怎么拆、怎么通信、怎么汇总）替代不了这一层：任务拆得再好，没有身份、隔离和熔断，规模化即失控。
- 基础设施层不会被「更好的模型」跳过：有状态、单实例、长 idle 是 Agent 负载的结构性特征，与模型能力无关。
