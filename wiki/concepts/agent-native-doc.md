# Agent 原生文档（Agent-Native-Doc）

**一句话**：写给 Agent 读的仓内领域知识系统。它只收录**代码里看不出来、但会影响改代码决策**的知识，以仓库为唯一权威依据（source of truth），由一个 Skill 负责冷启动和持续维护。它解决的问题是：Agent 缺的不是更多上下文，而是**更可信的上下文**。

## 要点
- **存什么**：一段文档如果随时能从代码重新生成，就不值得长期保存。
  - 代码里看得到的（不存）：函数、类型、目录结构、单仓内的调用关系、具体算法；
  - 代码外才知道的（要存）：跨仓库 / 跨团队的契约（接口定义、无 schema 的 JSON、三方库字段含义）、历史评审和事故复盘沉淀的决策、哪些验证方式才算有效（本地脚本、集成测试、数据监控）。
- **存在哪**：git 仓库是编码场景里最适合 Agent 的存储介质——可分发、多版本、跟着代码走。外部文档、聊天记录、工单系统「太多太散、太旧、权限不一定通」，不该当默认入口；要先蒸馏进仓库：事实指回它最初所在的位置，仓内只存经过判断的结论。
- **结构比数量重要**（「数据不是软件」）：给 Agent 原始检索访问数千条历史查询，准确率提升不到 1 个百分点。瓶颈不在能访问多少历史工作，而在结构。
- **领域定义要人把关**：用 LLM 自动生成指标定义是净负面的；知识要经 owner 确认才能入库。
- **维护比冷启动更重要**：知识过时后，Agent 开始给出「看起来合理但悄悄错了」的答案，准确率可以在一个月内从约 95% 漂到约 65%。

## 怎么做

### 三件事：捞知识、统一语言、维护闭环
**1. 捞知识**：三个渠道，各有短板，要互相校验。
| 渠道 | 做什么 | 问题 | 处理 |
|---|---|---|---|
| 搜内部文档 | 找事故纪要、设计文档、讨论记录，蒸馏进主题文档 | 老文档有信息但不一定对 | 结合合并请求证据和 owner 访谈校验，不把外部文档当最终答案 |
| 挖合并请求和 git log | 扫热点代码、反复修改的位置、注释和提交信息 | 只看得到「改了什么」，看不到「为什么」 | 把候选事实变成具体问题交给 owner 确认 |
| 冷启动访谈 | 和 owner 多轮确认真正的知识 | 成本高，问题太宽就没有信息增量 | 问题必须落在证据上，给 owner 可确认的具体假设 |

**2. 统一语言**：把仓库特有的名词、动词、实体关系和易混淆概念写进 `docs/CONTEXT.md`，减少人和模型之间的语义偏差。每条按「定义 + 不要混用 + 证据」记录；timeout、handler、error 这类通用概念不收，只收在本仓库语境下才有精确定义的词。需求澄清阶段的拷问式对话本身就会产出这份词表和 ADR。

**3. 维护闭环**：分三种路由，避免「记一句话」被升级成全量重审。
| 路由 | 触发 | 改动范围 |
|---|---|---|
| 冷启动 | 第一次给仓库建 Agent 文档 | 产出骨架，初始化整体文档 |
| 主动维护 | 用户说「文档错了 / 旧了 / 乱了」，或再次运行 | 大范围增量编辑，重新走搜索蒸馏 |
| 被动维护 | 对话里出现「记下这个 / 把结论固化进文档」 | 小范围增量，只动少量主题文档 |

### 仓库里的样子
```
AGENTS.md                 # Agent 入口与仓库级约定
docs/CONTEXT.md           # 领域词表 / 统一语言
docs/agent-native/        # 主题文档、maintenance-guide.md 等
```
主题文档里的操作规则按「已确认结论 + 依据 + 约束」来写。

### 同一张结构在别的场景也成立
- **数据分析**：数据分析通常只有一个正确答案、一个正确数据源，模型的创造力在这里是伤害。关键是让 Agent 把问题映射到数据模型里的具体实体。可信源按信任度排序：语义层（指标定义、维度映射、聚合规则）→ 血缘与转换图谱 → 历史查询语料 → 业务上下文。Skill 和数据模型放在同一仓库维护，约 90% 的数据模型变更同时改了 Skill；答案后附溯源页脚，标明数据层级、新鲜度和负责人。没有 Skill 时准确率不超过 21%，加上后稳定高于 95%。
- **大型代码库**：入口文件分层，根文件给全局视角，子目录文件给本地约定，只放广泛适用的内容；可复用的专业知识放进按需加载的 Skill；会话结束时由 Stop hook 提出入口文件的更新建议。
- **长程 Agent**：把文件系统当记忆，实验日志、diff、错误轨迹写进文件、按需读取，而不是塞在对话里。

四个场景给出的是同一张结构：**少量可信的权威源 + 分层按需加载 + 和代码同仓维护 + 人确认领域定义**。

### 克制是核心设计
最高回报的事，不是一上来搭知识图谱，而是先建一个最基础、能渐进式加载、有明确维护规则的文档系统。明确不做：定时维护、历史提交重放、接项目管理系统、图存储、多路检索。「内部文档 + 代码作为唯一权威依据」已能覆盖九成以上问题。

和其他 Skill 集成要**高内聚、低耦合**：在 `AGENTS.md` 里约定，思考、脑暴、方案评审、风险质询类 Skill 先读 `docs/CONTEXT.md` 和 `docs/agent-native/`；这个 Skill 自身保持自包含，不做「超级 Skill」，不和其他 Skill 产生重依赖。

### 怎么迭代这个 Skill
文档类 Skill 往往没有标准答案，好不好很大程度靠人判断。轻量的做法：先快速做出能跑的版本 → 用四五个基础用例抓明显问题 → 把生成的文档交给真实同事、真实仓库、真实任务检验。评测环境要隔离记忆，并在多种模型和 harness 上都测一遍。

## 边界与误区
- **误区：做一个「总结代码」的 AI 文档**。能从代码生成的东西存下来只是冗余副本，还会过时。
- **误区：多给原始材料就会更准**。数千条历史查询的消融实验否定了这一点。
- **结构对 ≠ 内容对**：基础规则评测全过、内容却完全不对的情况会发生；要用「隐藏知识」「不干扰」这类评分标准才能证明内容真的有用。
- **静默失败没有解决**：答案错了但看起来合理，用户可能永远发现不了。
- **模型抗噪变强后仍有价值**：仓内文档是团队把判断显化的地方——哪些结论已确认、哪些取舍已达成共识，能和代码一起 review、diff、回滚。
- **开放问题**：被动维护的触发准确率如何，会不会漏掉该记的时刻？「通用概念」和「仓库特有概念」的边界怎么定？owner 访谈的蒸馏结果怎样避免变成个人偏见？
