# Agent 工具接口（CLI 优先，MCP 作薄适配层）

**一句话**：Agent 最好用的工具接口，往往不是新的协议层，而是设计良好的命令行工具——非交互、结构化输出、幂等、输出有界、能自我描述。MCP 更适合看作 CLI 之上的薄适配层（thin adapter）；而 CLI 好不好用，一半取决于它背后的服务端接口是否也按 Agent 的需要设计。

## 要点
- **为什么是 CLI**：
  - 接入成本极低，现有工程能力天然能接；
  - 训练语料丰富，模型熟悉命令式交互；
  - 管道和脚本天然可组合；
  - 人和模型执行同一条命令，调试透明、结果容易对齐；
  - 适合渐进式披露，只返回当前步骤需要的信息。
- **Agent DX ≠ Human DX**：给人用的工具追求「好发现」，给 Agent 用的工具追求「可预测」。Agent 需要四样东西：不读文档也知道有什么命令（可发现）、不用正则硬抠（可解析）、同样输入永远同样格式（可预测）、输出量可控不撑爆上下文（有界）。
- **最重要的单一特征是 `--json`**，其次是一致的「名词 + 动词」命令结构、默认非交互（或提供 `--yes`）、清晰的结构化错误。
- **能力拆不成小命令，模型也用不稳**：一个能力如果不能自然地拆成清晰的小命令，通常也不容易被模型稳定使用。复杂的单体工具更适合拆成一组 CLI，再由 Agent Skill 编排。
- **要的是更好用的工具，不是更多工具**。

## 怎么做

### 好 CLI 的设计规范
| 规范 | 要点 |
|---|---|
| 层级子命令 | `tool resource verb [flags] [args]`，资源在前、操作在后；`--output`、`--format` 这类全局 flag 跨子命令统一；每个命令只做一件事 |
| 六条基本原则 | 结构化输出（管道时 JSON、终端时给人看）；`schema` 命令自省；数据走 stdout、诊断走 stderr；默认非交互；幂等；有界输出（`--limit`、`--offset`、`--fields`）。Agent 永远不该需要去解析 `--help` 文本 |
| 更激进的 Agent 优先原则 | Token 高效格式（比 JSON 省约 40% token）、列表默认只给 3–4 个字段、大字段截断并给出长度提示、预先算好聚合值、空结果明确输出「0 results」、结构化错误加 exit code、自动注入环境上下文、无参数运行时显示实际内容而不是 help、输出后附下一步可用命令的模板、每个子命令都有简洁的 help |
| AI 友好光谱 | 敌对（交互式，如 vim）→ 兼容（Unix 风格，如 grep / git）→ 友好（加了 `--json`，如 gh / terraform）→ 原生（为 Agent 设计） |

按更激进原则做的工具，在 490 次浏览器自动化和 425 次 GitHub API 测试里达到 100% 成功率，每任务成本 $0.074，低于 MCP 的 $0.100 和原始 CLI 的 $0.088。

### 把 CLI 暴露给 Agent 的四种形式
| 形式 | 适用 | 优点 | 代价 |
|---|---|---|---|
| A. 大段文本描述用法 | 命令少于约 20 个、验证期 | 零开发，模型理解无障碍 | 占上下文、容易和代码不同步、每次都要重读、只能全量或不给 |
| B. Schema 自省 | 成熟期 | 从代码生成、始终同步、可按需加载单个命令；首次调用准确率从约 60% 升到约 90%，解析错误从 41% 降到接近 0 | 要额外开发 schema 层 |
| C. MCP 封装 | 跨系统、需要认证 | 结构化输入输出，内置认证与审计日志 | 多一层抽象，加载 schema 有前置 token 成本 |
| D. 渐进式披露 | 通用 | 顶层只露命令分类加一句话，要用时再 `schema <cmd>` 或 `--help` | 半自动维护 |

形式 D 是形式 A 的升级版，思路和 Skill 的三层加载（先名称和描述、匹配后读正文、用到时再加载脚本资源）一致。

**怎么选**：本地开发、快速迭代（inner loop）直接用 CLI——多步调试任务里 token 效率高 33%，任务完成分 77 对 60；跨系统协调、需要集中认证和审计（outer loop）再包一层 MCP；已有 CLI 想快速接入，用「文本清单 + JSON 输出」；新建系统直接做「Schema 自省 + 渐进式披露」。顺序永远是**先有好 CLI，再按需包 MCP**。

### 服务端接口也要为 CLI 设计
当后端的消费者是 CLI（进而是 Agent）而不是 Web 前端时，侧重点不同：CLI 是无状态、一次性执行的客户端，要么快速返回，要么给流式进度，还要能精确判断错误并知道下一步做什么。

| 维度 | 给 Web 前端 | 给 CLI |
|---|---|---|
| 响应结构 | 聚合嵌套，配合页面渲染 | 扁平、单一职责；列表支持 ndjson（每行一个 JSON）方便逐行处理；`?fields=` 只取需要的字段 |
| 长操作 | WebSocket / 轮询 | 返回 `202` 加 `operation_id` 让 CLI 轮询；或 SSE 流式推送进度（对 CLI 更友好，直接逐行输出进度） |
| 错误 | 用户友好的提示文案 | 机器可判断的 `code`（决定退出码或是否自动重试）+ 可执行的 `hint`（直接告诉下一步跑什么命令）+ 精确到字段的校验错误（方便映射回哪个 flag） |
| 认证 | Cookie / OAuth 跳转 | Header 里的长期 token；需要用户授权时用 Device Flow（`tool login` 打开浏览器）；CI 自动化用 mTLS 或 Service Account；不用 Cookie / Session |
| 分页 | offset / page | cursor：增量拉取天然表示「上次读到哪」、不受中途插入删除影响、翻多深性能都恒定、cursor 自带位置所以无状态；代价是不能跳页，CLI 基本不需要 |
| 超时容忍 | 3–5 秒用户就烦 | 可以更长，但必须有流式进度 |
| 幂等 | 一般 | 更高：用户会习惯性按上箭头重试，写操作要支持 `Idempotency-Key`，或设计成 PUT 式声明语义 |
| 版本 | 可以强制升级前端 | 用户不一定升级 CLI，多版本共存时间更长；推荐用 Header 声明版本 |

这张表和 CLI 规范是同一条链路的两端：「有界输出」对应 `?fields=` 和 cursor 分页，「结构化错误」对应 `code` + `hint`，「幂等」对应 `Idempotency-Key`。给 Agent 用的工具，要从服务端就按 Agent DX 设计。

### 分阶段落地
1. **已有系统最小改造**：所有命令加 `--output json`；检测是否在终端，管道时自动去掉颜色；确认操作加 `--yes`；写一份精简命令清单作为 Skill 描述；不同错误用不同 exit code；错误输出为包含 `code` 和 `suggestion` 的 JSON。
2. **中期**：从代码自动生成 `schema` 子命令；支持 `--fields`、`--limit`；输入加固（路径遍历、特殊字符、双重编码——Agent 幻觉出的输入和人犯的错不一样）；支持 `--dry-run`。
3. **长期**：渐进式 schema 披露、从 schema 自动生成 MCP 封装、Token 高效输出格式、自动注入环境上下文、输出后附下一步命令模板。

## 边界与误区
- **「给更多工具」≠「给更好用的工具」**：真正值得投入的是后者。
- **把 `--help` 大段文本当接口**：命令超过约 20 个后上下文压力大，且无法和代码同步，应改成分层披露。
- **基础没打好就建 MCP**：先把 CLI 做好，再按需包 MCP；常驻 MCP 全量启用会让工具列表过长，比模型不够强还伤。用完的 MCP 服务器应关闭。
- **CLI 不是唯一答案**：交互式浏览外部系统、需要鉴权上下文、对象模型复杂时，MCP 更合适。CLI 走红也不只因为省上下文，工程师习惯、可组合、可审计、界面成本低同样重要。
- **成熟工具往往胜过新基础设施**：在代码库里用 grep、遍历文件、跟踪引用做 Agentic Search，比先建 RAG 索引更少出现索引滞后的问题。
