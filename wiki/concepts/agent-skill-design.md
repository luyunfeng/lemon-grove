# Agent Skill 设计

> Agent Skill 设计讲的是怎样把一个 Skill 写成**能被找到、能稳定执行、能被验证、能持续维护**的能力包。核心难点不在把流程写全，而在四件事：写判断而不是写教程；让描述准确触发；堵住 Agent 给自己找理由绕开规则的路；像对待代码一样先测试再上线。

## 要点
- **写判断，不写教程**：写清什么情况走 A、什么情况走 B、什么时候停下、什么时候先补信息；再配上反模式、模板和示例。模型本来就会「怎么做」，缺的是「在这里该怎么选」。
- **能被找到比写得好更难**：描述里要写清何时用、何时不用，用具体症状、报错信息、同义词覆盖关键词，否则 Skill 存在但 Agent 不知道。
- **抵抗「合理化」**：Agent 违规往往不是不知道规则，而是会给自己找理由绕过去。所以要显式否定常见变通、列出借口与反驳、给出红旗自检清单。
- **Skill 也要测**：先跑没有 Skill 的基线，把失败记下来（RED）；写最小 Skill 修掉这些失败（GREEN）；再堵新发现的漏洞（REFACTOR）。
- **按风险调自由度**：高风险、纪律型任务用刚性规则；分析型任务保留空间，但约束分析维度、依据和优先级。
- **高内聚、低耦合**：一个 Skill 只做一件事、边界写清楚；不要做「超级 Skill」，也不要让多个 Skill 互相重度依赖，组合靠路径引用。

## 怎么做 / 为什么

### 1. 正文结构
- 常见顺序：概述 → 何时使用 → 核心模式 → 速查 → 实现步骤 → 常见错误。
- 一个紧凑的模板：开头不超过两行说明何时用，一段心智模型，每个子主题三到六条要点，结尾必须有反模式段。
- 按类型定写法：技巧型（有步骤的方法）、模式型（思考方式）、查阅型（API、语法速查）、纪律型（强制纪律，如 TDD）。纪律型用刚性规则，模式型用灵活原则，Skill 开头最好自己说明属于哪一类。
- 分层放文件：`SKILL.md` 只放核心流程、触发条件和资源导航；细则、检查清单、反模式放 `references/`；输出格式放 `templates/`；格式和字段校验放 `scripts/`。重型查阅材料（例如几百行的 API 说明）单独成文件，按需读取。

### 2. 可发现性
- 描述以「当……时使用」开头，写具体症状，不写抽象功能名。
- 命名动词优先，例如 `creating-skills` 优于 `skill-creation`。
- 控制篇幅：入门工作流类少于 150 词，频繁加载的少于 200 词，其余少于 500 词。
- 关键概念在描述、标题、正文里重复出现，便于匹配。
- 交叉引用写路径，不用会强制加载的引用语法，避免把别的 Skill 一起拖进上下文。
- 触发质量两头都要防：该触发不触发、不该触发乱触发。必须每次都发生的事，不要指望 Skill，交给 Hook。
- 定期做上下文体检：找出描述过长、正文过长、内容重叠的 Skill。

### 3. 抗合理化
- 把基线测试里 Agent 用过的借口收集成「借口 → 反驳」表。
- 写明「违反字面规则就是违反规则本身」，切断「我遵守的是精神」这一整类论证。
- 给红旗清单让 Agent 自检，例如「我正在想跳过这一步，因为这次情况特殊」。
- 这类「预先反驳借口」的写法在不同团队的 Skill 里独立出现过，说明它是解决真实问题的通用设计。
- 局限：反驳表只能覆盖预料到的借口，Agent 找到新理由时就会失效，所以 Skill 需要持续迭代。

### 4. 测试：TDD for Skills
- **测试用例**是子 Agent 的压力场景，「生产代码」就是 `SKILL.md`。
- **压力类型**：时间、沉没成本、权威、经济、疲劳、社交、务实七类，组合三种以上最能暴露问题。
- **流程**：基线（不加 Skill 跑真实任务，记录典型失败）→ 从失败提炼规则、反模式和模板 → 新会话只加载 Skill 复测 → 用检查清单核对 → 能脚本化的交给脚本 → 积累成评测集持续迭代。
- **输出基准化**：把一次满意的输出存成基准，下次执行直接拿来做回归比对。
- **判断标准**：不是某次输出惊艳，而是在不同输入、不同会话、不同边界条件下稳定提升结果。
- **成熟度三问**：能否减少同类任务的典型失败？能否在新会话里稳定触发并执行？输出能否被检查清单或脚本验证？

### 5. 知识型、文档型 Skill 怎么测
这类 Skill 往往没有标准答案。可行路径是：先快速做出能用的版本，用四五个基础用例抓明显问题，再放到真实仓库、真实使用者手里检验。容易踩的坑：只在一个 Agent 工具上测，换工具就不兼容；跨会话记忆污染评测结果；「结构对」不等于「内容对」。

### 6. 维护
- Skill 和它描述的对象放在同一个仓库、走同一套 CI，改代码时顺手改 Skill，Skill 才不会悄悄过时。
- 模型能力变化后，为补偿旧短板写的约束要删减，定期审查整套配置。

### 7. 案例：领域产出型 Skill 的共同骨架
- **技术图生成**：把「画图」拆成语义识别（这是什么类型的图）→ 布局选择 → 几何校验（箭头、泳道、图形语义一致）→ 格式导出（SVG、PNG、动图、离线 HTML）。线型和颜色本身承载语义，例如实线表示主数据流、虚线表示异步事件。提示词要写得像设计说明，而不是一句「画个架构图」。
- **可编辑 PPT 生成**：先回答三个问题（使用场景、视觉风格、图片处理方式），再确认五项方案（画布尺寸、页数、配色、图标风格、字体），然后输出原生可编辑的 `.pptx`。原则是「可编辑性优先于完美」。
- **共同点**：先澄清结构，再生成；澄清要有限、具体（需求澄清类 Skill 常见的做法是一次只问一个问题，并附上推荐答案）；产物能继续编辑、能进版本管理、能被脚本校验。这比「一次生成得很惊艳」更重要。

## 边界与误区
- **误区：没有触发边界、决策逻辑、反模式和验证的 Skill 也算 Skill。** 它只是更长的提示词。
- **误区：规则写得越多越好。** 关键是堵住合理化的路径，而不是堆规则；规则一多，描述和正文都会失焦。
- **取舍：测试门槛定多高。** 「没有失败测试就没有 Skill」对纪律型 Skill 很有效，但对个人或小团队可能过重，导致 Skill 库一直是空的。务实的做法是：纪律型 Skill 严格走 TDD；知识型、产出型 Skill 走「少量基础用例 + 真实使用反馈」。
- **误区：测过一次就够。** 模型、工具、仓库都会变，评测集要随失败样本持续增长。
- **边界**：本页讲怎么写单个 Skill；Skill 能否被自动优化，属于自进化问题。
