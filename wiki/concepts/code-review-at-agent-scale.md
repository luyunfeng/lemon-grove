# Agent 时代的代码评审（Code Review at Scale）

> 当 Agent 写掉大部分代码，逐行人工 review 在物理上不可行。评审的目的从「有没有人读过这段代码」改为「这个变更可能出什么问题，哪种检查——自动的或人工的——最适合抓住它」，用最少的人工审查时间换取 revert 率和事故率不升。

## 要点

- **「有人读过」是糟糕的代理指标**。它不区分读了什么、能否发现风险。这一转换同时改变了评审发生的时机：从终点的闸门变成持续运行的过程，像写作时的拼写检查；多数变更在被要求人工看之前，已经被模型审查并修复过至少一次。
- **稀缺资源是人的时间和注意力**，且覆盖评审成本的两面：审查代码花的时间，和修坏代码花的时间。只压缩前者、把成本转移到后者，等于没省。护栏是 revert 率和事故率，一旦上升说明只是把人的时间挪了地方；过程指标是每 PR 人工审批数（中位数与 P95）、人工评论数、PR 等人时长。
- **分层防御，不靠单点闸门**。每一层只抓一部分问题、漏掉另一部分，漏网的由最后一层快速回滚兜底；某层漏了，复盘要问「这一层应该抓住它吗、为什么没抓住」，而不是只责备人。
- **审批强度跟风险走，不跟作者走**。风险档由分类器读变更内容决定：文档类零人、普通变更一人、最高风险与敏感路径两人。Agent 的 approval 永远不能顶替人的名额；指挥 Agent 生成变更的人本身计入必审名额，与亲手写等效。approval 只绑定特定 commit，系统无法担保的新提交（Agent push、手工解决的 merge）要重新审批。
- **评审必须收敛**。Agent 作者 × Agent 评审者可能无限互相消耗，有 PR 一夜跑了五十多轮。复盘发现评审者反复 flag 的内容约 59% 是首轮就存在的旧代码：它很少发现新问题，只是每轮多翻出几个旧的。
- **事故是评审者的评测集**。每个引发事故或被 revert 的变更，经专家确认后变成评测用例；评审者的 prompt、工具或模型一变，就每天在这个集合上重新打分，分数上升才保留。

## 怎么做

一个变更的完整生命周期通常长这样：

| 阶段 | 检查 |
|---|---|
| PR 前 | 模型运行测试、构建、lint 并展示输出（不允许只声称完成）；另一个全新上下文的子 Agent 审查 diff |
| 每个 PR | 必过 CI；多 Agent 并行找 bug、另一组 verifier 对每条 finding 投票过滤误报，幸存 findings 按严重度排序；独立的安全审查；两类 findings 未清都阻塞合并 |
| 审批 | 分类器定风险档（零人 / 一人 / 两人）；轻量通道仅限受信作者名单，敏感路径永远要人 |
| 合并 | merge queue 在最新 main 上重跑全部检查 |
| 发布 | feature flag 内部先用，分渠道渐进发布；作者与 on-call 观察，flag 可免部署关闭，坏构建直接 revert |

落地要点：

1. **把验证前移**。给模型可运行的检查（测试、构建、截图对照设计稿），要求它展示输出；完成后由全新上下文的子 Agent 审查，避免自评。这是 Verification（验证）的第一原则在评审上的应用。
2. **用文件沉淀评审标准**。CLAUDE.md 写项目栈、约定、目标与非目标，每次评审都会加载，评审者也负责指出违反约定、或让文档某行过时的变更；REVIEW.md 由 code owner 写，说明这片代码什么最重要：这个仓库里失败长什么样（文档是「内容说谎」，配置是「路由指错」）、限制 nit 数量、列出跳过的路径、要求以文件和行号为证据。评审标准是否被评审者真正遵守，要单独核查。
3. **每条 finding 必须被回应**：修掉，或带理由关闭线程。纯风格、诊断、清理类 finding 直接丢弃；每条按严重度标注（Important / Nit / Pre-existing），不是本 PR 引入的问题不算在作者头上。被反复 flag 的问题回源头修：改 skill、加 lint 规则、更新入口文档，见约束的强制分层（Rule Enforcement Layers）。
4. **治理收敛**：轮数封顶，例如三轮后要求作者停下来重新考虑方案；首轮之后只 re-review 新 diff；按 bug 类型修复全部实例而不是一行；不重复已发布的 finding。一轮通过率和平均轮数是健康指标。
5. **度量驱动评审者迭代**。优先级明确写下来：先抓真 bug，再降评审轮数。噪音按「人如何回应评论」分类测量（修了、反驳了、有意为之、无所谓），并在已知干净的 PR 上统计误报。
6. **人的位置上移**。留给人的五类决定：要不要做这件事（方向、品味、范围）；高风险代码（计费、自动更新器、CI 工作流）；会定模式被他人复制的架构；读证据（测试输出、命令与返回、截图、评审 findings——说不出自动检查会漏什么，就要求一次真正的评审）；对结果负责。落地后的所有权规则是 you land it, you own it：中小变更出问题通常由落地者修复，不是追责而是因为上下文最多，事故复盘针对系统。
7. **代码理解换一种获得方式**。评审的第二个功能——传播代码库理解——不再靠读彼此的 diff：想理解哪个切片，让模型针对它生成 explainer 或讲解工件，几分钟即得、反映代码当下状态。一行文案变更学不到东西，即将修改的模块的讲解才值得注意力，对应理解工件的应用。

## 边界与误区

- **误区：省下审查时间就是省了时间**。人工时间同时出现在审查侧和修复侧，只看审批数会掩盖成本转移，必须以 revert 和事故率为护栏。
- **误区：评审轮数越多越安全**。多轮的主要产出往往是旧 bug 的重复发现和噪音；噪音对 Agent 作者代价更高——人可以无视一个 nit，Agent 会修，于是多一轮提交和评审。
- **误区：低风险通道放开给所有人**。轻量审批只对受信作者开放，其他作者的变更始终需要额外一人审批。
- **尚缺的一环**：根据 revert 和事故指标自动收紧审批的熔断机制还不成熟；就位之前，零人合并的适用范围应当保守。
- **方向变更要趁早**。Agent 让「开始」变得便宜，有些工作不该落地；方向性异议要在评审线程早期提出，而不是等 PR 完成后用阻塞评论推翻。
