# 目标驱动与计划驱动（Goal vs Plan）

> 控制 Agent 执行有两种方式：**计划驱动**是事前定好步骤、按步骤执行；**目标驱动**是只给出可验证的完成条件，让 Agent 按「做 → 验 → 修 → 验」自己找路径，事后用验证判断是否达成。前者控制过程，后者控制结果；选哪种，取决于「怎么做」和「做到什么」哪一个已知。

## 要点
- **一句话区分**：计划是「先计划再执行」；目标是「定个目标，你自己想办法达成」。
- **选择规则**：「怎么做」已知、步骤稳定，用计划；「做到什么」已知、路径不确定，用目标。
- **目标驱动的核心是闭环自验证**：每一轮结束后检查完成条件，没达标就带着差距继续修，直到通过或触发上限。
- **目标驱动的上限由完成条件决定**：条件写得模糊，循环只会更快地收敛到错误答案。
- **两者互补，不是替代**：计划适合需要人把控每个环节的任务；目标适合探索、试错、多轮调优的任务。

## 对比
| 维度 | 计划驱动 | 目标驱动 |
|---|---|---|
| 控制点 | 事前：审阅步骤 | 事后：验证结果 |
| 执行方式 | 先定详细计划，按步骤顺序执行 | 设定目标和验证条件，自主探索路径 |
| 灵活性 | 计划定下后，中途调整成本高 | 按验证结果动态换策略 |
| 容错 | 某步出错，需要人工重排计划 | 自动发现错误 → 修复 → 再验证 |
| 人的工作 | 审阅计划、确认每一步、处理偏差 | 只定目标和验收标准 |
| 适合的例子 | 按设计文档实现三个接口；把 Python 2 代码迁移到 Python 3 | 重构模块、功能不变、代码量减少 50%；找出 bug 并修复到所有测试通过 |
| 成本 | 相对可控 | 可能更高（多轮验证迭代） |

一个直观的例子是「优化代码性能」：计划驱动可能先写一串分析步骤，但真实瓶颈未必在预想的位置；目标驱动直接设定「性能提升 30%」，让 Agent 自己测、自己调。

## 怎么做
**写好完成条件**是用好目标驱动的全部功夫：
- 把命令式任务改写成可验证的成功标准，先定义验证方式，再执行改动。
- 条件要对检查者可见。如果由一个只读对话记录、不调用工具的评估器来判断，就要让 Agent 自己运行命令并把结果打印出来，例如「运行竞态检测测试，0 个失败」。「线上服务恢复正常」这类外部状态，评估器看不到，不适合当条件。
- 在条件里写上退出口，例如「修复不稳定的测试，或 20 轮后停止」，并设 token 预算。
- 要求每次声称完成时附上证据：运行了什么、结果、没跑什么以及为什么、残余风险。这些内容写进对话，正好满足「评估器只能看对话」的约束。

**把目标循环沉淀成流程**：同一类目标反复出现时，可以把「执行 → 跑测试 → 失败就修 → 检查指标 → 不达标继续」封装成可复用的工作流，一次配置、多次运行。不在意 token 消耗时，这是最省人力的做法。

**两者可以串起来用**：先用计划或规格把「做到什么算完成」讲清楚，再交给目标驱动去达成；计划负责校准方向，目标负责闭环落地。

## 为什么独立评估
目标驱动里，「谁来判断完成」很关键。执行者自评，是在自己留下的语境里检查自己，天然倾向于高估；把判断交给一个有独立上下文、只看完成条件和产出的评估者，激励方向变成找问题。这是 Harness Engineering（驾驭工程）里生成与评估分离的思想在单个任务上的落地。另一种做法是让执行模型自判完成，它在完成条件能被确定性信号（测试、lint）覆盖时足够好用。

## 边界与误区
- **误区：什么都用目标驱动**。需求明确、步骤固定、需要人把控每个环节的任务，计划驱动更合适，成本也更可控。
- **误区：无人值守就是不用管**。无人值守的循环也在无人值守地犯错；目标循环跑完，「完成」的最终验收仍要有人负责，还要警惕理解债务和不加判断地接受结果。
- **误区：不设护栏**。迭代上限、预算、无进展检测、熔断，缺一个都可能让循环失控。
- **误区：把目标模式的自验证当成定时循环**。目标模式的循环是内置的「做 → 验 → 修」机制；定时循环是按时间间隔触发的调度器。两者可以组合（目标定义完成标准，定时循环持续推进），但不是同一个东西。
- **计划驱动也不是没有验证**：它把验证前移到审阅计划上，适合需要人把控每个环节的任务。
