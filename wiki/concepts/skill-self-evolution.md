# Skill 自进化

> Skill 自进化是把 Agent 的**行为层**（Skill、Prompt、工具描述，再往外是工作流和 harness 代码）当作可优化对象，不动模型权重：收集执行轨迹，用自然语言分析失败原因，提出有边界的改动，经过验证门控和人工审批后再上线。它想解决的是「Skill 靠人手工调、越补越特化」的问题；能否方向可控，完全取决于验证机制。

## 要点
- **优化的是行为层，不是权重**。改的是 `SKILL.md`、工具描述、system prompt 这类文本，不需要 GPU 训练，主要靠 API 调用。
- **验证就是奖励函数**。没有验证，就会出现三种典型问题：为迎合个例把 badcase 补进去导致过拟合；越优化越差；进化方向不可控。
- **改动要有界，门控要严格**。每步只允许少量原子编辑，限制 Skill 和工具描述的体积，只接受「严格优于当前最优」且在留出集上无回归的候选。
- **验证器、权限和人留在循环外**。被优化的系统不能改评测本身，否则会通过破坏评测来刷分；上线走 PR 审批，不自动生效。
- **现状是初步的工程探索**。能落地的主要是 Skill 文本优化，工具描述、系统提示、代码层的进化大多还在规划阶段；不能理解成「Agent 已经会自主进化」。

## 怎么做 / 为什么

### 1. 成立的三个前提
1. Agent 的行为主要由文本决定（Skill、Prompt、工具描述）。
2. 文本优化可以交给 LLM 完成。
3. 优化结果能被外部验证（测试、评测集、人工审批）。

第三条最难也最关键。它和训练侧的可验证奖励是同一个逻辑：信号越客观，优化越可控。

### 2. 基本流水线
当前 Skill / Prompt 作为基线 → 生成评测任务，或从历史会话里挖真实案例 → 执行并收集轨迹 → 用自然语言反思失败原因 → 生成候选变体 → 约束门控（结构完整、体积限制、测试和基准回归）→ 选出最优变体 → 提交 PR 由人审批。

这里常用的优化器是 GEPA（Genetic-Pareto）：用自然语言反思替代强化学习的梯度，采样轨迹、分析失败、生成候选、在 Pareto 前沿上挑选，逐步累积成一棵进化树。它的优势是学习信号比一个标量奖励丰富，改动路径人能读懂，样本效率明显高于在同类任务上直接做强化学习。

### 3. 三种 Skill 优化思路：差别在验证
| 思路 | 做法 | 验证方式 | 更新粒度 |
|---|---|---|---|
| 归纳式 | 大量轨迹并行分析，再层次合并出通用 Skill | 只做格式校验，没有显式效果验证 | 一次性合并 |
| 自然选择式 | 执行 → 提案 → 构建 → 验证闭环，失败驱动；维护一个「前沿集合」，累积的反馈历史起到「动量」作用 | 验证集得分超过前沿里最弱者才保留 | 每轮一个 Skill 或一次编辑 |
| 类训练式 | 把 Skill 优化对标模型训练：学习率、动量、验证门控，再加一层「调优经验的经验」做元学习 | 严格优于当前最优才接受 | 每步有上限的原子编辑 |

从上到下，验证越来越严、更新越来越小、越来越像训练，也就是「Skill 应当像参数一样被训练」。归纳式的价值在于聚合：例如「云主机无法远程连接」这类工单，单张很难抽象，聚合大量工单后才找到真正的共性原因（CPU 或内存跑高、磁盘写满、端口不通、安全组拦截）。

### 4. 从「改了」到「证明改对了」
更往外一层，是让 Agent 改进自己的 harness。两种成熟做法值得借鉴：
- **先挖弱点，再做有界改动**：收集轨迹，把失败聚类成有验证器支撑的失败模式；给提案者有边界的上下文（可编辑范围、失败模式、必须保留的通过行为、历史上失败过的改动）；最后用留入集（修好了没有）和留出集（有没有退步）的回归测试决定是否接受。
- **把每次改动变成可证伪的主张**：每个可编辑组件在文件系统里都有明确表示；原始轨迹先整理成逐任务的根因报告；每个改动附一份说明，写清证据、根因、目标修复、预期收益和回归风险；运行记录、追踪器、验证器、模型配置全部只读。

### 5. 工程侧的轻量版本
- **人工驱动的 TDD for Skills**：构造压力场景让 Agent 违规，强化 Skill，再堵漏。这是人做的元控制；自进化把「提出更好的 Skill」这一步也自动化了。
- **观察 → 候选 → 人勾选**：用 Hook 捕获会话观察（Hook 每次都会触发，比 Skill 可靠），后台用便宜模型检测几类模式（用户纠正、错误解决、重复工作流、工具偏好），生成带置信度的候选「直觉」条目，再聚类升级成 Skill 或命令；同一条目在多个项目里反复出现、置信度足够高时才提升到全局。落地时比让 Agent 自己决定「写入记忆」更稳，后者容易积累过期、偏题的内容。

### 6. 落地顺序
先有可重复的评测集和输出基准 → 再做「自动生成候选 + 人工审核」→ 最后才考虑有条件的自动接受。没有评测集就做自进化，只会放大过拟合。

### 判断是否成熟的三问
- 是否把失败变成可检索的证据？
- 是否把每次改动变成可证伪的假设？
- 是否把验证器、权限和人工审查放在自我演化循环之外？

缺任何一条，系统都容易从「自我改进」滑向「自我确认」。

## 边界与误区
- **误区：自进化等于模型改写自己的权重。** 目前能落地的都在 harness 层；即使是让 Agent 修改自己 harness 代码的开放式演化，也是「固定模型下的 harness 演化」。
- **误区：有递归结构就会越来越好。** 底座模型不够强时，递归优化可能越改越差；会提出改动和能从改动中受益是两种能力。
- **难点：谁来定义「更好」。** 用测试套件定义，方向就是「通过更多测试」；用人工评分定义，方向就是「人类偏好」；让 Agent 自己评，又回到自评偏差。弱而模糊的评测器、负结果没人记录、多样性塌缩、奖励作弊，都会直接伤害进化方向。
- **看效果数字要看前提。** 尚不成熟的项目，实验常常只有个位数的合成用例、用关键词重叠这类启发式打分，同一组结果按不同口径算出的提升幅度可以差很多。这类数字只能说明「流程跑通了」，不能当作效果证据。
- **人的位置在上移，而不是消失。** Harness 约束 Agent，进化系统优化 harness，人约束进化系统：从「在回路里」变成「在回路之上」。
