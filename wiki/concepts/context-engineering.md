# Context Engineering（上下文工程）

> 把上下文窗口当作稀缺的计算资源来管理：在正确的时机、以正确的格式，给模型**最小但高信号**的信息和工具。它解决的问题是：任务变成多步骤、跨工具、带状态之后，模型因为看不到该看的、或被无关信息淹没而出错。

## 要点
- **少而准，不是多**。上下文是每次调用注入的 token 集合，token 是边际收益递减的有限资源；上下文越长越杂，模型对关键信息的关注反而下降。
- **很多「幻觉」其实是上下文供给失败**：系统没有把完成任务所需的信息及时、准确地给到模型，模型只能在信息盲区里按概率猜。
- **核心设计思想**：只有当前步骤真正相关的信息才占用窗口，其余留在外部系统，等需要时再调取。
- **结构比数量重要**。在一个数据分析 Agent 的消融实验里，给 Agent 原始检索数千条历史查询，准确率提升不到 1 个百分点；瓶颈不是能不能访问历史工作，而是信息有没有结构。
- **它是驾驭工程的一层，不是全部**。上下文工程优化的是输入端，形态更接近开环；模型做偏之后怎样拉回来，交给 Harness Engineering（驾驭工程）。

## 为什么需要
任务从一次问答变成多步骤系统后，单靠写提示词会碰到三个边界：
1. **复杂度承载不了**：异常处理、格式要求、工具规范、「如果 X 就 Y」的补丁不断塞进提示词，最后变成一个不断打补丁的脚本。
2. **工具规则被噪音淹没**：关键的调用约束埋在大段背景文本里，导致调错工具、传错参数、顺序错乱。
3. **静态提示给不了实时状态**：服务状态、会话记忆、工具中间结果、当前执行阶段都没法写死。

问题于是从「怎么表达」变成「模型完成当前这一步，到底需要知道什么」。上下文还会从两个方向变脏：**静态上下文**随工具、文档、规则增加而膨胀；**动态上下文**在推理—行动循环里被长日志、编译输出、网页正文、大文件污染。

## 怎么做
这些手法的共同点是：信息默认待在窗口之外，由工具按需「拉」进来。

| 手法 | 做法 |
|---|---|
| 渐进式披露 | Skill 分三层加载：启动时只加载名称和用途；匹配任务后才加载正文指令；真正用到时才读取资源或执行脚本，进入上下文的往往只是执行结果 |
| 工具执行隔离 | 长日志、网页正文、大文件、测试输出落到外部存储或索引层，主上下文只留摘要、结论或可检索的句柄 |
| 文件系统即记忆 | 实验日志、diff、错误轨迹、过去的运行记录存成文件，按需读取，而不是塞进上下文 |
| 子 Agent 隔离 | 探索交给只读子 Agent，只返回结论，冗长的中间输出不进主会话 |
| 分层入口文件 | 根目录的 CLAUDE.md / AGENTS.md 只放指针和关键陷阱，子目录放本地约定；目录结构不自解释时，建一份轻量的代码库地图 |
| 过滤噪音源 | 用 `.ignore` 和 `permissions.deny` 排除生成文件、构建产物和第三方代码；按子目录限定测试和 lint 命令；用 LSP 做符号级导航，避免 grep 一次返回数千个匹配 |
| 小入口 + 可索引知识 | 不堆一个越来越臃肿的入口文件，而是小入口加上可版本化的设计文档、计划和验证状态 |

**放什么：可信度比数量重要**。
- 按信任度给信息源排序，结构化的可信源优先。在数据分析场景里，信息源按「语义层（指标定义、维度映射、聚合规则）→ 血缘图谱 → 历史查询语料 → 业务上下文」排序；没有 Skill 时准确率不超过 21%，加上结构化的 Skill 后稳定高于 95%。
- 只写代码推不出来的知识（领域概念、业务约束、历史决策），这部分是 Agent 原生文档（Agent-Native-Doc）的主题。

**Agentic Search 与 RAG 的取舍**。

| | RAG | Agentic Search |
|---|---|---|
| 做法 | 预先建嵌入索引，查询时检索片段 | 像工程师一样遍历目录、读文件、grep、跟踪引用 |
| 优势 | 超大规模语料下召回快 | 直接面对实时代码，没有索引滞后，不用维护嵌入管道 |
| 失效模式 | 索引滞后，可能返回已删除的函数 | 需要足够的起始上下文「知道往哪看」，效果取决于入口文件和 Skill 的分层质量 |

对活跃开发中的代码库，索引滞后通常不可接受，所以编码 Agent 多走 Agentic Search，再用入口文件和代码库地图补足「往哪看」。

## 边界与误区
- **误区：窗口越长越好**。长窗口并不等于用得好，上下文变长后效果会掉，费用也上涨。更可靠的做法是：保持代码库精简、维护代码库地图、及时修剪记忆，把跨会话的信息放进长期记忆而不是一直压缩上下文。
- **误区：有了驾驭工程，上下文工程就过时了**。它仍然决定每一次推理能看到什么；动态组装、渐进式披露、缓存优化、检索、记忆裁剪都不会消失。更准确的关系是：驾驭工程的一部分，就是为上下文工程搭一个好的供给机制。
- **天花板**：上下文工程的假设是「看到正确信息，输出就大概率更好」，这在单次推理里成立；但在运行数小时乃至数周的系统里，它保证不了模型不漂移、不累积错误。长程任务要把状态外部化，并配上验证回路。

| | 上下文工程 | 驾驭工程 |
|---|---|---|
| 控制形态 | 接近开环：结果不好，由人在回合之外调整输入 | 闭环：输出被测量、比较，偏差自动修正 |
| 类比 | 让每一次发射更准 | 飞行中持续修正弹道 |
| 关心的问题 | 该给模型看什么 | 模型看错、做偏之后怎么办 |

- **上下文本身可以被优化**。一种方向是把上下文从越来越长的提示词变成可演化的条目化手册：生成者产出轨迹，反思者从成败中提炼要点，整理者以条目形式更新结构化上下文；更进一步，把「如何管理上下文」的机制和「上下文里有什么」的内容拆开，让管理规则本身也进入优化。Agent 越独立，记忆越膨胀，上下文与记忆的生命周期管理会越来越像智能本身的一部分。
