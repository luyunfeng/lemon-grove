# Verification（验证）

> 生成容易，验证难。验证是 Agent 时代的瓶颈，也是最大的杠杆：把「做对了没有」从主观判断变成可自动执行、可回归的检查，Agent 才能被放心地长时间运行。

## 要点
- **瓶颈转移**：生成代码越来越便宜，确认它正确仍然昂贵。Agent 在孤立任务上成功率可以超过 80%，在连续演进的场景里跌到 38% 以下，主要障碍之一就是验证保真度不足——通过了测试，却引入了细微的语义错误。
- **一条原则**：能被客观验证的信号，比主观判断更可靠，也更能规模化。能验证的先自动化，不能验证的才留给人。
- **maker / checker 分离**：生成者评估自己的产出，会在自己留下的语境里思考，天然倾向于高估质量。检查者要有独立的上下文和预先定义的验收标准。
- **完成条件先于执行**：先定义「怎样算做完」、用什么方式验证，再动手。模糊的完成条件只会让自动化更快地收敛到错误答案。
- **判断力的核心**：知道什么证据能一锤定音，以及这个证据的边界在哪里——它什么时候会失效。

## 怎么做
**1. 把完成条件写成可验证的形式**
- 把命令式任务（「优化一下性能」）改写成可检查的成功标准（「基准测试提升 30%，所有测试通过」）。
- 条件要让检查者「看得到」：让 Agent 自己运行命令并把结果打印出来，例如「运行覆盖率测试，输出的覆盖率一行显示 ≥ 80%」。只能在外部系统里看到的状态，不适合当完成条件。
- 条件从哪里来：事前写规格，见 Spec 驱动开发与执行前校准（Vibe / Plan / Spec）。

**2. 分层选择检查手段**
| 被检查的东西 | 优先用的信号 | 说明 |
|---|---|---|
| 可形式化的正确性 | 测试、类型检查、lint、架构规则 | 确定性、便宜、可反复跑，优先交给工具 |
| 运行时行为 | 日志、指标、trace、UI 截图 | 把「800ms 内启动」这类要求变成可读的测量值 |
| 语义质量 | 独立评估 Agent、对抗性审查 | 贵，但能发现测试覆盖不到的问题 |
| 业务价值 | 事先对齐的指标口径和监控大盘 | 必须在项目启动时就设计，事后补不回来 |

**3. 要求完成声明带证据**
任何「完成」都要附上：运行了什么、结果是什么、失败如何处理、哪些没跑以及为什么、残余风险是什么。核心规则是：没有验证证据，就不要说「完成」。人工审阅也随之从逐个看补丁，转向审阅证据、设自动接受标准，只把关键区域交给人。

**4. 守住 source of truth，追问证据链**
- 不只问「结论是什么」，还要问「依据什么证据、证据的边界在哪、还有什么证据会推翻它」。例如 AI 给出崩溃调用栈时，继续核对偏移、汇编和源码的对应关系。
- 证据本身也会错：曾有 AI 根据日志断定某个功能引入了问题，实际是历史日志写错了。日志是重要证据，但不是天然真理。

**5. 为生产环境留余量**
离线评估要锚定标准答案，按领域设发布门槛（例如约 90%）。离线准确率应接近 100%，因为上线后自然会下降（例如降到约 95%）；数据和知识过时还会继续漂移，需要持续回归。对抗性审查有效但昂贵：在一个数据分析 Agent 上带来约 +6% 准确率，代价是 token +32%、延迟 +72%。

## 为什么
- 它决定了自动化的上限：Loop Engineering（循环工程）能跑多久、多放手，取决于「完成」判得准不准。
- 它是进化的方向盘：在 Skill 或 harness 自我改进里，验证就是奖励函数；没有验证，进化方向不可控。
- 它和模型训练是同一原则：后训练从人类偏好转向可验证奖励，也是因为客观信号噪声低、能无限扩展，见可验证奖励。

## 边界与误区
- **误区：通过测试 = 正确**。验证本身也要被验证。「静默失败」——答案错了但看起来合理——仍是没有解决的难题。
- **奖励投机（reward hacking）**：一旦验证信号变成优化目标，Agent 可能找到满足检查、但不符合意图的解法，比如针对单测、评审模型或基准作弊。对策是把验证器、测试数据和权限放在 Agent 能改动的范围之外，保持只读。
- **不是什么都能快速验证**：数学、代码、分类这类有明确答案的任务最适合；研究品味、长期价值、真实业务效果很难用快速验证器衡量，这部分仍要靠人的判断和事后指标。
- **置信度不能替代验证**：让模型自报置信度，可以用来决定把人工审查集中在哪里，但模型天生偏自信，置信度也不是概率，只能辅助外部验证。
- **自评不算验证**：同一个上下文里「写完再检查一遍」不等于独立检查。
