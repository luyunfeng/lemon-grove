# 子 Agent 编排（Sub-agents / Multi-Agent）

**一句话**：把一部分工作交给独立上下文的子 Agent 去做，只把结果带回主会话。拆分要回答四个问题：为什么要拆、按什么边界拆、之间怎么通信、结果谁汇总；工程上还要管住失败、预算、权限和追踪。

## 要点

- **上下文隔离**：搜索结果、日志、大段文件内容留在子 Agent 里，主会话只收到结论。子 Agent 探索可能花掉几万 token，交回主 Agent 的往往只是一两千 token 的摘要。这是子 Agent 最基础、收益最确定的用途。
- **拆分理由有四类，只有一类是并行**：隔离上下文；隔离相似重叠的工具；分开职责（提示词分支难维护、写和审角色冲突）；并行互不依赖的子任务。每一路只是一次查询，单 Agent 并行调工具就够；每一路都要自己搜、读、判断好几轮，拆开才换来各自干净的上下文。
- **拆开要付账**：token 用量约为普通对话的 4 倍，多 Agent 系统约 15 倍，有的对照分析里 token 用量一项就能解释基准表现差异的大头；协调本身也花钱——拆任务、写说明、读报告、核对版本。信息交接时会丢失，隐含决策会冲突：两个子 Agent 各做一块，各自的决定都说得通，放在一起对不上。上游的错误结论到下游就成了已知事实。
- **分离探索与编辑**：只读子 Agent 先摸清子系统，主 Agent 拿到完整信息后再改代码，避免边看边改。
- **分离实现者与检查者（maker / checker）**：写代码的和审代码的不是同一个上下文；检查者要有独立上下文，能接测试结果这类外部信号更好。
- **可检查是底线**：产出落在文件、日志、状态记录里，中断后还能恢复和追查；回传用固定字段（状态、结论、证据、假设、未核实项），人和程序都能检查。
- **给子 Agent 限权**：按最小权限配置工具白名单；只读角色不给写权限，有副作用的操作留给主 Agent 或要人确认。
- **成本路由**：探索、搜索交给便宜快的模型，主 Agent 保留强模型做理解、拆分和汇总；预算整棵树统一记账，子 Agent 继承剩余额度。

## 什么时候值得拆

值得拆：

- 子任务依赖少，各做各的：广度优先的调研、多来源分头检索、按模块分头审查。
- 过程很长、结论很短：读大量日志、翻代码，最后只要一个结论。
- 需要不同的工具或权限：只读的检索和能写的执行分开。
- 需要一个没参与过程的人来检查。
- 任务价值高到付得起额外开销。

不该拆：

- 各部分强依赖、要共享同一套决策——编码任务里真正能并行的部分通常比研究少。
- 一个 Agent 几步就能做完。
- 流程固定、每步都能写死的任务，用 Workflow 更稳。

判断关键不在流程固不固定，而在每一步要不要大量探索、要不要独立的上下文和权限、能不能并行。编码场景还要求同时满足：任务能独立验证、文件冲突概率低、主会话能汇总结果。

**Skill 还是子 Agent**：缺「会不会做」就加 Skill——Skill 是一份做事说明，活还是同一个 Agent 干，上下文和权限是同一套。缺「别把主上下文弄乱」「要用不同权限」「要独立检查者」「要并行跑几轮」才拆子 Agent——它在自己的上下文窗口里运行，有自己的系统提示词、工具和权限，做完只交回摘要。

## 怎么做

### 三种编排方式
| 方式 | 谁来编排 | 中间结果放在哪 | 规模 | 适合 |
|---|---|---|---|---|
| 模型逐轮委派（Subagents） | 主模型每轮决定派谁 | 回到主对话 | 每轮几个任务 | 聚焦的小任务：搜索、分析、审查 |
| 团队协作（Agent Teams） | 一个 Lead 协调，若干 Teammate 各自工作，共享任务列表和消息箱 | 各自的上下文 | 建议 3–5 个 teammate，每人 5–6 个任务 | 需要讨论和协调的复杂工作 |
| 脚本编排（Dynamic Workflows） | 模型先写一段编排脚本，由独立运行时在后台执行 | 脚本变量，只有最终答案回主对话 | 数十到数百个子 Agent；并发上限 16，单次上限 1,000 | 能拆成大量独立子任务的工作 |

脚本编排的关键区别是**编排逻辑被代码化**：可重复执行，同一会话内已完成的子任务可直接复用结果，不再依赖模型逐轮决策。代价是运行中不能接受用户输入，需要分阶段签收时只能拆成多次运行。

具体到 Claude Code 的内置角色：Explore（便宜模型、只读，做快速搜索）、Plan（只读，做规划期调研）、General-purpose（全部工具，做需要探索加行动的多步任务）。

### 常见结构
| 结构 | 做法 | 适合 |
|---|---|---|
| 主从（manager） | 主 Agent 拆任务、派活、汇总，子 Agent 只对它负责，被当工具调用 | 要一个 Agent 掌控流程、最后综合结果 |
| 流水线 | 按阶段排好，一个做完交给下一个，顺序写死 | 阶段固定、接近 Workflow 的流程 |
| 并行分片 | 同类任务切几份各做一份再合并，如长文档按章节抽取 | 可独立验收的分片 |
| 执行 + 审查（evaluator-optimizer） | 一个生成，一个评估反馈，循环往复 | 质量要过检查关的任务 |
| 按意图转交（decentralized） | 分诊 Agent 判断意图后把整个对话连同状态交给专职 Agent，单向转交 | 不需要居中掌控的场景，典型是客服 |

主从可以套娃（主 Agent → 编排 Agent → 原子 Agent），每多一层就多一次转述和等待，只有下层 Agent 多到一个管不过来、或各层权限确实不同才值得加。

Sub-Agent 一般指主从结构里由主 Agent 派生、做完交回结果的子 Agent；Multi-Agent 范围更大，还包括平级协作、互相转交、互发消息——agent teams 里的队友可以直接发消息、用共享任务列表认领工作，token 也明显更多。只需要各自交结果，用子 Agent；要边做边对齐，才考虑平级协作。

### 按什么边界拆
- **上下文边界**：子 Agent 拿一份任务说明就能干完，不需要主 Agent 之前的全部讨论；离开那些讨论就做不对的部分不该拆出去。
- **工具和权限边界**：只读的和能写的分开，碰生产数据的单独一个。
- **能单独验收**：产出要能单独检查——测试是否通过、文件是否生成、结论有没有出处；没法单独检查的产出，汇总时也查不出错。
- 按职位起名不等于找到边界：「产品经理 Agent」「架构师 Agent」如果读的是同一批材料、做的是互相依赖的决定，拆完只是多了几次转述。

### 预定义还是动态创建
- **预定义**：每种子 Agent 的提示词、工具、权限提前写好，主 Agent 只决定派谁、派什么。可测试、行为可预期；Claude Code 的自定义子 Agent 就是这种，可以用 tools 字段列出允许的工具。
- **动态创建**：主 Agent 临场写任务说明、定数量。灵活，但要有上限——曾有系统对一个简单问题派出 50 个子 Agent，后来把规模写进提示词：简单事实查询 1 个 Agent、3–10 次工具调用；直接比较 2–4 个子 Agent、各 10–15 次调用；复杂研究 10 个以上、分工要清楚。
- 常见做法是两者结合：类型预先定义，具体任务动态下发。

防止派生失控，管三样：**嵌套深度**（子 Agent 默认可以再派子 Agent，常见实现限到主对话下第三层，设为 1 关闭嵌套）、**并发数**（同一会话同时运行的子 Agent 有上限，超出直接失败）、**整棵树共用的预算**。再加循环检测：每次派生带上祖先链，派之前检查有没有绕回去；同样的工具同样的参数被反复调用要能识别；兜底是全局步数和时间上限。

### 任务契约
子 Agent 从干净上下文开始，看不到主 Agent 之前聊过什么，任务说明是它唯一的上下文来源。只写「研究某主题」这类模糊目标，会出现查错方向、重复调查。至少写清六样：

1. 要交付什么；
2. 做什么、不做什么，和别的子 Agent 怎么分界；
3. 已确认的事实和相关文件路径，免得重查；
4. 用哪些工具、优先看哪些来源；
5. 交回的格式；
6. 做到什么程度算完成，最多花多少步、多少 token。

检验办法：把说明交给一个没参与讨论的新同事，能不能直接开工。大材料不整段贴，给路径或链接让它自己读。子任务有难有易：难的给更强模型、更多预算，机械的给便宜模型。预算是整棵树共用的：开工前给各子 Agent 留份额，运行时统一累加所有 Agent 的用量，时间和 token 哪个先到哪个停；只看主 Agent 的用量会严重低估。

### 怎么通信
| 方式 | 做法 | 代价与管法 |
|---|---|---|
| 经主 Agent 中转 | 子 Agent 只和主 Agent 说话，彼此看不见 | 好控制好追踪；主 Agent 成瓶颈，所有报告都进它的上下文 |
| 共享状态（黑板） | 大家读写同一块存储：任务表、状态对象、共享目录 | 管住写入：一个任务只被一个 Agent 认领；同一数据只有一份权威副本；写入带版本，冲突能被发现 |
| 直接对话 / 转交 | 平级互发消息，或把整个对话交给对方 | 要有明确规则，实验性功能通常明显更费 token |

顺序与路由：经主 Agent 中转时顺序由它定；共享状态靠任务认领和加锁；直接对话要由协调者指定轮到谁。路由的说明要写清负责什么、不负责什么，彼此不重叠——道理和工具重叠时选不准一样；标一批真实问题测路由准确率，错例回流；给路由留拿不准的出口（追问用户或交通用 Agent）；派错了要能退回，转交限次数，免得来回踢皮球。

子 Agent 一般不参与主 Agent 的上下文——隔离本来就是拆的理由。缺信息时带着问题提前返回，状态写明「需要补充信息」，主 Agent 补完再派。

### 回传什么
两种主张可以兼顾：完整的过程记录留在文件里（隐含决策都在过程里，要时可查）；默认只回短结论，避免层层转述的传话游戏。回传用固定字段：状态（完成 / 部分完成 / 失败 / 需要补充信息）、几句话的结论、证据（文件路径、链接、测试结果）、做了哪些假设、哪些未核实。产出还会变时，结论绑定版本：实现交出可测版本后记下文件哈希，测试结论绑定这个版本，免得拿中间产物的失败结论来回讨论。

### 跨模型混合
主 Agent 用高能力模型做理解、拆分和汇总，执行层按任务类型交给其他模型或其他 CLI。两种形态：
- **原生混合**：仍由 harness 自己的派发机制创建子任务，保留任务树、消息、等待、恢复等状态管理；父线程可以像管理普通子 Agent 一样追问和汇总。
- **进程混合**：主 Agent 直接启动其他 CLI 当独立执行器，从标准输出或事件流回收结果。解耦、维护成本低，但父线程要自己处理超时、状态和汇总。

跨模型时最容易踩的坑：**只验证「路由到了哪个模型」不够，要验证任务正文真的送到了**。某些协作协议会在发送前把消息加密，第三方模型收到的是密文占位；这只能在发送端处理，接收端套代理救不回来。一次可靠的验收要看四层：协议版本对不对、派发时是不是明文、子线程里有没有完整任务文本、子任务有没有交回可复核的文件或测试结果。另外，中间的转发代理会看到密钥、提示词、工具参数和响应，属于完整信任边界，应只绑定本机并用独立访问密钥。

### A2A 与 MCP 的分工
MCP 用统一协议把工具和数据源接给一个 Agent；A2A（Agent2Agent）把 Agent 彼此连起来。调 MCP 工具像调函数，输入输出确定，工具自己不做判断；通过 A2A 找的是另一个 Agent，有自己的模型、工具和记忆，对你是黑盒，可能跑很久，中途还会回头要信息。

A2A 的核心概念：

- **Agent Card**：一个 JSON，写明这个 Agent 是谁、服务地址、支持的能力、怎么认证，标准路径是 /.well-known/agent-card.json；别的 Agent 先读它再决定要不要交活。
- **任务**：有状态、有生命周期（已提交、处理中、需要输入、需要认证、完成、失败、取消、拒绝），长任务可以停在「需要输入」，等对方补充再继续。
- **消息与产出物**：消息是一轮交流，产出物（artifact）是任务做出的结果。
- **传输**：HTTP 上的 JSON-RPC，长任务用 SSE 推进度或回调，另有 gRPC 和 HTTP+JSON 绑定。

适用判断：Agent 由不同团队、不同厂商开发、分开部署时才值得上 A2A；同一进程、同一框架里的主从，用框架自带的子 Agent 或函数调用就够，上 A2A 只是多了网络、认证和版本管理的成本。子 Agent 要不要做成服务同理：要独立扩缩容、独立发布、给别的团队用，才值得。

三个词连起来：Skill 是 Agent 自己的做事方法，MCP 接它手边的工具，A2A 把活交给另一个 Agent。项目里常常组合：Workflow 串主流程，节点里的 Agent 调 MCP 接进来的工具，要大量探索的步骤再派子 Agent。

### 汇总与冲突
汇总由主 Agent 做。并行分片时各子 Agent 按统一格式交结果、带出处（第几块、哪一段）；按字段合并、去重、标出冲突，不要把几份报告丢给模型自由改写；块很多时分层汇总。

子 Agent 结果全对、汇总却出现幻觉的常见原因：报告太多太长，漏看或看混；模型用自己的知识补空缺；转述时改了数字和限定词；几份报告有冲突，被揉成一个通顺的说法。约束办法：每条结论标出来自哪条证据，标不出来的不写；汇总后加一道核对，逐条检查结论有没有依据（可以设专门的引用核对 Agent）；关键的数字和名称照抄，不让模型改写；汇总这一步不给检索工具，免得它半路自己找新材料。

两个 Agent 结论矛盾，四步仲裁：先确认是不是真冲突——时间点、统计口径、数据来源不同都会造成假冲突；再按规则采信——权威数据源优先于文档，文档优先于模型推断，新版本优先于旧版本，有证据优先于没证据；规则判不了就去查——调权威系统核实，或派一个 Agent 专门复核，还不行交给人；冲突写进结果里，不让汇总模型自己挑一个了事。投票只在各自出错原因互不相关时有用：同一个模型、同一份错误资料，几票会一起错。

幻觉在链路上会被放大：上游一句猜测，到下游成了已知事实，再传就没人记得它没验证过。让证据跟着结论走：结论和出处一起传，没有出处的标「未核实」；下游把上游输出当说法、不当事实；关键事实在交接处核对一次；最终引用能追到原始出处。

### Critic 与检查循环
- **查什么**：优先有客观依据的——测试过没过、格式对不对、每条结论有没有出处、需求清单上的项做没做到；主观部分用评分标准打分。
- **要不要换上下文**：同一个模型在同一个上下文里检查自己作用有限，没有外部反馈时模型很难自我纠错，改完有时反而更差。Critic 要有独立上下文，只看需求和产出、不看执行者的推理过程；能接测试结果、工具返回这类外部信号更好；条件允许换一个模型。
- **不通过怎么办**：给出具体问题和证据——哪条测试没过、哪条结论缺出处；执行者按清单改，不是整个重做；证据不足就定向补证，列出缺哪几条、只派任务补这几条。
- **防循环**：设最多几轮；连续两轮问题数没有减少就停；整体预算到线也停。停下时把没解决的问题写进结果，或交给人。
- **Critic 自己也要评测**：判错了好结果被打回、判漏了坏结果放过去，拿一批标好对错的结果去测它。检查不能省，检查的结论也要有证据。

### 工程治理
- **失败与超时**：每个子 Agent 设超时和步数上限；偶发错误（网络抖动、限流）有限重试，同样错误反复出现就别再试；失败也带着做完的部分返回，写清做到哪步、哪些未核实，主 Agent 据此重派、换人、跳过或降级；长任务从出错处恢复，而不是从头再来；有副作用的操作（写库、发消息、下单）要幂等，重试不能做两遍。
- **成功率是乘出来的**：五个环节各 95%、互相独立、出错不重试，整体只有约 77%。既看整体成功率，也看每个环节的，才知道该在哪加检查、加重试。
- **权限**：默认不全给，按最小权限——检索、审查只读；实现只能写自己的目录或分支；发消息、写生产数据、部署这类副作用操作，要么留给主 Agent，要么要人确认。消息同理：能发给谁、能读哪些共享状态都要限定。
- **追踪与记账**：一个任务一个 trace ID，每个子 Agent 是其中一段，记下任务说明、工具调用、结果、token 和时间。出了问题才能定位是谁引入的错，成本才能分到每个 Agent 头上。
- **评测先建单 Agent 基线**：同一批任务，单 Agent 基线和多 Agent 各跑几遍（结果有随机性，一遍不够），比成功率或质量分、耗时、token 和费用；分环节看路由准确率、子 Agent 完成率、Critic 判对率、汇总结论有多少能在子 Agent 结果里找到依据。起步二十来个代表真实用法的问题就够，模型打分加人工抽查。
- **延迟**：每多一层就多一轮模型调用、一份任务说明、一次汇总，串行部分只会更慢；并行只缩短互不依赖的那几路，整体耗时取决于最慢的一路。

### 推荐顺序
先用子 Agent 解决上下文污染，再考虑用脚本编排做规模化，最后才上跨模型混合。简单的单文件修改、纯文字润色、没有明确边界的发散讨论，不需要子 Agent。

## 边界与误区

- **并行 ≠ 有效**：大规模并行的协调质量、冲突解决和成本仍是未知数，可能出现「效率上去了，账单也爆了」。
- **子 Agent 不是分身越多越好**：token 成本随人数和层数增长，嵌套深度、并发数、总预算都要有上限。
- **maker / checker 分离不等于验证完成**：检查者也是模型，最终完成与否仍要靠测试、构建等确定性证据。
- **子 Agent 输出不要倾倒探索过程**：要求它返回摘要、结论和证据字段，否则隔离的意义就没了。
- **为了拆而拆**：说不出单 Agent 哪里不够、拿不出单 Agent 对照数据、没想清失败后怎么办、结论打架听谁的、循环几轮停，这样的多 Agent 方案站不住。
