# Superpowers

## 它是什么

一套构建在可组合 Skills 之上的 AI 编程完整开发方法，以 Claude Code 插件形式提供，是影响最大的 Agent 技能框架之一。它的取向是**纪律主义**：Agent 启动后不急着写代码，而是先退一步问清你真正想做什么，再按一条强约束的链路推进，每一步都有铁律和硬关卡。

四条核心原则：测试先行（永远如此）、流程优先于猜测、简洁是首要目标、证据先于「声称成功」。

## 核心机制

### 1. 七步工作流

1. **Brainstorming**：写代码前激活。一次只问一个问题，尽量给选择题；提出 2-3 种方案并比较权衡；设计按 200-300 字一段呈现，每段后问「这看起来对吗？」；需要时可以回退，灵活性优先于硬推。
2. **Using Git Worktrees**：设计批准后，切到独立工作树。
3. **Writing Plans**：把批准的设计拆成 2-5 分钟一个的小步骤（写失败测试、跑一遍确认失败、写最小实现、跑一遍确认通过、提交，各算一步）。计划要写到精确的文件路径、完整代码和精确命令，因为它假设执行者是一个「热情但品味差、判断力差、没有项目上下文、讨厌测试的初级工程师」。
4. **Subagent-Driven Development**：每个任务开一个新子 Agent，任务之间做审查。审查分两阶段：先查规格合规（是否符合计划），再查代码质量。
5. **Test-Driven Development**：RED → 确认失败 → GREEN（最小代码，不加功能）→ 确认通过 → REFACTOR。铁律是「没有失败测试先行，就没有生产代码」；先写了代码就**整段删掉**重来，不许留着「对照着改」。
6. **Requesting Code Review**：任务之间激活。
7. **Finishing a Development Branch**：任务完成后收尾。

另有系统化调试技能：根因调查 → 模式分析 → 单一假设并最小化验证 → 先写失败用例再修。铁律是「没有根因调查，就没有修复」；修复连续失败 3 次以上，就去质疑架构。

### 2. 三层强制模型

| 层级 | 载体 | 靠什么起作用 | 适合 |
|---|---|---|---|
| Level 1 | CLAUDE.md / Rules | 建议性上下文，靠写得好 | 编码风格、项目约定 |
| Level 2 | Skills | 结构化流程，加上合理化反驳表和红旗列表 | TDD、调试、代码审查 |
| Level 3 | Hooks | 硬性强制，退出码 2 阻断 | 安全策略、必须跑的检查 |

### 3. 抗合理化设计

核心洞察：**Agent 违规往往不是不知道规则，而是会给自己找理由绕过去。** 所以要堵住每一条合理化路径，而不是写更多规则：

- 显式否定每一种变通，而不只是陈述规则；
- 写一条基础原则「违反字面规则就是违反精神规则」，切断整类「我遵守的是精神」式论证；
- 合理化反驳表，例如：

| 借口 | 现实 |
|---|---|
| 太简单，不需要测试 | 简单代码也会出错，测试只要 30 秒 |
| 我稍后再写测试 | 后写的测试一写就过，证明不了什么 |
| 已经手动测过了 | 临时的不等于系统的，没有记录、没法重跑 |
| 删掉几个小时的工作太浪费 | 沉没成本；留着未验证的代码才是技术债 |

- 红旗列表，让 Agent 自己察觉「我正在合理化」。

### 4. TDD for Skills

把写 Skill 本身当成 TDD：测试用例是子 Agent 压力场景，「生产代码」是 SKILL.md。

| TDD | 写 Skill 时 |
|---|---|
| RED | 不带 Skill 跑压力场景，逐字记下 Agent 怎么违规、找了什么借口 |
| GREEN | 写一个只修这些失败的最小 Skill，不为假想情况加内容 |
| REFACTOR | 找新的借口，补反驳、补红旗、更新触发描述，再测 |

压力分七类：时间、沉没成本、权威、经济、疲劳、社交、「务实 vs 教条」，最好组合 3 种以上。铁律是「没有失败测试先行，就没有技能」，对新建和修改都适用。一个 Skill 算「防弹」的标志：Agent 在最大压力下仍选对，并引用 Skill 的章节作为理由，承认诱惑但仍然遵守。

### 5. Skill 的写法约定

- frontmatter：`name`、`description`、`when_to_use`（以 "when" 开头、写具体症状）等；正文顺序 Overview → When to Use → Core Pattern → Quick Reference → Implementation → Common Mistakes。
- 四种类型：Technique（有步骤的方法）、Pattern（思考方式）、Reference（API / 语法速查）、Discipline（强制纪律，如 TDD）。纪律型用刚性规则，模式型用灵活原则，Skill 自己声明是哪种。
- 可发现性（CSO，Claude 搜索优化）：关键词覆盖错误信息、症状、同义词；命名动词优先（`creating-skills` 而不是 `skill-creation`）；控制字数（入门工作流 <150 词，频繁加载的 <200 词，其他 <500 词）；交叉引用写路径，不用 `@`，避免被强制加载。
- 组合优于重复：用路径引用其他技能，而不是复制内容。

## 怎么用

- **适合谁**：希望 Agent 默认遵循完整工程流程的人。想自己掌控流程、按任务挑工具的人，更适合 mattpocock/skills 这类可自由组合的工具箱。
- **什么时候不值得做成 Skill**：一次性方案、别处已有良好文档的标准做法、项目特定约定（放 CLAUDE.md）。
- **TDD 门槛按类型调**：铁律对个人或小团队可能过重，导致技能库长期为空。务实的做法是纪律型严格走 TDD，查阅型和模式型降低门槛。
- **反驳表需要持续迭代**：它的有效性取决于能否预测 Agent 的借口，出现表里没有的新借口就会失效。
- **注意触发范围**：几乎任何编码任务都会触发完整链式流程（所谓「1% 规则」），小改动时会显得过重。
- **和 ECC（Everything Claude Code）的关系**：Superpowers 没有记忆、没有安全扫描、没有专门的 Token 优化，只支持 Claude Code；ECC 在这些方面更强，但编排是灵活分派。两者都想当总指挥，同时装会冲突；以 Superpowers 为主干、选择性吸收 ECC 独有能力是一种可行组合。
