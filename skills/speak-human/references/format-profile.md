# 用户确认的格式偏好

本技能采用经使用者确认的结构偏好：格式是重点，措辞只作必要调整。下文完整说明排版规则，使用时无需读取原始聊天或截图。

## 按这个层级组织

1. **一级编号是主干。** 用 `1.`、`2.`、`3.` 承载主要事项或论点。它们可以是并列主题，不擅自解读成执行步骤或优先级。点数跟内容走。
2. **点首提炼主题，解释接着写。** 可用“**前置依赖：**解释”这样的短标签，也可加粗一个完整判断；读者只看点首就知道各点在说什么。主题必须有实际区分作用，避免“效率提升：提高效率”式重复。
3. **二级圆点放从属补充。** 例外、适用范围、补充规则和注意事项放在所属主项下面，不与主干混为同级。一般最多两层；没有补充就不加子项。
4. **加粗落在关键信息上。** 除点首外，可强调段内真正影响理解的词句，例如独立发布、需同时满足、暂不包含、仅支持。保留完整条件和否定，不把整段涂成粗体。
5. **每点允许有完整解释。** 不把每句话都拆成圆点，也不把一段内容压成只有标题的提纲。短枚举可放在句内，长枚举才拆成子项。

## 控制整体版式

- 工作同步可先用一句话交代事项和上下文，再进入编号。原文已有的称呼、提及和链接按需要保留；没有就不凭空补上。
- 以编号承担结构，短消息通常不需要再套多级 Markdown 标题，也不强制加总结段。
- 有排期时，把事项、负责人和时间放在一起；多条排期可成为同一主项下的圆点。缺少负责人或日期时不补造。
- 同一主项的续行及子项正确缩进，列表前留空行。下例中的空行和缩进是排版的一部分。
- 优先复现层级与强调。截图里的编号颜色、字号和缩进线来自聊天客户端，不靠特殊字符或 HTML 强行模拟。
- 用户明确要保留原格式、只写一句话、保留表格或代码时，遵从当次要求。

## 格式示意

下面是虚构的排版示意，用来展示层级，不作为改写时新增业务内容的来源。

```markdown
同步下本次对齐的范围和安排。

1. **本次范围：**先支持创建和编辑，暂不包含批量导入。
2. **发布规则：**预览和正式发布需要**分别确认**。
   - 可以只生成预览，不正式发布。
   - 两个版本无需保持一致。
3. **研发安排：**创建模块周二提测，编辑模块周四提测；走查时间还没确定。
```

模仿的是“主干—解释—补充”的关系与局部强调，不要求每次都写开场、三个主项、同样的标签或同样的口头禅。措辞默认保留原文语气，只修不顺、冗余或影响理解的地方。
