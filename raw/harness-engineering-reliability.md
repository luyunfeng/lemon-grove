# Harness Engineering：把可靠性问题变成系统设计问题

## 核心观点

- AI 写代码是否可靠，关键不只在模型本身，而在于有没有一个足够强的验证、反馈和修复闭环。

## 记录到的判断

- Kiro 更强调流程约束，优先解决“做什么”和“怎么做”的对齐问题。
- Claude Code 更强调执行自治，让模型自己拆解、实现和推进。
- 两者都重要，但单独看都没有完整回答“AI 写完后怎么确认它真的写对了”。
- Harness Engineering 把注意力从“怎么驱动模型”转向“怎么设计环境”：人类负责明确意图、设计工具链、反馈回路与验收机制。

## 我的理解

- 可以把 Kiro、Claude Code、Harness Engineering 理解为分别强调约束、自治和验证。
- 如果只强调流程，不解决反馈闭环，AI 可能只是“按流程稳定地产出错误”。
- 如果只强调自治，不提供可验证环境，执行效率再高也很难转化成可靠交付。
- 对团队来说，最值得先建设的通常是验收标准、自动化测试和可观测性。

## 图里这版更好懂的说法

> Harness Engineering 不是单纯“让模型更会写”，而是给 AI 配一整套外层驾驶系统，让人类工程师从亲自开车，变成设计路线、分派任务、检查结果的人。

### 一个直觉类比

- 过去的软件工程更像“出租车司机自己开车”：人、车、路线、验票都由同一个人包办。
- Harness Engineering 更像“车队调度公司”：先把人和车拆开，再用调度、监控、验收把流程组织起来。
- 这意味着工程师不再主要负责逐行写代码，而是负责设计 AI 能安全工作的外部环境。

### 图中的关键零件

- `人类工程师`：提出意图和约束。
- `任务规划器`：把大任务拆成可并行的小任务。
- `Agent 实例 A/B/C`：各自独立完成子任务。
- `自动验证`：编译、测试、lint、安全扫描，负责把错误尽早拦住。
- `人类审阅`：合并、打回、修正方向。
- `反馈回环`：失败结果回到上游，推动下一轮改进。

### 这张图想表达的核心

- Harness 的重点不是单个 Agent 有多强，而是整个系统能否把多个 Agent 组织成一个可靠的生产流水线。
- 真正的价值在于把“写得对不对”从主观判断变成可自动验证、可回归、可迭代的工程过程。
