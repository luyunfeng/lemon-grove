# 软件工程的终结

论文：The End of Software Engineering: How AI Agents Are Fundamentally Restructuring the Software Paradigm  
作者：Zhenfeng Cao | arXiv:2606.05608v1 | 2026年6月4日 

**核心论点** — AI Agent 的出现不是渐进改进，而是对软件工程范式的**根本性重构** 。传统软件中"代码是决策逻辑的载体"，Agent 系统中"代码是 LLM 推理循环的短暂工具"。软件工程的核心能力正从"写出好代码"转向"设计可靠的推理约束边界"。 

## 一、范式转变：从固化逻辑到动态推理

传统软件范式

#### 决策逻辑被「提前写死」

人类工程师分解问题，将判断逻辑编码为静态代码——if-else、状态机、算法。所有决策逻辑必须在系统遇到任何输入之前，由人类显式编写。

→

Agent 范式

#### 决策在运行时动态生成

LLM 作为主要推理引擎，动态生成并丢弃代码。代码不是系统本身，而是临时产物——"用完即扔的工具"。决策逻辑在运行时由推理循环产生。

> "The agentic paradigm dissolves the very premise on which software engineering was founded." — Zhenfeng Cao, 论文引言

### 形式化定义对比

维度 | 传统软件系统 S = (C, D, E) | Agent 系统 A = (M, 𝒯, ℳ, Π)  
---|---|---  
核心引擎 | 静态代码 C | 大语言模型 M  
决策机制 | 预设计逻辑 D（静态） | 运行时生成推理（动态）  
代码角色 | 决策逻辑的载体 | 短暂工具性资源  
演化方式 | 人工重构 | 自修改 / 自补丁  
复杂度上限 | 人类认知 O(1) | 模型能力（持续增长）  
  
★

**复杂性定律** ：n 个组件的可能交互路径 P(n) ∈ Θ(2ⁿ)。人类认知能力"基本恒定"，与指数级增长的复杂度之间存在结构性错配——这是软件项目边际生产力递减的深层原因。

## 二、复杂性转移：从本地软件到 AaaS

论文提出了软件交付的三代演进，每次都将复杂性从终端用户向更擅长处理它的主体转移：

代际 | 核心机制 | 复杂度承担者 | 收入模式  
---|---|---|---  
Software 1.0（本地） | 代码在本地执行 | 终端用户 | 许可证销售  
Software 2.0（SaaS） | 代码在云端执行 | 供应商 | 订阅制  
Software 3.0（AaaS） | Agent 自主运行 | **Agent 本身** | **按结果付费**  
  
> "The party best positioned to absorb complexity absorbs it." — 论文 3.1 节

### "AI → Software → Result" 为什么失败

1 · 瓶颈持续存在 结构性弱点

人类仍然是关键路径。AI 辅助写代码，但设计、审查、部署、维护仍依赖人类工程师。效率提升有限，因为瓶颈在人。

2 · 复杂度天花板未破 结构性弱点

最终交付物仍是传统软件。代码库随时间膨胀，技术债务累积，人类认知上限决定了系统复杂度的上限。

3 · 迭代延迟 结构性弱点

任何变更都需要完整的人类协调链：需求 → 设计 → 编码 → 测试 → 部署。Agent 范式下，意图直接映射为结果，消除中间层。

## 三、Agentic Engineering：一门新学科

论文明确提出"Agentic Engineering"作为区别于传统软件工程的独立学科，具有不同的研究对象、控制模型和人类角色。

维度 | 传统软件工程 | Agentic Engineering  
---|---|---  
核心产物 | 源代码（静态） | Agent 系统（动态）  
控制中心 | 人类工程师 | LLM 推理引擎  
开发周期 | 线性：设计→编码→测试 | 自主迭代循环  
人类角色 | 代码作者 | 意图架构师、协调员、审计员  
输出单位 | 可运行软件 | 交付的结果  
  
### 人类的新差异化能力

  * **意图表达** — "以足够的清晰度和约束条件定义目标"
  * **架构监督** — "多个 Agent 如何协调"
  * **质量校准** — "定义'好'的标准是什么"
  * **伦理治理** — "确保 Agent 行为与组织价值观一致"

> "The productivity multiplier for those who master agent orchestration will far exceed the traditional '10x engineer' benchmark—not through faster typing, but through the ability to coordinate swarms of agents." — 论文 4.3 节

## 四、四阶段演进路线图

2023–2025

Stage I

#### 工具增强（Tool-Augmented）

代码补全、单行修复。人类是作者+审查者。代表：GitHub Copilot, Claude Code。

2025–2027

Stage II

#### 单任务自主（Single-Task Autonomous）

端到端功能构建。人类是意图架构师+审计员。代表：Devin, OpenHands。

2026–2029

Stage III

#### 多 Agent 团队（Multi-Agent Teams）

协调 Agent 群，覆盖完整生命周期。人类是 PM+架构师+审计员。代表：LangChain, MetaGPT。

2028+

Stage IV

#### 自进化生态（Self-Evolving Ecosystems）

自主发现、自适应。人类是目标设定者+伦理治理者。"软件"与"Agent"的界限完全消融。

### 四大核心挑战

挑战 | 描述  
---|---  
上下文漂移 | Agent 失去对系统级不变量的连贯理解  
错误传播 | 前期错误在后续工作中复合放大  
技术债务意识缺失 | 为完成当前任务优化，不考虑可维护性  
验证保真度不足 | 通过测试的同时引入微妙的语义错误  
  
> "The >80% to <38% gap quantifies the distance between current agent capability and the threshold for fully autonomous software engineering." — 论文 5.3 节

★

**关键判断** ：Agentic Engineering 作为"增强范式"今天已经真实且变革性，但完全自主开发"仍是一个多年的研究挑战"。

## 六、我的理解

### 这个范式转变意味着什么？

这篇论文最触动我的不是"AI 会取代程序员"的焦虑，而是对**软件本质** 的重新定义。以下是几点思考：

  * **代码地位的根本下降** ：以前代码是资产，现在代码是耗材。可维护性、代码质量的传统指标可能不再适用——如果代码只存在几分钟，"干净代码"的意义是什么？
  * **推理边界比代码更重要** ：当 Agent 可以生成任意代码时，真正有价值的是**约束** ——什么不能做、什么必须做、什么优先级更高。这类似于从"写程序"到"写规范"的转变。
  * **验证成为核心瓶颈** ：生成代码容易，验证正确性难。EvoClaw 悬崖告诉我们，Agent 在孤立任务上表现很好，但在连续、开放场景中迅速退化。这意味着"测试和验证"将成为新的核心竞争力。
  * **组织形态会改变** ：论文提到"更小的 Agent 协调者团队可能取代更大的开发者团队"。这不是简单的裁员，而是角色重构——从"写代码的人"变成"设计意图和约束的人"。

## 七、开放问题

### 值得继续探索的问题

1\. 推理边界的"编程语言"是什么？
    如果未来工程师的主要工作是设计约束边界，那么描述这些边界的"语言"会是什么？是形式化规范（如 TLA+）、自然语言提示工程，还是某种新的 DSL？
2\. 技术债务在 Agent 范式下如何定义？
    如果代码是临时的，传统意义上的技术债务（代码腐化）可能消失。但 Agent 的"推理债务"——错误假设、偏差累积、上下文污染——可能成为新的债务形式。如何度量和管理？
3\. 从 >80% 到 <38% 的 gap 如何弥合？
    EvoClaw 悬崖揭示了 Agent 在连续场景中的脆弱性。是等待模型能力自然提升，还是需要新的架构范式（如更强的记忆机制、自我验证循环、人机协作框架）？
4\. "按结果付费"的经济模型可行吗？
    AaaS 的收入模式是"按结果付费"，但如何定义和验证"结果"？如果 Agent 交付了功能但引入了安全漏洞，责任如何划分？
5\. 这对软件教育意味着什么？
    如果"写出好代码"不再是核心能力，计算机科学教育应该如何调整？应该加强哪些能力（形式化思维、系统架构、伦理判断），弱化哪些能力（语法细节、调试技巧）？

这些问题没有标准答案，值得持续跟踪和讨论。

★

**论文结语** ："The old software engineering is ending; the new one has already begun." 这不是末日预言，而是范式转换的宣言。
