# Affaan Mustafa：Agentic Engineering 精华笔记

> **演讲者**：Affaan Mustafa（Anthropic Hackathon 冠军、Everything Claude Code 作者、AgentShield 创始人）
> **活动**：公司内部技术论坛特邀分享 · 2026.5.29 深圳

---

## 1. 核心观点

AI 编程的下一波跃迁**不在模型本身**，而在 Agent 周围的"操作系统层"（Harness）。

当模型已能写出 80 分代码后，真正决定 Agent 是否"可用"的是：

- **Skill（技能）**：可被复用、可被验证的行为单元
- **Memory（记忆）**：跨会话、跨任务的长期上下文
- **权限 & 预算门控**：哪些事 Agent 可以自己做，哪些必须人类点头
- **评审门禁**：PR 进主干前必须通过的"红绿灯"
- **安全检查**：AgentShield 等安全层
- **证据链（Evidence）**：Agent 说自己做完了——拿什么证明？

> **关键判断**：单个工程师层面，AI 编程工具已经显著提效；但在大型组织中，真正的核心已经从"模型会不会写代码"变成 **"组织有没有能力治理这些代码"**——边界、可评审产出、安全回执、成本预算控制，缺一不可。

## 2. AI 编程四阶段

| 阶段 | 形态 | 人类参与度 |
|------|------|-----------|
| 1 | 自动补全（Copilot） | 人类承担 100% 决策 |
| 2 | 对话式代码助手 | 模型在工作流之外 |
| 3 | 仓库级智能体 | 人进入 Reviewer 角色 |
| 4 | **自主协作团队** | 人主导意图，Agent 执行 |

我们正处于 **Phase 4 早期**：多 Agent 分工协作，HITL（人类在环）逐渐淡出。

## 3. Harness vs MetaHarness

### Harness（单 Agent 外壳）

套在单个 Agent 身上的"操作外壳"，包含：

- Skill / Rule / Hook / Memory / Eval
- 权限、预算、审批、护栏
- 可评审的 diff、测试、发布证据

> **PPT 原话**："A harness runs one agent loop."

### MetaHarness（集群操作系统）

管理"一整批 Agent"的统一层，解决：

- 不同团队用不同 Agent（Claude Code / Cursor / Codex / OpenCode）
- 切换模型时行为偏离
- 切换代码库时重新配置
- 跨团队协作"鸡同鸭讲"

> **PPT 原话**："A meta harness governs many harnesses."
> **核心洞察**：如果 runtime 层不断变化，那持久的机会就在 **behavior 层**。

## 4. ECC（Everything Claude Code）

### 4.1 本质

ECC **不是 prompt 合集**，而是对 **上下文 + 运行规则** 的统一封装。

把团队中反复要解释的事情（编码风格、测试规则、回滚机制、依赖识别）抽到共享行为层。

### 4.2 五个核心原语

| 原语 | 作用 | 区别 |
|------|------|------|
| **Skill** | 告诉 Agent "好的工作长什么样" | 按需触发，可链式调用 |
| **Rule** | 保持稳定："永远遵循 X" | 持久化，Agent 必须吸收 |
| **Hook** | 运行时强制执行 | 强制触发，不依赖 LLM 判断 |
| **Memory** | 总结先前决策 | 跨会话恢复上下文 |
| **Eval** | 测试、冒烟检查、证据 | 质量门禁 |

### 4.3 "300% 效率提升"

来源不是模型变聪明，而是三件事：

**🔁 把"耐用行为"放进共享层**
- Skill / Rule / Memory 在一个地方维护
- 通过适配器与本地工具映射，不绑死任何一个 Agent
- 不同团队在相同上下文之间迁移，几乎无缝

**✅ 把"安全 & 可回滚"刻进流水线**
- 自动识别依赖、拆分安全包
- 每个 PR 都强制带测试和回滚机制
- 通过 AgentShield 这样的安全层做兜底

**📊 把质量门禁前移**
- linting、测试、安全审查提前
- 多 Agent 在明确标准下并行

> 注意：300% 是平均值。10x 工程师提升更 exponential，1x 更 logarithmic。Agentic 工具会**拉大差距**。

### 4.4 ECC 实际使用链路

- **链式 Code Review Agent**：在 PR 上反复对话产出深度审查意见
- **扫描可视化日志**：ECC 工具对扫描过程的可视化日志
- **输出基准化**：把任意 Skill 的输出当作"基准"，下一次执行直接拿来回归测试

## 5. AgentShield 安全

### 5.1 Agent 时代的五类风险

| 风险 | 典型场景 | 级别 |
|------|---------|------|
| Prompt / Tool 注入 | README、工单诱导 Agent 执行异常；连接工具时缺乏所有者校验导致权限拓展 | 高 |
| MCP / Plugin 漂移 | 社区插件缺乏所有者校验扩展权限 | 高 |
| 敏感密钥泄露 | 工作流中夹带的私密数据被外发 | 高 |
| 包管理风险 | install / build 时被注入恶意包 | 中 |
| 无限制执行 | 创建工单、调用付费接口、触发部署——背后是真实账单 | 中 |
| 虚假安全感知 | 扫描误报导致"狼来了"；过度信任扫描结果反而忽视真问题 | 低 |

### 5.2 AgentShield 扫描范围（PPT 原文）

> "AgentShield scans agent configuration, MCP servers, hooks, package-manager risk, prompt injection patterns, and policy promotion evidence."

### 5.3 应对原则

- **危险动作必须获批** —— 只读分析与写操作分离
- **最小工具 + 最小权限** —— 按需授予，并限制网络访问
- **全量记录 + 可审查证据** —— MCP Server、插件、Hook、Skill 都视为"外部部分"，做内外隔离，留下安全团队可以审的证据链
- **Red Team / Blue Team 演练** —— 主动找漏洞，比被动报警更有效

安全循环：`Scan → Classify → Route → Gate → Report`

## 6. Hackathon 实战要点

- **Scope 管理至上**："做不做"比"怎么做"重要十倍
- **任务拆分要清晰**：拆不到点上，多 Agent 只是相互干扰
- **Artifact 必须可见、可验证**：没有证据，就没法判断系统到底"行不行"
- **安全内建于整个流程**，不是最后补丁
- **小团队明确分工**：一人负责 Agent 与 runtime，一人负责其他，彻底避免"等待"

> "最强的系统，不是写代码最强的那个 Agent，而是能从每个任务安全学习的系统。"

### 6.1 设计反哺

这套经验后来直接反哺了 ECC 的设计：**生态分层（runtime / IDE / Skill 层 / 评测层）+ 行为层封装 + 持续验证闭环**——本质上都是"用工程纪律约束 Agent"。

## 7. 企业级 Agent 团队演进

### 四阶段路径

```
Stage 1: 咨询 & 只读（代码库检查、事件总结）
   ↓
Stage 2: 有界写入（可开 PR、必须附带测试和证据）
   ↓
Stage 3: 专用工作流（依赖升级、测试改进、安全审查）
   ↓
Stage 4: Agent 团队（Planner + Builder + Reviewer + Security + Release）
```

### 避免两个错误

- **欠采纳**：只把 AI 当本地聊天助手
- **过度自治**：给 Agent 广泛权限前组织还没准备好

### Agent 角色分工

| 角色 | 职责 |
|------|------|
| Planner | 意图 → 任务图，拆分通道、预算、依赖 |
| Builder | 并行执行，worktree 中实现变更 |
| Reviewer | 检查正确性、回归、边界情况 |
| Security | 供应链风险、密钥暴露、MCP 风险 |
| Release | 组装证据、发布说明、截图、审批 |

## 9. FAQ 精华

**Q：如何让 Agent Team 更有效？**
> 1. 让 Agent 与系统做映射，消除假设
> 2. 使用任务图（Task Graph），Reviewer 修剪
> 3. 每个产物落到可验证的 artifact

**Q：怎么构建 Codebase 的 Spec / Memory，让 Agent 给出有效的业务级 CR？**
> 1. Code 的 Memory 应当是分层的，捕捉**不变的领域概念**
> 2. 不只关注"代码好不好"，还要关注**边界违规**和**系统依赖**
> 3. CR 说明必须基于 Spec
> 4. 不要做"通用 CR Agent"，要做**专注于具体方向**的 CR Agent（安全、性能、领域规则等）

**Q：模型未来是否不需要 Harness？**
> Harness 不会消失，而是转向：
> - Email / Policy / Permission 的精细化管理
> - **观测性 (Observability)** 成为更核心的能力
> - 整体层次复杂性会下降，但**单层的工作会更复杂**
> 
> 一句话：**不是 Harness 消失，而是 Harness 的形态变了。**

**Q：上下文超过 200K 后掉点怎么办？**
> 1. 关键不在于压缩上下文，而在于**长期记忆 (Long-term Memory)**
> 2. 部分公司宣称的大窗口**有较强的营销成分**，且费用大幅上涨
> 3. 工程实践：保持代码库精简、创建 Code Map、及时更新地图并修剪 Memory、通过 Hook 限制只读上一个 Skill 输出

**Q：从简单 Demo 到复杂业务系统，应用 Agent 的方式有何不同？**
> 1. 复杂系统**反而更需要减少假设、提供更多上下文**
> 2. **不要试图一次性大改大动**
> 3. 推荐路径：**小补丁 → 测试 → 不断迭代**，让 Agent 始终在"可控可回滚"的范围内推进

**Q：ECC 同时支持多个 Agent，新增/剔除 Skills 时如何维护？**
> 1. 本地 Adapter 设计上是轻量的，通常一两次 PR 就能解决
> 2. Skill 增删的影响主要落在**适配器层而不是核心层**
> 3. 保证质量的关键：Skill 的**可重复性 + 输出基准化**——把每次输出当作回归用例

**Q：学 Agent 的最好方式？**
> "最好的方式就是自己动手做。哪怕做出来的东西没用。" **基于开源系统从头构建**（不要从 fork 开始），让自己在重新理解中长出对系统的直觉。

**Q：AI 产出太多，人类被淹没？**
> 人类审阅从"写每个补丁"转为"接受证据"。设定自动接受标准，只有关键区域才提交人工。

---

## 10. 关键 Takeaway

1. **Agent 能力上升时，价值从"模型会不会写代码"转向"组织能不能治理 Agentic Work"**
2. **Harness 是引擎，MetaHarness 是舰队操作系统**
3. **ECC 不是 prompt 包，是给 Agent 的 "durable shape"**
4. **安全是设计阶段的事**，内置到 Harness
5. **企业采用分四阶段**，避免欠采纳和过度自治
6. **每个任务都应改进操作系统层**：struggled with context → improve memory；repeated mistake → turn into rule

> **Winning 系统不是写代码最多的 Agent，而是能从每个任务安全学习的系统。**
