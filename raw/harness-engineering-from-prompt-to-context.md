# Harness Engineering 学习笔记：从 Prompt Engineering 到 Context Engineering

## 摘要

- Prompt Engineering 解决的是单次交互里“我该怎么问”。
- 当任务从一次问答演变成多步骤、跨工具、带状态的复杂系统时，Prompt Engineering 会因为复杂度膨胀、工具约束丢失和上下文静态化而迅速失效。
- Context Engineering 进一步回答“系统该在什么上下文里让模型工作”，重点从措辞优化转向上下文供给。
- Harness Engineering 则更进一步，把注意力从“怎么问模型”推进到“怎么设计一整套让模型稳定工作的外部系统”。

## 一句话总结

Harness Engineering 不是研究“怎么把 prompt 写得更好”，而是研究怎么给大模型套上一整套可观测、可验证、可纠偏的外部控制系统。

它把模型当成一个会漂移、会犯错、会自我高估的概率系统，不再指望模型一次就答对，而是通过上下文供给、规则约束、工具执行、状态管理和反馈回路，让系统在长时间运行中持续逼近正确结果。

如果说 Prompt Engineering 解决的是“我该怎么问”，Context Engineering 解决的是“模型该知道什么”，那么 Harness Engineering 解决的就是：`当模型做偏了之后，系统怎样把它拉回来。`

## 1. Prompt Engineering 解决了什么问题

Prompt Engineering 解决的核心问题是：`我该怎么问，模型才更容易给出我想要的回答？`

在大型语言模型刚开始被广泛使用时，它几乎是开发者和模型交互的主要手段。这个阶段里，开发者主要通过调整提示词的表达方式来影响输出质量，比如：

- 用 few-shot 示例告诉模型“像这样回答”
- 用 Chain-of-Thought 引导模型展开推理
- 用角色设定稳定语气、身份和输出风格

它本质上优化的是单次交互中，人类对模型的表达方式。

> [!note]
> 如果把模型看成一个能力很强但上下文极度有限的执行者，那么 Prompt Engineering 更像是在研究“怎样把一句话说得足够清楚”。

## 2. 为什么 Prompt Engineering 在复杂系统里会失效

Prompt Engineering 在简单任务里很有效，但在复杂系统里会逐步显露边界。

### 2.1 复杂度无法承载

当任务链条变长后，开发者往往会不断往提示词里塞入：

- 异常处理逻辑
- 背景设定
- 输出格式要求
- 工具使用规范
- 各种“如果发生 X，就执行 Y”的补丁规则

结果是提示词迅速膨胀，最后变成一个庞大、脆弱、难维护的文本系统。它不再像一个清晰的指令，更像一个不断打补丁的脚本。

### 2.2 工具规则被上下文噪音淹没

在复杂 Agent 系统里，模型不仅要“回答”，还要：

- 选择正确的工具
- 生成符合约束的参数
- 在正确的时机调用外部能力

但当提示词过长、内容过杂时，这些真正关键的工具调用规则很容易被淹没在大量背景文本中，导致模型：

- 调错工具
- 传错参数
- 搞错调用顺序
- 输出看起来合理、实际却无法执行的格式

这说明问题已经不只是“提示词写得不够好”，而是系统把关键约束和噪音混在了一起。

### 2.3 静态提示无法提供实时上下文

更严重的问题是，静态提示词无法实时注入很多复杂系统真正依赖的信息，例如：

- 微服务当前状态
- 用户历史交互轨迹
- 会话专属记忆
- 工具返回结果的中间状态
- 当前任务所处的执行阶段

一旦这些信息缺席，模型就只能在信息盲区里基于概率继续猜。所谓的 Hallucination，很多时候并不只是模型“胡说八道”，而是系统没有把模型完成任务所需的上下文及时、准确地给到它。

## 3. Context Engineering 补上了什么

为了克服静态提示词的局限，行业重心开始从 Prompt Engineering 转向 Context Engineering。

如果说 Prompt Engineering 主要在优化“怎么表达”，那么 Context Engineering 更像是把问题升级为：

`模型在完成当前任务时，到底需要知道什么？`

它把大语言模型的上下文窗口视为一种稀缺且极其有限的计算资源，并对这份资源进行动态、系统化管理。

从这个角度看，Context Engineering 不是单纯把 prompt 写得更长，而是在重构“信息喂给模型”的装配流水线。它真正关心的是：

- 系统应该给模型提供哪些上下文
- 这些上下文应该在什么时机被注入
- 哪些信息应该被保留、裁剪、压缩或重写
- 如何让模型在每一步都处于尽可能“信息充分”的状态
- 这些信息应该如何被结构化地组织和呈现

它不再把提示词看成唯一控制面，而是把模型执行质量理解为一个上下文供给问题。

> [!info]
> 一个很有代表性的行业判断是：很多 AI Agent 的失败，本质上不是模型能力不够，而是上下文供给失败。这个判断也推动了行业重心从 Prompt Engineering 进一步转向 Context Engineering。

有一种很清楚的表述方式是：Context Engineering 的目标，是以正确的格式提供正确的信息和工具，使模型能够完成仅靠提示词本身难以完成的复杂任务。

从这个角度看，Context Engineering 已经不只是“写 prompt 的升级版”，而是在重新定义 Agent 系统的输入层。

### 3.1 一个很典型的例子：Anthropic 的 Agent Skills

Anthropic 的 Claude Agent Skills 可以看作 Context Engineering 的一个教科书级案例。它背后的关键机制可以概括为：`渐进式披露（Progressive Disclosure）`。

它的核心思想不是在系统启动时把所有知识、规则、脚本和说明一次性塞进上下文，而是把信息拆成不同层级，按需加载。

#### Level 1：元数据

- 启动时加载
- 每个 Skill 只占很少的 token
- 只包含名称和用途描述

这一层的目的，是让模型先“知道有什么能力存在、什么时候应该调用”，而不是立刻读完全部细节。

#### Level 2：指令

- 在 Skill 被触发时加载
- 通常是面向执行的说明文档
- 告诉模型应该遵循什么流程、注意什么约束

这一层解决的是“既然决定要用这个 Skill，那具体该怎么做”。

#### Level 3：资源和代码

- 只在真正需要时才按需读取或执行
- 可以是脚本、资源文件、模板、附加文档
- 真正进入上下文的，往往只是执行结果，而不是完整代码本身

这一层的价值在于，把大量高 token 成本的材料留在上下文之外，只有在必要时才通过工具链接入，从而避免一开始就把上下文窗口挤爆。

> [!note]
> 这个例子很能说明 Context Engineering 的本质：不是把所有信息都给模型，而是让模型在恰当的时机只看到当下最需要的信息。

### 3.2 一个很关键的设计思想

这类系统背后的核心设计思想可以概括成一句话：

`只有当前步骤真正相关的上下文才占用上下文窗口，其余信息留在外部系统中，等待按需调取。`

这里的“外部系统”可以是很多东西，比如：

- 文件系统
- 脚本和工具
- 检索系统
- 记忆存储
- 服务接口和运行时状态

这意味着一个成熟的 Agent 系统，并不会试图在一开始就把所有知识一次性塞进模型，而是把大部分信息保留在上下文窗口之外，只在必要时通过工具、读取、检索和执行把它们重新接进来。

这也解释了为什么很多 CLI 形态的 Agent 工具会突然变得非常有吸引力。CLI 天然具备几个和 Context Engineering 高度契合的特征：

- 它可以把大量信息保留在文件和目录中，而不是硬塞进 prompt
- 它擅长按需读取、搜索、过滤和执行
- 它可以把脚本、命令、工具结果和工作区状态接到模型面前
- 它让“上下文在外部、按需进入窗口”这件事变得非常自然

> [!warning]
> 更稳妥的说法是：这不是 CLI 类工具流行的唯一原因，但它很可能是一个重要原因。CLI 的走红还和工程师习惯、工具可组合性、自动化能力、可审计性和低界面成本有关。

### 3.3 Context Engineering 的天花板

这些实践都是真实有效的。无论是渐进式披露、KV cache 优化、工具掩码，还是文件系统记忆，它们都明显提升了模型在复杂任务中的表现。

但它们本质上都在回答同一个问题：

`如何让模型在这一次推理中，获得更好的上下文？`

换句话说，Context Engineering 优化的主要还是输入端。它背后的核心假设是：

> 如果模型看到了正确的信息、用了正确的工具，并且在一个足够合适的上下文窗口中完成推理，那么输出大概率会更好。

这个假设在单次推理里通常成立，但当系统进入长时运行状态后，问题就开始变了。

在一个需要持续运行数小时、数天甚至数周的代理系统里，即使每一次推理的上下文都已经尽量做到“最优”，你依然无法保证这个概率系统不会：

- 逐步发生漂移
- 累积错误模式
- 在无人值守时悄悄退化
- 在多轮任务链条里把局部偏差放大成系统性问题

这正是 Context Engineering 的天花板所在。它可以极大提升某一次推理的质量，却不能天然保证一个长期运行系统的稳定性。

从更底层的角度看，Context Engineering 虽然已经拥有了：

- 更强的信息供给能力
- 更复杂的检索与记忆网络
- 更丰富的外部工具体系
- 更严格的格式与约束机制

但它仍然很难对模型生成过程中出现的瞬时误差做出实时反应。也就是说，它擅长把模型送进一个更好的起跑位置，却不天然负责在模型跑偏之后把它拉回来。

于是，一个更关键的问题出现了：

`如果输出已经偏了，怎么办？`

这正是 Context Engineering 没有彻底回答，而 Harness Engineering 开始接手的地方。

## 4. Harness Engineering 要解决的到底是什么问题

如果 Prompt Engineering 回答的是“怎么问”，Context Engineering 回答的是“给什么上下文”，那么 Harness Engineering 更接近在回答：

`怎么把模型放进一个可验证、可反馈、可纠偏的工程系统里？`

它关心的不只是模型眼前看到了什么，还关心：

- 任务怎么拆解
- 工具怎么被封装和约束
- 执行结果如何验证
- 失败后如何反馈回系统
- 多个 Agent 如何协作而不是互相放大错误

换句话说，Harness Engineering 研究的是模型外层的“驾驶系统”。

在这个框架里，模型只是系统中的一个组件，而不是全部。真正决定可靠性的，不只是模型能不能生成答案，而是系统能不能：

- 让它在正确的边界里工作
- 尽早发现错误
- 把错误转化成反馈
- 让下一轮执行比上一轮更接近正确结果

这也是为什么 Harness Engineering 更像是在讨论 `可靠性架构`，而不仅仅是提示词技巧或上下文拼装。

### 4.1 Harness Engineering 为什么会出现

要真正理解 Harness Engineering 为什么会崛起，思考方式需要发生一个很大的切换。

传统软件工程建立在低熵、确定性的世界观之上。无论是：

- 编译器对语法树的解析
- 关系型数据库对事务的一致性处理
- 工业控制系统对运动方程的执行

它们都默认一件事：在给定输入的前提下，系统应该稳定地产生确定输出。理想状态下，输入到输出的映射应当尽可能接近 `P(y|x)=1`。

在这个范式里，模糊性和随机性通常都被当作缺陷。只要出现不可预测行为，我们就会把它视为 bug，并尝试把它消除。

但大语言模型把我们带进了另一种系统类型。基于 Transformer 的模型，本质上不是在执行确定性映射，而是在对下一个 token 或下一个动作进行概率采样。它更接近：

`y ~ P(y|x)`

这意味着，模型输出天然不是一个唯一结果，而是一个概率分布上的采样结果。

如果放任这样的系统自由运行，它就不再像传统程序那样沿着一条严格指定的轨道前进，而更像是在高维语义空间里进行一种有偏的随机漫步。很多局部步骤看起来都“差不多合理”，但长期积累下来就可能逐步偏离目标。

从这个角度看，问题已经不再是“这句 prompt 还能不能再改一改”，而是：

`我们该怎样约束一个概率系统，让它长期表现得像一个可靠系统？`

这也是为什么仅仅优化输入端，无论是 prompt 微调还是更精准的上下文检索，都不可能从根本上解决问题。它们可以提升单步质量，却不能单独对抗长期运行中的偏移、累积误差和行为退化。

真正可行的工程方向，是把这类系统放进一个闭环控制架构里。

> [!note]
> 用控制理论的语言说，Harness Engineering 的意义在于：不仅要给系统输入目标和信息，还要持续观测输出、检测偏差，并通过反馈把系统重新拉回目标轨道。

也因此，Harness Engineering 和 Prompt Engineering、Context Engineering 的根本差异不只在“做得更多”，而在于它开始把大模型当作一个需要被持续控制、校正和验证的概率性行为系统，而不是一个只要喂够信息就会自然稳定正确的推理引擎。

### 4.2 从“steer”到控制论

有一句很短的话，几乎可以当作 Harness Engineering 的直觉版定义：

`Humans steer. Agents execute.`

这句话里的 `steer` 很值得玩味。它表面上只是“掌舵、引导”的意思，但如果放回工程史里看，会发现它和控制论有一条很深的暗线。

1948 年，数学家 Norbert Wiener 出版了《Cybernetics》，奠定了控制论的基础。`Cybernetics` 一词来自希腊语中“舵手”的概念，本身就带有“通过反馈进行引导和控制”的意味。

Wiener 的核心洞见可以概括为：复杂系统之所以能够保持稳定，不是因为它们从不出错，而是因为它们拥有持续感知偏差、比较目标、再进行修正的反馈回路。

典型例子包括：

- 恒温器感知温度、对比设定值、调节加热强度
- 人体神经系统感知外界、发出动作、监测效果、持续修正
- 工业控制系统不断比较当前状态与目标状态，并动态调节控制量

Harness Engineering 做的，本质上正是这件事，只不过被控制的对象从传统机器、物理装置和服务器系统，变成了大语言模型驱动的 Agent 系统。

从这个视角看，Harness Engineering 的关键转变在于：它不再幻想只靠一段写得足够好的文本，就能稳定驱动一个高熵概率系统；它开始接受另一件事，那就是模型一定会偏、会漂移、会犯错，而工程系统必须有能力实时发现这些偏差，并把它拉回可接受范围。

所以，Harness Engineering 的核心并不只是“给模型更多上下文”，而是构建一个闭环控制系统。这个系统通常包含：

- 机械性约束：格式约束、接口边界、工具权限、执行规则
- 确定性反馈：测试结果、验证结果、运行状态、审计信号
- 持续状态管理：记忆、阶段信息、任务进度、失败历史

它真正要完成的事，是把高熵、带概率波动的模型输出，强制收敛到一个更稳定、更可验证、更接近正确的状态空间里。

### 4.3 理解 Harness Engineering 需要的最小控制理论

如果要继续往下理解 Harness Engineering，掌握一层最基础的控制理论框架会很有帮助。

一个完整的控制系统，通常可以理解为同时具备四种功能：

- 量测
- 比较
- 计算
- 修正

对应到结构上，它一般由五类核心元素构成：

#### 被控对象（Plant）

需要被调节的系统或过程。  
在传统控制系统里，它可能是蒸汽机、电机、机械臂；在 Harness Engineering 语境里，它更接近由大模型驱动的执行过程本身。

#### 传感器（Sensor）

负责测量系统输出，使系统状态变得可观测。  
在 AI 系统中，这一层常常对应测试结果、运行日志、工具返回值、监控信号、用户反馈等。

#### 控制器（Controller）

接收误差信号，并计算接下来该如何修正。  
它决定系统在发现偏差后，应该重试、回滚、改写上下文、切换工具，还是升级到人工介入。

#### 执行机构（Actuator）

根据控制器发出的指令，对被控对象施加作用。  
在 Agent 系统里，执行机构通常体现为具体的工具调用、脚本执行、任务重跑、参数调整等动作能力。

#### 反馈回路（Feedback Loop）

把系统输出重新送回，与目标进行比较，并据此持续修正。  
这是真正让系统能够“越跑越稳”的核心机制，也是控制理论最关键的部分。

### 4.4 反馈、误差与闭环

控制的核心是负反馈。系统并不假设自己永远正确，而是假设偏差一定会出现，所以必须持续测量偏差并修正偏差。

一个最基本的表达方式是：

`e = r(t) - y(t)`

其中：

- `r(t)` 是目标值或参考值
- `y(t)` 是系统当前输出
- `e` 是误差信号

控制器会根据这个误差信号调整输入 `u`，从而推动系统输出逐步逼近目标值。

放到 Harness Engineering 里，这件事可以理解成：

- 先定义“什么叫做正确”
- 再持续观测“当前结果离正确还有多远”
- 然后通过工具、验证、回退、修复等机制把偏差压回去

也正因为如此，控制论从一开始就不是单纯讨论“命令”，而是在讨论“控制与通信如何通过反馈共同构成稳定性”。

### 4.5 开环与闭环

理解 Harness Engineering 时，另一个非常重要的区分是开环和闭环。

#### 开环控制

- 不使用反馈
- 给出输入后直接执行
- 结构简单
- 成本较低
- 但抗扰动能力很差

如果把很多早期 Prompt Engineering 式工作流看作系统，它们其实很接近开环结构：给模型一个 prompt，模型给出结果，然后流程就结束了，中间缺少持续校正。

#### 闭环控制

- 引入反馈
- 能自动检测偏差
- 能补偿外部干扰和模型误差
- 能在运行过程中持续修正

这也是现代控制系统的主流形式。对应到 AI Agent 领域，Harness Engineering 的关键价值，正是把原本偏开环的模型调用，改造成一个具备观测、比较、修正能力的闭环系统。

## 5. Prompt / Context / Harness 三者关系

可以把三者理解成三个递进层次：

| 层次 | 核心问题 | 关注点 |
| --- | --- | --- |
| Prompt Engineering | 我该怎么问？ | 措辞、示例、推理引导、角色设定 |
| Context Engineering | 系统该提供什么上下文？ | 记忆、检索、状态、裁剪、注入时机 |
| Harness Engineering | 怎样让整套系统稳定地产出可信结果？ | 编排、验证、反馈、约束、协作 |

它们不是互相替代的关系，而更像逐层外扩：

- Prompt Engineering 仍然重要，但更像最内层的人机表达技术
- Context Engineering 解决的是模型“看见什么”
- Harness Engineering 解决的是模型“被怎样组织、约束和验证”

## 6. 用控制论拆解 OpenAI 的 Harness

如果继续沿着控制论的视角往下看，一个很有帮助的总公式是：

`Agent = Model + Harness`

这个公式的意思很直接：一个可用的 Agent，从来不只是模型本身。

其中：

- `Model` 是那个负责处理 token、压缩世界知识、进行模式识别和生成的智能核心
- `Harness` 则是所有“不是模型本身”的东西，包括代码、配置、工具、执行逻辑、状态管理、验证机制、反馈回路和人工接管策略

从这个定义看，Harness 的范畴其实比 Context Engineering 更大。Context Engineering 主要关注模型在某一步应该看到什么，而 Harness 则进一步关心：

- 模型在整个系统里如何被组织
- 模型输出如何被检测和修正
- 外部工具和状态如何被接入
- 系统如何在长期运行中保持稳定

也可以说，Context Engineering 更像是 Harness 内部的一个子问题，而不是它的全部。

### 6.1 被控对象：一个会漂移的概率系统

控制论的起点永远是同一个问题：

`你要控制的对象，到底具有什么样的动力学特性？`

放到 Agent 系统里，被控对象并不是整个产品界面，而是那个持续生成判断、动作和中间结果的模型执行过程本身。

LLM 的一个关键特性是，它天然是概率性的，而不是确定性的。即使给定相同输入，也不一定产出完全相同的结果。更重要的是，它的误差并不是静止的，而会在生成过程中不断传播和累积。

可以这样理解：

- 第一步生成出现一个很小的偏差
- 这个偏差会成为下一步生成的上下文
- 下一步再基于这个已经带偏的上下文继续推进
- 于是局部误差会在多步链条中逐渐放大

这就是为什么模型的漂移问题非常棘手。它不是某一个 token 偶然错了，而是系统可能在不知不觉中滑向一条越来越偏的轨道。

从工程观察上看，这种漂移在代码 Agent 场景里尤其明显。模型会倾向于复制仓库中已经存在的模式，即使这些模式本身并不一致、并不优雅，甚至已经是次优解。短期看，这像是在“贴合代码库风格”；长期看，它可能意味着系统会逐步吸收并强化已有缺陷。

这也是 Harness Engineering 必须出现的一个核心原因：如果被控对象本身就是一个会漂移、会积累误差、会放大局部坏模式的概率系统，那么系统设计就不能只停留在“把输入喂好”，而必须进一步考虑如何持续检测漂移、抑制漂移并纠正漂移。

### 6.2 为什么不能继续靠人兜底

当系统开始表现出漂移时，一个非常自然的早期思路是：先靠人来修正。

例如：

- 人工检查模型产出
- 定期清理低质量结果
- 在关键节点加入人工确认
- 通过人工 review 压住系统退化

这在系统规模还小、运行时间还短的时候确实有效，但它几乎注定无法扩展。

原因也很简单：你不可能用人工去长期对抗一个 `7 x 24` 持续运行的随机过程所带来的熵增。只要系统还在不断生成、不断复制模式、不断引入微小偏差，人力兜底就会越来越像一种高成本、低上限、不可持续的补丁。

从这个角度看，这个问题的真正结论并不是“人不重要”，而是：

> 被控对象本身是不可信的，系统稳定性必须主要来自外部闭环约束，而不能建立在“希望模型自己长期保持正确”这种期待上。

人类当然仍然重要，但在人和系统的关系里，人的角色更应该是设定目标、定义约束、设计反馈和处理升级异常，而不是持续充当一个手工吸收熵增的补丁层。

### 6.3 传感器：让系统的每一层状态都可观测

控制论里有一条非常硬的规律：

`传感器的精度，决定了控制的精度。`

如果你无法测量系统状态，你就几乎不可能真正控制它。

这也带出 Harness Engineering 和 Context Engineering 的一个根本差异。Context Engineering 更关注的是：

`人类想给模型看什么？`

而 Harness Engineering 进一步关心的是：

`模型自己究竟能看见什么？`

这不是措辞差异，而是思维方式的变化。前者仍然更像输入优化；后者则开始真正把系统可观测性当成控制前提。

顺着这个思路，也能解释一个很常见的现象：为什么在 code 领域，大模型通常比在很多别的知识工作领域表现更强？

一个很重要的原因是，代码天然更容易获得高质量反馈：

- 代码可以运行
- 运行结果可以被观测
- 观测结果可以快速回流为修正信号

也就是说，代码场景天生更适合构建闭环。这并不意味着代码领域的任务更简单，而是意味着它更容易把“好坏”从主观判断变成机器可消费的反馈信号。

从这个角度看，许多更难被自动化取代的工作，恰恰不是因为任务本身更高级，而是因为它们更难形成低延迟、高精度、可持续的反馈回路。

OpenAI 这类代码 Agent 系统里，真正厉害的地方，往往不只是模型本身，而是它把传感器工程做得非常细。

#### 1. 运行态可观测

Agent 不只是读代码，还可以直接感知应用运行状态。

例如，为独立工作区配套独立的应用实例和临时可观测性栈，让 Agent 能读取：

- 日志
- 指标
- trace

这样一来，像“服务需要在 800ms 内启动完成”或者“关键链路中不能有超过 2 秒的 span”这类要求，就不再只是模糊期待，而会被转化成 Agent 能直接读取和验证的测量信号。

#### 2. UI 可观测

如果系统能接入浏览器或页面调试协议，Agent 就不只是在操作代码，而是在“看见”界面结果。

它可以感知：

- DOM 快照
- 页面截图
- 页面导航结果
- 交互后的渲染变化

这一步非常关键，因为它把过去主要依赖人眼判断的“UI 对不对”，变成了模型也可以消费的一类反馈信号。

#### 3. 质量趋势可观测

更成熟的系统不会只测量某一次任务是否成功，而会测量质量在时间维度上的变化趋势。

比如：

- 不同产品域的质量评分
- 不同架构层的稳定性趋势
- 某类问题是否在持续反复出现

这类机制的意义在于，它让系统不只看当前结果是否过线，还能看出自己是不是在缓慢退化。

#### 4. 架构知识可观测

还有一类常被忽视的传感器，是结构化架构知识本身。

不是把所有规则堆进一个越来越臃肿的大型 `AGENTS.md`，而是保留一个小而明确的入口文件，把真正的设计文档、架构说明、执行计划和验证状态放进可索引、可更新、可版本化的知识结构里。

这样做有几个好处：

- 不让单个大文档挤占上下文窗口
- 不让“所有东西都重要”最后变成“没有东西真正重要”
- 让知识结构可以按需读取，而不是一次性硬塞
- 让系统性约束具备可维护性和可追踪性

从控制论角度看，这其实也是一种传感器设计。因为它让 Agent 不只是看到眼前的文件内容，还能看到整个系统的结构关系、当前计划状态和可验证边界。

### 6.4 控制器：编码在仓库中的判断标准

在控制论里，控制器的职责是接收误差信号，也就是“目标状态”和“实际状态”之间的偏差，然后据此计算修正指令。

放到 Harness Engineering 里，控制器并不一定是某个单独的程序模块，它很多时候体现为：`编码在仓库中的规则、标准和修正逻辑。`

其中最典型的一类控制器，就是自定义 linter 规则。

普通的 linter 往往只会告诉你“哪里错了”。但在 Harness Engineering 语境里，一个更强的控制器不仅描述错误，还会把修正方向直接注入 Agent 的推理过程。

比如，一条普通的错误信息可能只是：

```text
Error: Circular dependency detected between module A and module B.
```

而更像 Harness Engineering 风格的错误信息会进一步给出结构性修正建议：

```text
Error: Circular dependency detected between module A and module B.
Remediation: In this codebase, dependencies must flow forward through
Types -> Config -> Repo -> Service -> Runtime/UI.

Module A (Service layer) cannot import from Module B (Runtime layer).
Move the shared type to the Types layer, or use the Providers interface
for cross-cutting concerns like auth, connectors, or telemetry.
```

这样的报错，本质上已经不只是错误提示，而是一种控制信号。它同时包含了两部分内容：

- 误差描述：哪里违反了系统期望
- 修正指令：应该按照什么方向把系统拉回正确状态

而且它的一个关键优势在于，它是确定性的。同样的违规，永远触发同样的控制逻辑，不会像模型生成那样发生概率漂移。

除了 linter 之外，更高一层的控制器还包括那些被明确编码下来的工程原则，例如：

- 优先使用共享工具包，而不是随手手写辅助函数
- 不允许 YOLO 式数据探测
- 在边界处必须验证数据形态
- 跨层依赖必须遵守明确的架构方向

一旦这些原则被编码进仓库，它们就不再依赖某个人在 review 里临时提醒，而是会变成系统自动执行的控制逻辑。

> [!note]
> 这也是 Harness Engineering 很有意思的一点：很多过去只存在于“资深工程师脑子里”的判断标准，正在被不断显式化、结构化、程序化。

再往前一步看，控制器甚至可能具备一定的自我进化能力。因为 linter 规则、验证逻辑和工程原则本身，也可能在 Agent 的辅助下被持续生成、调整和强化。换句话说，系统不仅在用控制器约束模型，控制器本身也在变成一个可以被持续改进的工程产物。

### 6.5 执行器：Agent 修改世界的能力

这一层反而是最容易理解的。

在控制论里，执行器是接收控制信号之后，对被控对象真正施加作用的组件，比如阀门、电机、舵面或者机械臂。

放到 Harness Engineering 里，执行器对应的就是 Agent 真正改变外部世界的能力，例如：

- 修改代码
- 运行命令
- 提交 commit
- 打开 PR
- 响应 review 意见
- 重试流程或修复 CI 失败

也就是说，Agent 并不只是一个“会分析”的系统，它还是一个“会动手”的系统。

从这个角度看，Agent 的上限不只是由推理能力决定，也由执行链条决定。只要执行器足够完整，一个单次运行中的 Agent 就可以连续完成一整条工程任务，而不是只给出一个中间建议然后停住。

一个典型流程可能包括：

1. 验证代码库当前状态
2. 复现已报告的问题
3. 记录失败现象
4. 实现修复
5. 重新驱动应用验证效果
6. 记录修复后的结果
7. 发起变更请求
8. 回应 Agent 或人类的 review 意见
9. 检测并修复 CI 构建失败
10. 只在真正需要人类判断时才上报
11. 最终合并变更

这里真正值得注意的，不是“Agent 能做很多事”，而是其中有几个动作天然带有闭环特征：

- 回应 review 意见
- 检测并修复 CI 失败
- 在验证不过时继续迭代

这说明执行器的价值从来不只是把修改写出去，而是让系统具备持续尝试、持续修正、直到满足约束为止的能力。

所以，执行器本身并不是最复杂的部分。真正复杂也真正关键的是：执行器的输出不会停留在外部世界，而是会重新回到传感器系统中，被再次观测、比较和判断，从而形成下一轮控制动作。

## 7. 用控制论拆解 Anthropic 的 Harness

如果说 OpenAI 的 Harness 更像一个经典的多层级联控制系统，那么 Anthropic 展示的是另一条很有代表性的路线：把生成和评估拆成独立 Agent，用对抗性反馈取代自评。

Anthropic 在 2025 年 11 月的《Effective Harnesses for Long-Running Agents》里，已经开始讨论长时运行 Agent 的 harness 设计；到 2026 年 3 月发布的《Harness design for long-running application development》里，这条思路又被进一步推进。

它不是一开始就长成三 Agent 结构的。更早的方案更像两阶段系统：

- 初始化 Agent：建立环境、准备上下文、完成前置设置
- 编码 Agent：逐个实现 feature、推进主任务

而新方案则把职责拆得更明确，升级为三个专职 Agent：

- 规划者（Planner）
- 生成者（Generator）
- 评估者（Evaluator）

从控制论视角看，这个变化不是简单的“多加一个 Agent”，而是把系统从“生成后自我检查”推进到了“由外部独立角色施加反馈”。

### 7.1 被控对象：一个会自我欺骗的生成系统

OpenAI 面对的核心问题是"模型会漂移"。Anthropic 发现了一个更根本的问题：Agent 会对自己的输出过度自信，即使产出平庸也会给出高评价。

这不是偶然的观察，而是一种系统性失效模式。当同一个模型既负责生成又负责评估时，它天然倾向于合理化自己的决策路径——因为评估时它看到的上下文，恰好就是自己生成时留下的推理痕迹。这更像是一种认知闭环：模型在自己的叙事里找到了自洽性，然后把自洽性误判为质量。

从控制论角度看，这意味着被控对象不仅会漂移，还会主动掩盖漂移信号。如果传感器和被控对象共享同一个推理过程，那么传感器本身就已经被污染了。

这也是为什么 Anthropic 的方案选择了一个看起来更"浪费"但更可靠的路径：把评估职责从生成者身上彻底剥离出去。

### 7.2 控制架构：从级联控制到对抗性分离

OpenAI 的架构更像经典的级联控制——多个层级的控制器串联起来，每一层都在做"观测→比较→修正"，但本质上共享同一个被控对象和同一套反馈通道。

Anthropic 的三 Agent 架构则走了另一条路。它的核心设计原则是：生成和评估必须是独立的推理过程，各自拥有独立的上下文、独立的目标函数和独立的判断标准。

三个 Agent 的职责分工：

- **规划者（Planner）**：负责理解需求、拆解任务、定义验收标准。它不写代码，只输出结构化的任务计划和每个子任务的"done"定义。
- **生成者（Generator）**：接收计划，逐步实现。它拥有完整的工具链（代码编辑、终端、浏览器等），但不负责判断自己的产出是否达标。
- **评估者（Evaluator）**：独立审查生成者的产出，对照规划者定义的验收标准进行判断。它可以打回、要求修改、指出具体问题，但不直接修改代码。

从控制论视角看，这个架构的关键创新在于：它把传感器（Evaluator）从被控对象（Generator）中完全解耦出来。评估者不会看到生成者的推理过程，只看到最终产出和预先定义的标准。这样做的好处是，评估信号不会被生成过程的叙事所污染。

### 7.3 为什么对抗性分离比自评更可靠

自评失效的根本原因，可以用一个很简洁的模型来理解：

当 `Generator` 和 `Evaluator` 是同一个推理过程时，评估函数 `E(x)` 的输入 `x` 本身就是由生成函数 `G` 产生的，而且 `E` 和 `G` 共享相同的权重和上下文偏置。这使得 `E(G(input))` 天然倾向于高估质量，因为评估者在生成者留下的语境里思考，很难跳出那个框架。

对抗性分离则打破了这个闭环：

- Evaluator 拥有独立上下文：它不看 Generator 的中间推理，只看产出物
- Evaluator 拥有独立锚点：它对照的是 Planner 预先给定的验收标准，而不是 Generator 的自我叙事
- Evaluator 的激励方向不同：它的"成功"不是认同生成结果，而是发现问题

这在结构上非常接近对抗训练（adversarial training）的思想，只不过不是在权重层面对抗，而是在推理层面对抗。

> [!note]
> 一个直觉性的类比：这更像是把"程序员"和"code reviewer"拆成两个不同的人，而不是让同一个人写完代码后自己 review 自己。

### 7.4 反馈回路：评估驱动的迭代修正

在这个架构里，反馈回路的工作方式和 OpenAI 的级联控制有本质区别。

OpenAI 的闭环更多依赖确定性信号（测试通过/失败、linter 报错、CI 状态），控制器是编码在仓库中的规则。

Anthropic 的闭环则把一个独立 Agent 本身当作控制器。Evaluator 不只是返回 pass/fail，而是生成结构化的反馈：哪里不满足标准、具体差在哪、建议怎么改。这些反馈会被注入 Generator 的下一轮上下文，驱动修正迭代。

整个循环可以表示为：

1. Planner 输出任务计划 + 验收标准
2. Generator 基于计划实现代码
3. Evaluator 对照验收标准审查产出
4. 如果不通过 → 反馈注入 Generator → 回到步骤 2
5. 如果通过 → 进入下一个子任务

这个循环会持续运行，直到所有子任务通过评估，或者达到预设的最大迭代次数。

从控制论角度看，这是一个带有显式终止条件的负反馈闭环。它的误差信号不再是简单的数值偏差，而是语义级别的差距描述。这意味着修正过程可以更加精准——Generator 不只是知道"错了"，还知道"错在哪、离对有多远"。

### 7.5 和 OpenAI 方案的对比

两种架构可以从控制论角度做一个结构性对比：

| 维度 | OpenAI 的级联控制 | Anthropic 的对抗性分离 |
| --- | --- | --- |
| 被控对象特征 | 会漂移的概率系统 | 会漂移且会自我欺骗的概率系统 |
| 传感器设计 | 确定性信号为主（测试、linter、运行态） | 独立 Agent 评估 + 确定性信号 |
| 控制器形态 | 编码在仓库中的规则和标准 | 独立推理的 Evaluator Agent |
| 反馈信号类型 | 结构化错误信息 + 修正建议 | 语义级差距描述 + 具体改进方向 |
| 核心设计假设 | 模型会偏，但可以用确定性约束拉回 | 模型不仅会偏，还会掩盖偏差；必须外部独立评估 |

两者并不是互相排斥的。一个成熟的系统完全可能同时使用确定性控制器（linter、测试）和对抗性评估 Agent，前者处理可形式化的约束，后者处理需要语义判断的质量问题。

### 7.6 Harness 会随着模型能力变化而重构

Anthropic 这条路线里，还有一个非常值得记住的原则：

> Harness 的每一个组件，都编码了一个关于“模型当前局限性”的假设。

这句话的分量很重。它意味着 harness 不是一个抽象上永远正确的系统设计，而是一组针对“当前模型还不擅长什么”所做的临时性工程回应。

例如，当模型还存在明显问题时，系统可能必须补上这些组件：

- 接近上下文窗口极限时会草率收尾，于是需要手动上下文重置
- 处理长任务链时稳定性不够，于是需要把任务拆成 sprint
- 自评偏差太强，于是需要独立的评估者来进行对抗性反馈

这些组件在某一代模型上可能非常必要，但随着模型能力变化，它们未必会一直同样重要。

如果新的模型表现出：

- 上下文稳定性明显增强
- 长链任务规划能力更强
- 调试和代码审查能力更好
- 自动上下文压缩已经足够可靠

那么之前为了补这些短板而存在的一部分 harness 开销，就可以被削减。

这也是一个很成熟的设计哲学：

`找到最简的方案，只在需要时增加复杂度。`

因此，Harness Engineering 不是一条“只会不断堆结构”的路。它同样要求工程师在每一代模型进步之后，回过头去审视：

- 哪些控制结构仍然承重
- 哪些组件已经可以退休
- 哪些旧假设已经不再成立

> [!note]
> 这大概是 Anthropic 路线最有启发性的地方之一：不是把 harness 当成固定模板，而是把它当成会随着模型能力迁移而持续重构的外部系统。

## 8. OpenAI vs. Anthropic

把 OpenAI 和 Anthropic 的 Harness 放在一起看，会发现它们虽然路径不同，但其实在控制论层面解决的是同一个问题：

`如何让一个随机系统在长时间运行中保持稳定，并持续逼近目标状态。`

OpenAI 更像是在不同时间尺度上搭建多层嵌套反馈回路，用确定性工具和工程规则去持续修正偏差；Anthropic 则更强调把生成者和评估者拆开，用对抗性的 Agent 间博弈去压制自评偏差，让质量逐步收敛。

可以把两者先做一个结构化对照：

| 维度 | OpenAI Harness | Anthropic Harness |
| --- | --- | --- |
| 控制架构 | 多层嵌套反馈回路 | 三体对抗架构 |
| 核心抽象 | 更像工业控制系统 | 更像生成与评估分离的对抗系统 |
| 反馈信号来源 | 确定性工具、运行态信号、Agent review | 专职评估 Agent、交互结果、可执行验证 |
| 主观质量控制 | 质量文档、人工评分、长期趋势跟踪 | 独立评估者、对抗迭代、结构化验收标准 |
| 典型创新点 | 在多时间尺度上自动巡检和修正 | 把主观标准转化为可验证条件，并通过独立评估压制自评偏差 |

如果再把它们往抽象层抬高一点，可以这样理解：

- OpenAI 的重点是 `让系统在多层反馈里自动纠偏`
- Anthropic 的重点是 `让系统在角色分离里避免自我欺骗`

前者更擅长处理那些可以被形式化测量的偏差，比如：

- 测试是否通过
- 代码是否违反架构规则
- 服务是否达到性能指标
- 运行状态是否出现异常

后者更擅长处理那些难以被单一确定性指标定义的质量问题，比如：

- UI 是否足够有设计感
- 交互是否真的顺手
- 方案是否只是“能用”，但整体仍然粗糙

但殊途同归。放到控制论框架里，两者都在验证同一个更底层的原则：

> 稳定性来自反馈，而不是前馈。

也就是说，不管是多层嵌套回路，还是对抗性 Agent 分工，真正让系统长期可用的都不是“起点时喂得多准”，而是系统是否具备持续感知偏差、放大有效反馈并压制错误累积的能力。

## 9. Context 和 Harness 的分界线

到这里，其实可以把 Context Engineering 和 Harness Engineering 的分界线说得更清楚一点。

一个很直观的说法是：

- `Context Engineering` 更接近开环（Open-loop）
- `Harness Engineering` 更接近闭环（Closed-loop）

### 9.1 Context Engineering 为什么更像开环

在 Context Engineering 里，开发者会精心组装信息、设计 pipeline、决定给模型看什么，再把这些内容送进模型，等待输出结果。

如果结果不理想，通常的修正方式是：

- 调整 prompt
- 调整检索内容
- 改写上下文结构
- 重新执行一次

这当然有效，但它本质上仍然更接近开环系统。因为系统本身并没有内建的持续纠偏机制，修正动作更多依赖人类在回合之外重新调整输入。

换句话说，Context Engineering 优化的是：

`这一次推理之前，我该怎样把信息准备得更好？`

### 9.2 Harness Engineering 为什么更像闭环

Harness Engineering 则不止于“把输入准备好”，它更关心输出之后会发生什么。

在这种系统里：

- 输出会被持续测量
- 测量结果会和目标状态比较
- 偏差会被显式识别
- 修正动作会被自动触发
- 而且这种修正不依赖人类即时介入

这就是典型的闭环控制逻辑。系统并不假设自己第一次就一定正确，而是假设偏差迟早会出现，所以要把“发现偏差并拉回目标轨道”内建为系统能力。

### 9.3 两者真正的差异不在单次输出

这两类系统最容易被混淆的地方在于：在上下文足够好的情况下，它们某一次的输出质量可能非常接近，甚至完全一样。

真正的差异不在于某一枪打得准不准，而在于：

`当输出已经偏了之后，系统是沉默的，还是会主动把它拉回来。`

从这个角度看：

- 开环系统的问题，是它很难应对扰动
- 闭环系统的力量，在于它能够处理不确定性

即便 LLM 在某次推理中发生漂移、复制了坏模式、或者沿着一条错误路径越走越远，闭环系统仍然有机会在不同时间尺度上检测并修正这些偏差。

### 9.4 信号处理和控制工程的区别

如果用更抽象一点的语言来比较，可以这样理解：

> Context Engineering 优化的是单次推理中的信息配比，本质上更接近信号处理；Harness Engineering 优化的是系统在时间维度上的渐近稳定性，本质上更接近控制工程。

前者的目标，是让每一次发射尽量更准。  
后者的目标，是让整个弹道在飞行过程中持续被修正。

这也是为什么两者并不是简单的上下位替代关系。Context 解决的是“模型看什么”，Harness 解决的是“系统在模型看错、做偏、跑歪之后怎么办”。

## 10. Superpowers：开源社区的 Harness 实践标杆

如果前面的案例更多来自大公司内部实践，那么 Jesse Vincent 的开源项目 `Superpowers` 代表的是另一种很有意思的维度：`被社区投票验证过的 Harness Engineering。`

它的重要性不只在于流行，更在于它把很多原本只存在于团队流程、资深工程师经验和内部规范里的东西，压缩成了一套可以跨平台复用的行为约束系统。

从形式上看，Superpowers 更像一组可组合的 Skill 文件；但从控制论角度看，它其实是一套写给编码 Agent 的外部控制系统。

### 10.1 被控对象：上下文污染和目标偏移

Superpowers 瞄准的不是“模型不会写代码”这种最表层问题，而是长时任务里更常见的两类失败模式：

- 上下文窗口被越来越多的无关信息污染
- 任务在推进过程中逐步偏离原始目标

它的一个核心应对方式是 `上下文隔离`。每个任务派生出新的 subagent，不默认继承主会话的全部历史，而是由上游控制者只注入当前任务真正需要的信息。

从控制论角度看，这等于让每个执行器都尽可能从更干净的初始状态启动，从源头压低漂移和污染累积。

### 10.2 控制器：冻结的流程链和硬性关卡

Superpowers 最有代表性的控制器设计，是把一条原本可能被模型跳过的开发流程，冻结成一条必须遵守的阶段链：

`Brainstorming -> Writing Plans -> Execution`

每个阶段之间都有硬性关卡。例如：

- 没有完成 brainstorming，就不能直接开始写代码
- 没有把 spec 写清楚，就不能进入详细计划
- 没有通过审查，就不能进入下一步执行

这种设计的关键不在于“流程更复杂”，而在于它把“正确的工作顺序”编码成了不可轻易绕过的控制逻辑。

> [!note]
> 这类 hard gate 很像工业控制里的联锁机制：不是提醒你最好这样做，而是在条件不满足时直接阻断后续动作。

### 10.3 传感器：两阶段独立审查

Superpowers 的另一层传感器设计，是把审查拆成两个不同目标的独立 reviewer：

1. `Spec Compliance Reviewer`：先检查“做的是不是对的事”
2. `Code Quality Reviewer`：再检查“这件事做得好不好”

顺序不能颠倒。因为系统首先要保证方向正确，其次才讨论质量优化。

如果任一审查不通过，执行者就必须修复后重新接受同一类型的复查，直到过关为止。

这使得反馈信号不只是“通过 / 失败”，而是被拆成了不同维度的质量测量：目标对不对、实现好不好、测试够不够、模式是否健康。

### 10.4 执行器：按任务价值分配模型成本

Superpowers 还有一个很有工程味的设计点：它并不假设所有任务都值得用最强模型去做，而是把模型选择本身也纳入控制系统。

更重的模型用于：

- 架构判断
- 设计与 spec
- 高风险审查

更轻的模型用于：

- 局部实现
- 明确范围内的编码任务
- 已经被 spec 限定得很细的执行步骤

这其实是一种经典的资源分配策略：把有限的计算预算集中在最需要判断力的节点，而不是平均洒在整个流程里。

### 10.5 一个很特别的点：用反馈回路约束反馈回路

Superpowers 最有意思的地方，也许不是某一个单独的 Skill，而是它开始系统性地测试和强化 Skill 本身。

如果说 Skill 文件本身就是反馈回路的实现，那么 `TDD for Skills` 本质上是在对反馈回路本身做反馈控制，也就是一种元控制。

这可以被理解成：

- `RED`：构造压力环境，让 Agent 在压力下跳过 Skill 或违反流程
- `GREEN`：强化 Skill 指令，让 Agent 在同类环境里重新遵守流程
- `REFACTOR`：优化表达，减少冗余，让约束更稳也更轻

换句话说，它不只是拿 harness 去约束任务执行，而是在反过来迭代 harness 本身。

从这个角度看，它和前面提到的 OpenAI 路线、Anthropic 路线其实是同构的：

- OpenAI 在迭代垃圾回收和多层反馈结构
- Anthropic 在重审每一个组件背后的模型局限假设
- Superpowers 在测试 Skill 是否真的能约束 Agent

三者都不是把 harness 当成一次性搭好的外壳，而是在持续优化“约束是否真的生效”。

### 10.6 为什么这个案例重要

Superpowers 的意义，不只是它是一个受欢迎的开源项目，而是它证明了一件事：

> 开发者真正缺的，往往不只是更强的模型，而是一套能让任意模型更稳定工作的反馈约束体系。

如果这个判断成立，那么 Harness Engineering 就不是大厂内部的特殊技巧，而是一条会逐步外溢到整个开源生态、工具生态和个人工作流中的普遍方法。

## 11. 四个维度，一个结论

把前面的几条线放在一起看，会发现不同团队、不同规模、不同场景，其实都各自触到了 Harness Engineering 的一个关键维度。

- `Vercel / Superpowers`：约束设计  
  好的 Harness 不是给模型加更多管道，而是找到正确的抽象层级，在干净的边界内释放模型的自适应能力。

- `LangChain`：闭环反馈  
  不换模型、只改反馈回路和控制策略，也可能带来跨级别的性能提升。系统上限不只由模型决定，也由 harness 质量决定。

- `Anthropic`：状态管理  
  当 Agent 需要跨越会话边界持续工作时，控制系统的状态必须外部化、持久化、增量化，不能只依赖模型自己的记忆。

- `OpenAI`：多层控制  
  当系统需要在不同时间尺度上稳定运行时，就必须把传感器、控制器、执行器和反馈回路编织成多层次结构，而不是指望单次推理天然正确。

如果把这些案例再往上抽象，可以收敛到一个更高层的判断：

> 优化 LLM 系统的稳定性和可靠性，真正的杠杆不只在模型本身，而在包裹模型的控制架构。

这大概就是 Harness Engineering 最核心的命题。

### 11.1 但这不意味着 Context Engineering 过时了

这里最容易被误解的一点是：既然 Harness 更高一层，那是不是说明 Context Engineering 已经过时了？

恰恰相反。

更准确的说法应该是：

`Harness Engineering 是 Context Engineering 的上位框架，而不是它的替代品。`

Context Engineering 仍然非常重要，因为它决定了模型在每一次推理里到底能看到什么。动态上下文组装、渐进式披露、KV-cache 优化、RAG、记忆裁剪，这些工作都不会消失，它们仍然是系统质量的基础。

只是从控制论角度看，Context 更像是 harness 里的传感器层和输入优化层，而不是系统的全部。

### 11.2 一个很好的说法

有一句话把两者关系说得很清楚：

> Part of harness engineering is building a good delivery mechanism for context engineering.

如果把它翻成更直白的工程语言，大概就是：

> Harness Engineering 的一部分工作，是为 Context Engineering 构建好的交付机制。

这句话的重要性在于，它避免了一个二选一式的误解。问题从来不是“是做 Context，还是做 Harness”，而是：

- Context 能不能把对的信息送到模型面前
- Harness 能不能让这些信息真正进入一个可控、可验证、可修正的系统流程里

换句话说，光有传感器还不够。你还需要：

- 控制器：编码在仓库和流程中的判断标准
- 执行器：Agent 真正修改世界的能力
- 反馈回路：多层检测、比较和纠偏机制
- 状态管理：跨回合、跨阶段、跨会话的外部记忆与进度结构

如果一定要打一个比方，可以这样说：

- Context Engineering 给了系统“眼睛”
- Harness Engineering 给了系统“眼睛、手、大脑和记忆”

所以，这篇文章最终想收束到的，不是“Context 已死，Harness 登场”，而是：

`Context 是 Harness 的基础层，Harness 是把 Context 变成长期稳定系统能力的上层结构。`

## 12. 从 “In the loop” 到 “On the loop”

如果再把这个变化往人的角色上收束，可以得到一个更大的结论：

`工程师正在从 in the loop 走向 on the loop。`

过去，在很多 AI 辅助开发流程里，人类工程师还停留在执行闭环内部，像一个疲惫的校对员一样，逐行审查、逐处修补、逐次确认模型产出的代码。这是一种典型的 `in the loop` 角色：人类自己就是闭环中的人工控制器。

但随着模型能力上升、任务链条变长、系统运行时间拉长，这种角色会越来越不可持续。它的问题不只是效率低，而是人力本身并不是一个适合 `7 x 24` 持续吸收系统熵增的控制部件。

Harness Engineering 在某种意义上，正是在终结这种停留在自然语言层面的脆弱博弈。它开始更诚实地面对这样一个事实：大语言模型首先是一个高熵、概率性的动力系统，而不是一个只要提示得当就会稳定服从的确定性程序。

也因此，工程重点发生了迁移。真正重要的，不再是人亲自卡在每一次生成里做微观修补，而是人站到整个控制环的上方，去设计：

- 哪些约束是不可推翻的
- 哪些信号会被持续测量
- 哪些偏差必须自动修正
- 哪些状态需要被外部化和持久化
- 哪些节点才值得人类真正介入

从控制论语言看，这意味着人不再主要扮演闭环内部的“手工执行器”或“临时纠错器”，而开始扮演闭环之外的：

- 系统设计者
- 规则制定者
- 验收标准定义者
- 反馈结构编排者

这其实就是从 `in the loop` 到 `on the loop` 的本质变化。

> [!note]
> 前者意味着人被困在回路里不断补洞；后者意味着人站在回路之上，决定这个系统应该怎样感知、比较、修正和收敛。

从这个角度看，Harness Engineering 的价值并不只是“让 Agent 更能干”，而是给了工程师一种新的位置。开发者不再只是微观地“提示”模型，而是通过架构、法则和反馈机制，去宏观地“控制”整个智能系统。

如果说 Prompt Engineering 的时代更像是在研究如何和模型说话，那么 Harness Engineering 的时代更像是在研究：

`如何把一个会犯错、会漂移、会自我高估的概率系统，稳定压缩进符合工程标准的控制域里。`

## 13. 我的理解

- Prompt Engineering 并没有过时，它只是从主角变成了底层能力。
- Context Engineering 让我们开始认真对待“上下文是一种系统资源”。
- Harness Engineering 则进一步提醒我们：AI 系统的可靠性，不应该寄托在模型一次答对，而应该寄托在系统能否持续发现并修正错误。

对工程团队来说，这个演进意味着一个很重要的认知变化：

> AI 工程的重点，正在从“优化模型输出”转向“设计模型工作的环境”。

## 附录：X-Engineering Timeline

如果把视角再拉高一点，会发现 Prompt Engineering、Context Engineering、Harness Engineering 这几个概念，并不是彼此割裂地突然出现，而是在同一条演化路径上逐步长出来的。

从早期的 Prompt Engineering，到后面被广泛采用的 Context Engineering，开发者一直在试图通过不断优化输入端的信息质量，来引导模型朝着期望的方向输出。而 Harness Engineering 则进一步把问题推进到系统层：通过构建包含机械约束、确定性反馈和持续状态管理的闭环控制系统，把高熵的模型输出强制收敛到稳定的正确状态。

换句话说，这不是几个孤立术语的并列，而是一条自然递进的工程时间线：

- `Prompt Engineering`：优化表达方式
- `Context Engineering`：优化输入信息结构
- `Harness Engineering`：优化整个系统的控制与稳定性

也正因如此，后面如果要继续展开时间线，最值得追的问题不是“哪个词先被谁发明”，而是：

- 谁在什么时间点做了什么实践
- 哪些技术瓶颈推动了概念切换
- 哪些产业事件让这些方法从局部技巧变成了显式范式

这个附录的意义，不是重复正文，而是给这些概念的演化脉络留一个入口。

### 一个关键时间点：2026 年 2 月

一个很值得记住的节点，是 2026 年 2 月 11 日 OpenAI 工程师 Ryan Lopopolo 发布《Harness engineering: leveraging Codex in an agent-first world》。

这篇文章之所以重要，不只是因为它给出了一个清晰命名，还因为它第一次把这套方法以极强的工程结果绑定在一起公开展示出来。文中写到：

- 一个起步仅 3 人的小团队
- 在大约 5 个月内
- 用 Codex Agent 生成了约百万行代码
- 打开并合并了约 1500 个 PR
- 平均每位工程师每天约 3.5 个 PR
- 且“没有一行是人手写的”

这些数字让 Harness Engineering 不再只是一个抽象概念，而第一次显得像一种可被工业化验证的方法。

更有意思的是，`Harness Engineering` 这个说法在 2026 年 2 月上旬就已经开始流传，常被归因于 Mitchell Hashimoto 这一时期的相关表述。更稳妥的说法是：OpenAI 的这篇文章让这个概念被大规模传播和固定下来，而命名本身则很可能是在更小范围的实践讨论中先出现的。

从时间线上看，这一阶段的重要性在于：行业终于开始意识到，真正决定 Agent 系统上限的，不只是模型本身，而是模型外面的约束、验证、反馈和状态结构。
