# Claude Code 的 goal 模式

**TL;DR** — Claude Code 提供 `/goal` 和 `/plan` 两种任务执行方式。 plan 模式先制定详细步骤再执行；goal 模式设定可验证的目标，由 AI 自主探索路径并通过 "做 → 验 → 修复 → 验"的循环直到达成。goal 模式更适合复杂、探索性强的任务。 

## 核心概念

### 两种模式的本质区别

维度 | /plan 模式 | /goal 模式  
---|---|---  
**执行方式** | 先制定详细计划，按步骤顺序执行 | 设定目标 + 验证条件，AI 自主探索最优路径  
**灵活性** | 计划一旦确定，中途调整成本高 | 随时根据验证结果动态调整策略  
**容错性** | 某步出错需人工干预重排计划 | 自动发现错误 → 修复 → 再验证，闭环自愈  
**人工介入** | 需审阅计划、确认每步、处理偏差 | 人只定目标和验收标准，中间过程 AI 自主搞定  
**适用场景** | 需求明确、步骤固定的任务 | 复杂任务、需要多轮试错调优的任务  
**Token 消耗** | 相对可控 | 可能更高（多轮验证迭代）  
  
### goal 的自验证循环

goal 模式的核心机制是一套自验证的闭环：

做 → 验 → 修复 → 验 → ... → 通过

AI 自己判断"做好了没"，没做好就继续修，直到满足验收条件 

## goal 模式的核心优势

自验证闭环

#### 无需人工盯梢

AI 自己判断完成度，未达标自动修复再验证。人只需设定验收标准，不需要在每一步确认"这样可以吗"。

减少上下文切换

#### 专注目标而非过程

plan 模式下人需要审阅计划、确认每步、处理偏差。goal 模式下，人只负责设定目标，中间过程 AI 自主搞定。

探索性任务

#### 适合路径不确定的场景

比如"优化代码性能"，plan 可能先写分析步骤，但实际瓶颈可能不在预期位置。goal 直接设定"提升 30%"，AI 自己测、自己调。

动态调整

#### 根据反馈实时修正

执行过程中发现原计划行不通？goal 模式会自动换策略。plan 模式则需要人介入重新规划。

## 何时用哪种模式？

适合 /plan

#### 需求明确、步骤固定

"按这份设计文档实现三个 API 接口"  
"把这段 Python2 代码迁移到 Python3"  
需要人把控每个环节的任务

适合 /goal

#### 目标清晰、路径不确定

"重构这个模块，保持功能不变但减少 50% 代码量"  
"找出这个 bug 并修复，所有测试通过"  
愿意让 AI 自主探索、接受多轮迭代

★

**关键洞察** ：plan 是"先计划再执行"，goal 是"定个目标你自己想办法达成"。 当任务涉及探索、试错、多轮调优时，goal 模式通常更高效。

## 配合 workflow 自动化

goal 的验证循环可以封装成可复用的 workflow，一次配置多次运行：
    
    
    # 伪代码示例：goal + workflow 的自动化循环
    workflow "code-refactor-loop" {
      goal = "重构模块，减少 50% 代码量，所有测试通过"
      
      loop {
        step: 执行重构
        verify: 运行测试套件
        if (测试失败) {
          step: 分析失败原因并修复
          continue  // 回到验证
        }
        verify: 统计代码行数
        if (减少不足 50%) {
          step: 寻找更多简化空间
          continue
        }
        break  // 目标达成，退出循环
      }
    }

如果不介意 token 消耗，用 workflow 来实现这个循环是最推荐的做法。

## 常用命令

`/goal ultrathink ultracode`

使用 goal 模式，启用深度思考（ultrathink）和高质量代码生成（ultracode）。 适用于复杂任务，让 AI 在思考深度和代码质量上加强。 

`/plan`

传统的计划模式。AI 先制定详细步骤清单，经确认后按顺序执行。 适合需求明确、需要人把控每个环节的任务。 

`/loop`

循环执行某个操作。注意：goal 模式里的"循环"不是 /loop 命令， 而是 goal 内置的自验证循环机制（做 → 验 → 修复 → 验）。
