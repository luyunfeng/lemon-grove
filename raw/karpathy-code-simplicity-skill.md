# Karpathy 风格的代码简化 Skill

> [!summary]
> 这个仓库不是在讲“怎么把代码写得更高级”，而是在把 Karpathy 对 LLM coding pitfalls 的观察，压缩成一套可直接放进 `CLAUDE.md`、Cursor rules 或 skill 文件里的行为准则。

## 这个仓库在做什么

- 把 Karpathy 对代码代理常见问题的观察，整理成一份可复用的 Claude Code 指南。
- 核心目标是让模型少做四类事：
  - 乱猜
  - 过度复杂化
  - 改到不该碰的地方
  - 没有验证就推进
- 仓库同时提供了：
  - `CLAUDE.md`
  - Cursor project rule
  - 可复用的 skill 文件

## 四条原则

### 1. Think Before Coding

- 不要默认替用户补全假设。
- 有歧义就问，不要悄悄选一个解释继续做。
- 有 tradeoff 就讲出来，不要假装只有一个答案。

### 2. Simplicity First

- 用最少的代码解决问题。
- 不做用户没要求的抽象和配置。
- 如果一个问题能更短、更直接地解决，就应该更短、更直接。

### 3. Surgical Changes

- 只改用户要求的部分。
- 不顺手重构旁边没坏的代码。
- 不碰无关的注释、格式和死代码。

### 4. Goal-Driven Execution

- 把命令式任务改写成可验证的成功标准。
- 先定义验证方式，再执行改动。
- 对多步任务，最好先列出一个短计划和验收点。

## 我的理解

- 这类 skill 的价值，不在于“让模型更会写”，而在于“让模型更少犯工程性错误”。
- 它本质上是在把资深工程师的编程卫生习惯，写成可以反复套用的系统约束。
- 对 agent 来说，这比单纯要求“写得更聪明”更有效，因为它直接约束了行为边界。

## 适合什么场景

- 代码修改会牵一发而动全身的项目
- 需要严格控制 diff 的团队
- 经常遇到“模型擅自补假设”的协作场景
- 希望把提示词规范化为项目级约束的团队

## 一句话总结

这不是一个追求"更强模型"的 skill，而是一套把 Karpathy 式代码卫生原则落成工程规则的模板。
