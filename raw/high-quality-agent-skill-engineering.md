# 高质量 Agent Skill：不是更长的 Prompt，而是可复用的专家能力包

来源微信公众号

作者霍格沃兹软件测试开发

时间2026-07-20 抓取

原文[mp.weixin.qq.com](https://mp.weixin.qq.com/s/jgW83N-d113kyPGiN8GZ5Q)

**核心观点：** 高质量 Skill 不是把常用 Prompt 封装成长提示词，而是把专家决策、反模式、模板、工具、验证流程和迭代样本组织成一个可复用、可验证、可迭代的能力包。

文章的面试答案本质是：Skill 质量考察的是 Agent 工程化能力，而不是提示词技巧。它要能稳定完成一类任务，而不是只在一次演示里表现好。

## 面试官真正考察什么

考察点| 真正想听的内容| 回答重点  
---|---|---  
任务抽象能力 | 能否判断什么任务值得 Skill 化。 | 不是所有任务都封装，只有高价值重复问题才值得沉淀。  
专家经验沉淀能力 | 能否把人的判断规则写进 Skill。 | 写清触发条件、边界、决策树、反模式、示例和模板。  
质量保障能力 | 有没有验证、评测和迭代机制。 | 用 checklist、脚本、评测集和新会话验证稳定性。  
  
## 是否值得 Skill 化

**反复出现** 团队每天或每周都会做类似任务

**足够复杂** 不止一句 Prompt，涉及多步骤和多约束

**专家判断** 熟手和新手输出差距明显

**质量要求** 输出需要结构、标准、验证或审计

**可沉淀** 规则、模板、脚本、样本可以复用

**值得维护** 收益覆盖编写和迭代成本

文章给出的公式：适合做成 Skill 的任务 = 反复出现 + 足够复杂 + 有专家判断 + 对输出质量有要求。简单、低频、一次性的任务不该强行 Skill 化。

## 高质量 Skill 的九个工程要点

### 1\. 写判断，不写废话

核心不是“根据需求生成结果”，而是写清什么情况下走方案 A、方案 B、停止或补充信息。

### 2\. 明确反模式

禁止编造业务规则、跳过验证、直接执行高风险修改、输出无法验证的空泛建议。

### 3\. 提供模板和示例

模板保证格式稳定，示例保证表达和深度稳定。

### 4\. 控制上下文成本

删掉通用废话，只保留触发条件、边界、专家判断、模板、工具导航和验证方式。

### 5\. 按风险调自由度

高风险任务降低自由度；分析类任务保留分析空间，但约束维度、依据和优先级。

### 6\. 复杂任务配工作流

长链路任务必须写清每一步做什么、产出什么、哪些步骤不能跳。

### 7\. 分层组织文件

`SKILL.md` 写核心流程，`references` 放细则，`templates` 放模板，`scripts` 做确定性校验。

### 8\. 关注触发质量

描述要写清什么时候用、什么时候不用，避免该触发不触发和不该触发乱触发。

### 9\. 建验证闭环

用 checklist 和脚本检查输出；失败时让 Agent 修正，再输出最终结果。

## 决策树示例：测试用例生成

### 需求完整时

  * 先生成主流程用例。
  * 再补充异常流程。
  * 最后补边界、权限、数据一致性和幂等场景。

### 需求不完整时

  * 不要编造不存在的业务规则。
  * 先标记缺失信息。
  * 再基于已有信息生成可确认的草稿。

### 高风险需求时

  * 涉及支付、权限、资金、删除、审批时，必须提升风险等级。
  * 必须补充回滚、审计、重复提交、异常中断场景。

### 输出要求

  * 标注优先级和自动化建议。
  * 结论必须可执行、可验证。
  * 完成后按 checklist 自检。

## 验证闭环

**Baseline** 不用 Skill 跑真实任务，记录典型失败

**Extract Rules** 从失败样本提炼规则、反模式和模板

**New Session** 新会话只加载 Skill 重新测试

**Checklist** 检查覆盖、优先级、幻觉、格式和验证性

**Script** 能脚本化的校验交给脚本

**Eval Set** 形成评测集，持续迭代

文章强调：真正高质量的 Skill，不是一次输出惊艳，而是在不同输入、不同会话、不同边界条件下稳定提升结果。

## 面试回答骨架

我不会把 Skill 简单理解成 Prompt，而是把它看成 Agent 系统中的可复用专家能力单元。高质量 Skill 的核心，是把专家经验沉淀下来，并在真实任务里稳定提升 Agent 的执行质量。 

  1. 先判断任务是否值得 Skill 化：重复、复杂、有专家判断、有质量要求。
  2. 提取专家决策逻辑：走哪条路径、何时停止、何时补信息、何时不能执行。
  3. 编写简洁指令：保留任务特有规则，删除通用废话。
  4. 配套资源和工具：模板、references、scripts、checklist。
  5. 验证触发质量和执行质量：看该不该触发、是否误触发、流程是否执行。
  6. 用真实任务持续迭代：基线、失败样本、新会话测试、评测集。

## 我的理解

这篇文章最有价值的地方，是把 Skill 从“Prompt 封装”重新定义为“专家经验产品化”。如果一个 Skill 只有漂亮话，没有触发边界、决策逻辑、反模式、模板和验证闭环，它只是更长的提示词。

我会用三个指标判断 Skill 是否成熟：第一，它能否减少同类任务中的典型失败；第二，它能否在新会话中稳定触发并执行；第三，它的输出是否能被 checklist 或脚本验证。满足这三点，才算从个人经验走向团队能力。

对企业 Agent 系统来说，Skill 的长期价值是形成可维护的能力资产：随着失败样本增加，Skill 里的反模式、评测集、模板和脚本不断进化，Agent 才会越来越像团队里的熟手，而不是每次重新靠上下文临场发挥。
