# Agent-Native-Doc：给 Agent 领域知识只需要一个 Skill

## 核心论点

agent-native-doc 的目的是给内部仓库冷启动并持续维护一套 Agent 原生文档系统——把代码外、但会影响改代码决策的领域知识，沉淀成 agent 能持续读取、验证和维护的工作文档。

> [!important] 业界共识
> OpenAI 的 harness engineering 和 Anthropic 的 Claude Code 实践得出一致结论：要让 agent 在复杂仓库里干好活，需要一套显式的、仓内的、能持续维护的领域知识系统。

## 一、为什么不做一个总结代码的 AI Doc

### AI Doc 存什么

判断标准：如果一段文档可以随时从代码里重新生成，那它就不值得长期存。更值得存的是代码生成不出来的东西。

**代码里能看到的：**
- 函数、类型、目录结构
- 单仓内的调用关系
- 具体算法实现

**代码外才知道的：**
- 跨仓库/跨团队契约（IDL、无 Schema JSON、三方库含义）
- 历史评审、事故复盘沉淀的决策
- 哪些验证方式才算有效（本地脚本、集成测试、数据监控）

### AI Doc 存在哪

> [!tip] 仓库就是 source of truth
> git 仓库本身在 Coding 领域是最 AI Native 的存储介质——云边一体、可分发、多版本、个性化。

外部资料（Lark 文档、Meego、聊天记录、Oncall）不适合做默认入口，因为：
- **太多太散**：从复杂业务信息中获取有用知识可能需要一个 AGI
- **太旧**：文档几年没人维护是常态
- **权限不一定通**：新同学进来需要多长时间申请好权限

外部资料不应直接变成影响决策的证据，应经过蒸馏沉淀到仓库中：事实回到原始出处，仓内文档保存经过判断的结论。

> [!note] 即使模型抗噪能力增强，In Repo Doc 仍有价值
> 这是团队把判断显化的地方：哪些结论已被确认，哪些取舍已形成共识，哪些规则值得和代码一起 review、diff、回滚、演进。

## 二、具体如何做：三件事

### 1. 捞知识

从 Lark、MR、git log 通过 owner 访谈蒸馏，初始化领域文档。

| 来源 | 做什么 | 主要问题 | 处理方式 |
|------|--------|----------|----------|
| Lark CLI 搜索 | 用 `lark-cli search` 找事故纪要、设计文档、聊天记录，蒸馏进主题文档 | 老文档有信息但不一定正确 | 结合 MR 证据和 owner 访谈校验，不把外链当最终答案 |
| MR / git 挖掘 | 扫描热点代码、反复修改的位置、注释和提交信息 | 能看到"改了什么"但不知道"为什么" | 把候选事实变成具体问题，交给 owner 确认 |
| 冷启动访谈 | 和 owner 多轮确认真正的知识 | 成本高，问题宽泛就没有信息增量 | 问题必须落在证据上，给 owner 可确认的具体假设 |

### 2. 统一语言

沉淀本仓库特有名词、动词、实体关系和易混淆概念，减少人与模型之间的语义偏差。

- 不收录 timeout、handler、error 等通用概念
- 重点记录像 gateway、rerank、理想态这类特定语境下才有精确定义的词
- 写入 `docs/CONTEXT.md`

> 受 [grill-with-doc skill](https://github.com/mattpocock/skills/blob/main/skills/engineering/grill-with-docs/SKILL.md) 启发。

### 3. 维护闭环

| 路由 | 触发方式 | 更改内容 |
|------|----------|----------|
| 冷启动 | 第一次给仓库建 agent 文档 | 产出文档骨架、初始化整体文档到仓库内 |
| 主动维护 | 用户主动说"docs 错了/旧了/混乱"，或再次运行 | 大范围增量编辑，重新走搜索蒸馏过程 |
| 被动维护 | 对话中出现"记下这个/把结论固化进文档" | 小范围增量维护，只动部分主题文档少量内容 |

## 三、仓库里的样子

### 目录结构

```
agent_eval/
├── AGENTS.md                    # agent 入口与仓库级约定
├── README.md
├── docs/
│   ├── CONTEXT.md               # 仓库领域词表 / 统一语言
│   └── agent-native/            # agent-native-doc 冷启动产物
│       ├── README.md
│       ├── credentials-and-tenants.md
│       ├── maintenance-guide.md
│       ├── multi-scaffold-eval.md
```

### CONTEXT.md 示例

领域语言记录格式——定义 + 不要混用 + 证据：

```markdown
### 短期记忆 / Message
- 定义：用户、分身、Agent 或 Tool 在一个 conversation_id / session_id 下写入的一条上下文消息。
- 不要混用：不要把 ABase 中的 message key、RDS 表 message、IDL MessageData 完全等同。
- 证据：app/model/message.go、Lark《记忆DSL》（2026-01-29）、owner 确认（2026-05-19）。
```

### 主题文档示例

确认的操作规则格式——已确认 + 依据 + 约束：

```markdown
### 2.1 <某条已确认的操作规则>
- [原文为某内部仓库的凭证存放配置示例，涉及内部配置细节，收录时已移除；格式为「已确认结论 + 依据 + 约束」]
```

## 四、迭代中的痛点和思考

### 评测驱动可以解决一些问题，但不是所有

> [!warning] 评测不是万能的
> 文档类/Coding 类 skill 很多时候没有明确的 golden truth。写得好不好、有没有抓到关键判断，很大程度上依赖人的判断。

推荐的轻量迭代方式：

1. **先 vibe create**——把 skill 跑起来，形成能工作的版本
2. **用少量基础评测抓明显问题**——四五个 case 检查基础能力
3. **真实使用中的 vibe check**——把生成的 doc 喂给真实同事、真实仓库、真实任务

### 踩过的坑

| 痛点 | 暴露方式 | 解决方式 |
|------|----------|----------|
| 跨 Agent 兼容 | 只在 Codex 测试，Claude 不兼容 | 尽可能测试所有模型和 Harness |
| 评测本身不稳定 | 涉及多轮时 timeout，结论变化大 | 总时长上限、重试和快速失败 |
| 评测被记忆污染 | 跨会话携带技能上下文 | 设定独立项目和 Coding Agent 路径，隔离记忆 |
| 结构对≠内容对 | 基础规则评测通过但实际完全不对 | 隐藏知识和不干扰类 rubric 才能证明内容有用 |

### 克制：不做什么比做什么更重要

> [!quote] 核心原则
> 不做什么，往往比做什么更重要。最高 ROI 的事，不是一上来就搭知识图谱，而是先建一个最基础、但能渐进式加载、有明确维护规则的文档系统。

不做的：定时维护、历史 commit 重放、接入 Meego、图存储、多路检索链路。
理由：基于飞书信息 + 代码 source of truth 已能覆盖 90% 以上问题。

### 和其他 Skill 集成：高内聚，低耦合

- 在 AGENTS.md 里约定：思考/脑暴/方案评审/风险质询类 skill 先读取 `docs/CONTEXT.md` 和 `docs/agent-native/`
- agent-native-doc 仍然自包含，不强依赖其他 skill
- 每个 skill 只做好自己的事

> [!tip] 集成原则
> 不要搞 Super Skill，不要让多个 skill 之间产生重依赖。高内聚，低耦合。如无必要，勿增实体。

## 我的理解

这篇文章的核心洞察是：==Agent 需要的不是更多上下文，而是更可信的上下文==。仓库作为 source of truth，加上蒸馏后的领域知识，比堆砌原始信息更有效。

三个关键设计决策值得记住：
1. **只存代码生成不出来的知识**——避免文档成为代码的冗余副本
2. **三层维护路由**——冷启动/主动/被动，避免"记一句话"被升级成全量重审
3. **高内聚低耦合**——每个 skill 自包含，通过 AGENTS.md 约定集成方式

与 [[harness-engineering-from-prompt-to-context|Harness Engineering]] 和 [[claude-code-large-codebases-best-practices|Claude Code 最佳实践]] 的观点一脉相承：决定上限的是 harness，不是模型。
